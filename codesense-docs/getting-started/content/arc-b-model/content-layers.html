Arc B · Content layers

Four places. Checked per file, closest first.

A file in your context lives in exactly one place: a repo's content folder, your private space, your team, or a parent team. Where it lives decides who sees it and whether it is pushed. When an agent launches, CodeSense looks each file up in the order below and takes the closest copy. Learn the four rows and the one rule about launches, and you've learned the model.

The priority stack

Highest priority first. For every file an agent's launch asks for, CodeSense checks this stack top-down and uses the first place that has a file at that path. It decides file by file, not folder by folder: .claude/skills/ can hold one skill from your team and another from a parent team, side by side.

1

Repo content

<org>/<team>/repos/<host>/<owner>/<repo>/content/

Who sees it: the team itself (child teams don't inherit repo content), and only when an agent launches in that repo. It lives in the context repo, so it is pushed like team content. Use it for "the kit for this codebase": a lint skill or a CLAUDE.md that only makes sense in one repo. It wins over every other place for a launch in that repo, and doesn't exist anywhere else.

2

Private

~/.codesense/users/<you>/scratch/orgs/<org>/

Who sees it: only you, only in this org. A local-only git repo CodeSense initializes for history; never pushed, never shared. A private file wins over the team's at the same path, for you only, with two exceptions: you can switch off "Use my private items in ‹Team›" for a team, and a single private file can be set to "Use team's". Its sibling scratch/all-orgs/ comes right after it and carries inert items (skills, prompts, snippets, templates) into every org you open. See Private & All-orgs.

3

Team content

<org>/<team>/content/

Who sees it: the team and every child team. It lives in the context repo's own git tree and is pushed and pulled with the org's remote. The shared-truth layer: specs, stories, team decisions, the skills you want everyone to carry.

4

Parent teams

<org>/<parent>/content/, then its parent, and so on

Who sees it: every team below them in the chain, for the files the parent shares in config/sharing.yml (for example share: ['content/**']; see Teams). With no file, a parent shares nothing. A child team inherits each shared file it doesn't hold itself; the nearest parent wins when two of them hold the same path. In the left nav, inherited files carry a quiet marker.

What a launch copies

The stack says where a file comes from. The agent decides which files: its context list in agent.yaml names folders and files, and an agent without one gets its runtime's default (for Claude, CLAUDE.md plus .claude/commands, hooks, agents and skills; for Codex, AGENTS.md and .agents/skills). An agent launched in a team workspace (a team's own workspace, not a code repo) defaults to .claude/commands and .claude/skills instead; its files are staged into a separate worker folder that isn't a git repo, so no git exclude is written. A per-repo override, saved with the agent, can add or remove paths for one repo.

  1. Prepare once. At launch CodeSense resolves that list through the stack, compares the result with what the worktree already has, and copies what is missing, plus newer versions of files it copied earlier, in one batch. It never overwrites a file the repo tracks or a copy you edited; those are kept and listed in the launch report. The copied paths go into the clone's .git/info/exclude (shared by all worktrees of that clone), so they never show up in git status.
  2. Then nothing moves on its own. Editing team content doesn't touch a running worktree, and editing a file in a worktree doesn't touch the team. No background sync, no folder that "belongs" to a team.
  3. Agents ask explicitly. hydrate_worktree and hydrate_story bring more context in; reverse_sync_worktree (after preview_reverse_sync_worktree) and route_file_to_context send an edit back. Wrap them in your own sync skill if you want a routine.

Who sees what

The same four places against the audiences, and whether a file there is pushed with the context repo.

Place You Team Child teams Pushed to remote?
1 · Repo content ✓ in that repo ✓ in that repo — ✓ via org remote
2 · Private (and all-orgs) ✓ — — —
3 · Team content ✓ ✓ ✓ inherited if shared ✓ via org remote
4 · Parent teams ✓ ✓ inherited if shared ✓ inherited if shared ✓ via org remote

Editing an inherited file

An inherited file is still the parent team's file. Open it from a child team and the viewer says so: "This file comes from ‹Parent›. Changes you make here update it for ‹Parent› and every team that inherits from it." While you edit, the toolbar reads From ‹Parent› — edits save to ‹Parent›. Deleting, renaming or moving an inherited file asks you to confirm first, because it happens in the parent team.

To change it for your team only, choose Copy into ‹team› on the file. That writes a copy into your team's own content. Your copy is now the closest one, so it wins for your team and its children; the parent and its other children keep the original.

Picking a place when you save something

  • Will this ship with the team? → Team content. It is pushed with the org remote and teammates get it on their next pull.
  • Should several teams share it? → the parent team they all inherit from.
  • Is this only useful in one source repo? → Repo content under that (host, owner, repo).
  • Is this a personal experiment or shortcut, scoped to one org? → Private. Never pushed.
  • Is this an inert skill / prompt / snippet / template you want in every org? → All-orgs. Refuses non-inert kinds on save.

Wherever it lives, a file reaches an agent only when that agent's context asks for its path. If you're not sure where it goes, start at Private and share it later with Share with ‹Team›…: see Promoting a private file to the team.
