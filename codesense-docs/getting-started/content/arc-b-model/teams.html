Arc B · Teams

One parent, many children, resolved nearest-first.

Teams in CodeSense form a tree, not a web. A team can declare one parent_team, and its context becomes its own content plus the files its parents choose to share (their config/sharing.yml). Inheritance is decided per file. Folders are shared and merged, never owned by one team; for each file the closest team wins, so your team's file beats a parent's at the same path. Chain depth caps at 64.

Nest teams with set_team_parent

Use set_team_parent to set or clear a team's parent. A child receives only ancestor content/ and panes/ paths declared in config/sharing.yml; each middle team must share them onward. Agent and routine configuration under config/ does not inherit. The nearest shared copy wins.

What teams.yml declares

One teams.yml at the org root lists every team. It's a plain array; each entry declares a name, a slug for the directory at the org root, a display_name, and the remote key. parent_team is the one load-bearing optional field: set it, and the team inherits from that team's chain. Agents can set it too, with set_team_parent. 

teams:
  - name: default
    slug: default
    display_name: Default
    remote: origin
    parent_team: platform
  - name: platform
    slug: platform
    display_name: Platform
    remote: origin
    parent_team: root
  - name: root
    slug: root
    display_name: Root
    remote: origin

landing_page is optional: the team's home page, relative to its content/ folder. Without it CodeSense uses README.md, README.html or index.html from that folder, and nothing if none exists. The page opens whenever the team has nothing open: when you enter the team with no tabs, and when you close its last tab. If the tab you close is the home page itself, the team stays empty until you next enter it. Tabs you left open always come back instead. A page that resolves outside the team's content (an absolute path, .., or a symlink leading out) or names a hidden file or folder (.env, .claude/…) is never opened.

You don't edit teams.yml for this. Right-click one of the team's own files, in the left nav or on its tab, and choose Set as team starter page; the page shows a small house in the nav. On that page, Clear starter page goes back to the default (README.md, README.html or index.html). Files a parent team shares, hidden files and the read-only CodeSense Docs can't be set. The file must exist when you set it; if it is later moved or deleted, the team opens its default page instead, and Settings → Workspace says so. Settings → Workspace also shows each team's starter page with Change and Clear, and agents use the set_team_starter_page MCP tool. The change is a local edit of the context repo until you, or an agent, commit and push it.

How a file resolves along the chain

  1. Build the chain. From the team, append each parent_team until you hit null or the depth cap (64). For default above the chain is [default, platform, root].
  2. Resolve each file, closest first. For every file path, the team's own content is checked first, then each parent in order. The first team that has the file, and shares it down to you, supplies it.
  3. Merge folders, never own them. If default has .claude/skills/review/SKILL.md and platform has .claude/skills/deploy/SKILL.md, default sees both in one .claude/skills/ folder. If both have review/SKILL.md, default's copy wins. You override a file by placing one closer to home.
  4. No cycles. The validator rejects a parent_team that would form a loop. Rename-safe: renaming a team re-points every child's parent_team in one write.

When an agent launches, the chain sits under two closer places, the repo's own content and your private space: the full order is on content layers. What the agent actually gets is the part of that merged view its context asks for, copied once at launch.

Inherited files in the left nav

Open default and the left nav shows its own files and its parents' in the same folders. An inherited file carries a quiet marker naming the team it comes from, and while you edit it the toolbar reads From platform — edits save to platform.

  • Editing it edits the parent's file. Opening it shows: "This file comes from platform. Changes you make here update it for platform and every team that inherits from it." The save goes to platform's folder. Deleting, renaming or moving an inherited file asks you to confirm first (for example "Move in platform?"), because it happens in platform for every team that inherits it.
  • Copy into default (the file's menu offers "Copy into ‹team›" for the team you're in) makes your team's own copy. It is now the closest one, so it wins for default and its children, while platform keeps the original. Delete that copy later and platform's version shows again.
  • Folders are shared, files are inherited. A folder shows up once, with every file from every team in the chain merged into it. New files and files you drop into it land in your team. Inherited files can't be dragged, and renaming or deleting a folder only touches your team's files in it.

When to set a parent

  • Shared skills across several products. Put the skills on platform, make each product team's parent_team: platform.
  • A pilot team that borrows the mainline's agents. Set parent_team to the main team; only the overrides live on the pilot team's own layer.
  • Don't nest without reason. One flat team is fine for a solo dev. The chain is a tool for people who need the same skill in two places.

How to do this via MCP

An agent reads every team's parent from describe_setup and follows the links to produce the chain: 

// describe_setup {} → { data: { orgs: [{ slug, teams: [{ name, parent? }] }] } }
const org = setup.data.orgs[0]
const chain = (name) => {
  const seen = []
  let cur = name
  while (cur) {
    if (seen.includes(cur)) throw new Error('cycle')
    seen.push(cur)
    cur = org.teams.find(t => t.name === cur)?.parent
  }
  return seen
}
chain('default') // → ['default', 'platform', 'root']
