Arc B · Source repos

Code lives in source repos. Context binds them to a team.

A context repo tells CodeSense what to work on; a source repo is the code it works on. Each team lists the source repos it works in, and can keep repo content for each one: files that an agent's launch picks up only in that repo, ahead of everything else. One team can hold many source repos; one source repo can be bound in several teams, each with its own repo content keyed by (team, host, owner, repo).

Where they live on disk

A team's list of source repos is in the org's teams.yml, so it's shared with the team. Where each repo lives on your machine is yours alone: you bind a team's repo to a local clone, a git checkout you made with your own git. CodeSense never clones for you, and never commits, pushes or merges in it.

Story worktrees go beside the clone, at ../<repo>-wt/<slug>, on the branch the story's frontmatter names (branch, else the older branch_name or dev_branch), or feat/ plus the story file's name (without .md) when it names none. The first open of a story's workspace creates its worktree; later opens reattach it. Arc C covers worktrees in depth. A clone CodeSense made for you in an earlier version lives under ~/.codesense/users/<id>/sources/ and keeps working.

Add a repo, then attach it

There are two moves here: add puts a repo on the team's list; attach binds it to your local clone, so worktrees, terminals and editor actions find its code. Open the Source repos tab from Go → Source Repos (⌘⌥R).

1

Add the source repo

Under Add a source repo, choose Local folder and Choose folder… to pick a clone you already have, then Attach folder: the repo is added and the clone bound in one step. Or choose From a URL, paste the repository URL or owner/repo, and press Add repo to track it on the team. A folder is tracked as the repo its upstream remote names, else its origin.

2

Attach your clone

A repo added by URL shows as Not attached — no working copy yet under Tracked repos. Clone it with git, then press Attach local clone on its row and choose Browse for clone directory. The repo's own content folder is <team>/repos/<host>/<owner>/<repo>/content/ in the context repo, for example billing/repos/github.com/ledgerline/api/content/.

3

Confirm the repo content resolves

Drop a tiny file in <team>/repos/<host>/<owner>/<repo>/content/.claude/skills/hello/SKILL.md, then preview an agent whose context includes .claude/skills with agent_preview and that repo. The skill is listed from the repo tier. Launch the agent in a worktree of that repo and the file is copied in with the rest of its context. A launch in any other repo never sees it.

Why repo content, not just team content?

  • Repo content is the "kit for this codebase." Repo-specific lint skills, a CLAUDE.md tuned to one codebase, notes that only make sense with that repo open. It wins over your private space and the whole team chain, but only for launches in that repo.
  • Team content is the shared-truth layer. Specs, stories, team decisions, skills every repo should get. Both live in the context repo and are pushed and pulled with it.
  • Neither moves on its own. A launch copies what the agent's context asks for, once. To pick up a later edit, an agent calls hydrate_worktree; to send a worktree edit back, it calls reverse_sync_worktree. A per-repo override on the agent can add or remove paths for this repo only.
How to do this via MCP

An agent walks the same shape with four tools:

  • list_source_repos: the team's repos, the legal source_repo values, and each repo's clone (attached, missing or unattached, with localPath).
  • add_source_repo: add a repo to a team by url, or by path to bind an existing clone at the same time.
  • attach_source_repo_path: bind (or rebind) a local clone to a repo the team already tracks.
  • remove_source_repo: stop tracking a repo. The clone stays on disk.

Live schemas are in mcp-explorer.
