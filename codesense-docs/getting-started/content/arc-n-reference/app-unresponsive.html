When CodeSense stops responding

Use the error text to distinguish a stalled runtime from a call that reached its time limit.

Architecture: the runtime is unresponsive

When the independent heartbeat observer reports a runtime stall, an MCP call can return this exact error:

CodeSense UI/runtime unresponsive (runtime heartbeat stalled); wait, then retry; restart the app if it persists. Outcome may be unknown; inspect state before repeating mutations
  1. Wait briefly, then retry a read-only call such as list_sessions.
  2. Before repeating an action that writes or sends something, inspect whether it already completed. Accepted work can continue after an error is returned.
  3. If calls keep failing or the app stays unresponsive, restart CodeSense.

A fully frozen runtime cannot reply to MCP; check for the self-capture file instead.

Example: probe before repeating an action

After a runtime-stalled error or the relay's outcome-unknown error, wait, then make this read-only MCP tool call:

{
  "name": "codesense_call_tool",
  "arguments": {
    "name": "list_sessions",
    "arguments": {}
  }
}

When the probe succeeds, inspect the session state before repeating an earlier write or message.

The absolute backstop

Every MCP call has a default 15-minute (900-second) absolute backstop, including healthy long calls. There are no per-tool exemptions. At the default setting, its distinct error is:

MCP tool call exceeded the absolute backstop of 900 s. Outcome may be unknown; inspect state before retrying

This error reports elapsed time; it does not establish a runtime stall. Inspect the operation's state before retrying it.

Set CODESENSE_MCP_TOOL_TIMEOUT_SECS in the environment that launches CodeSense to configure the backstop in positive whole seconds. For example, CODESENSE_MCP_TOOL_TIMEOUT_SECS=1800 allows 30 minutes. Invalid or zero values use the default 900 seconds; positive overrides are uncapped. The error shows the configured number of seconds.

Sessions keep their MCP transport

A stalled request receives an error for that request while the session's MCP transport stays open:

CodeSense did not answer in time; outcome unknown; inspect state before repeating writes

If the relay loses its downstream connection to CodeSense, it reconnects with bounded backoff. It never repeats a pending tool call automatically. Wait, retry a read-only probe, and inspect state before repeating a write. For HTTP downstreams, an expired request retires the downstream connection; other outstanding calls also report an unknown outcome before reconnection. Authentication or policy failures still end the connection.

When the session server confirms a session is still live, a delayed expiry notification keeps its existing owner, team and captured workspace. An app restart also restores the captured workspace for that same live session. An ended session stays removed. If the server cannot report liveness, the session is released when it expires.

If a session still reports Transport closed, restart that session. Restarting the app alone does not reconnect a session whose client already closed its MCP transport.

Architecture: renderer recovery and self-capture

The renderer watchdog reloads a stalled webview. If its original renderer remains stuck, it terminates only a renderer verified to belong to this app, then reloads again and waits for a heartbeat within a bounded recovery window. If the UI stays stuck, restart the app.

Separately, an OS thread watches runtime and logger heartbeats. After either stops for 30 seconds, it writes a marker directly to the app log and takes a five-second macOS sample of the app's own process.

The capture is written to the app's logs directory. For the standard macOS install:

~/Library/Logs/ai.codesense/runtime-stall.sample.txt

Each sample is capped at 4 MiB. There is at most one capture per incident; capture re-arms after both heartbeats recover. A later capture replaces the same file, so copy it if you need to retain evidence of an earlier incident. Isolated installs use their own app logs directory.
