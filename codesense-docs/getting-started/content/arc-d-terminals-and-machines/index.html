Local or remote, same CodeSense

You can work on your Mac, on a beefier Linux box, or both at once. CodeSense treats them the same: open a terminal tab, launch an agent, hydrate a worktree, run a routine — the shortcuts, the inbox, the dashboards don't care whether the shell is on this Mac or a remote host over SSH. This arc teaches you the one mental model that spans both, and names the handful of places where parity breaks on purpose.

One tab shape

A CodeSense terminal tab is a workspace-scoped shell. On your Mac it's a native PTY. On a remote host it's a PTY on that host, framed over SSH by the CodeSense terminal server. From the UI the tab looks the same, keys work the same, scrollback is captured the same way, and the agent CLI (claude, codex) launches the same way.

The MCP tools follow the same shape: open_terminal_tab for local, open_remote_tab for remote; both take the same workspace handle and launch argument.

Where parity breaks on purpose

Three things are not identical, and the docs are honest about it:

  • The app itself runs on the Mac you run CodeSense on, which owns your profile directory. Only one, and it has to be local. Everything else — tabs, agents, worktrees — is reproducible on either side.
  • Native OS APIs (keychain, Finder reveal, system notifications) use the local Mac. On the remote the equivalent is the terminal server plus plain shell.
  • File watching is instant on your Mac (fsevents); remote uses a 5–10 s poll by default, tightenable with git fsmonitor.

Every other workflow is parity. The parity matrix enumerates them row by row.
