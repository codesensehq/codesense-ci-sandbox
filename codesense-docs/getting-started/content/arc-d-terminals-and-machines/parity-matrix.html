Local ⇄ Remote — the whole truth, one page

The one page where we tell the whole truth about what works, what has a caveat, and what doesn't yet. Every workflow in CodeSense is listed; both machine sides get a cell; the rightmost column names the caveat or gap and the workaround if we have one. If a cell changes, this page is where it changes first.

✓ parity ⚠ caveat ✕ gap Caveats are documented differences you can live with; gaps are things CodeSense doesn't yet do remotely at all.

The matrix

Workflow Local Remote Notes
Open terminal ✓ ✓ open_terminal_tab for local, open_remote_tab for remote. Same args, same handle shape, same scrollback contract. First remote open per account spins up the terminal server if it isn't there yet.
Run an agent CLI (claude, codex) ✓ ⚠ Launch is identical (launch: 'claude'). Caveat: each person signs in to the agent CLI on each machine; CodeSense never copies agent sign-ins across machines. On the remote, the first --dangerously-skip-permissions may show the agent's one-time confirmation (answer it via run_in_terminal_tab).
Run OpenCode (opencode) ✓ ✕ OpenCode runs on your Mac only, typed or launched as builtin/opencode. Remote tabs and remote agent launches run a shell, Claude Code or Codex. Workaround: run OpenCode on this Mac.
Launch a saved agent (foreground / background) ✓ ⚠ launch: { agentKey } works on either side. Caveat: remote launches require preparedWorkspaceHandle from a verified hydration (not just a path), and the account's runtime + sign-in must be present. The terminal server pins its identity; permissionMode: 'bypass' needs an up-to-date server.
Hydrate a worktree ✓ ✓ Hydration runs on whichever machine the workspace targets, and only when an agent launches or asks. The first remote open performs the git clone/fetch on the remote; later opens reuse that worktree. Same frontmatter; same depends_on; same handle contract.
Open workspace ✓ ✓ open_workspace picks the machine when the workspace is remote; the resulting workspace handle addresses tabs and files the same way local workspaces do.
Run a routine ✓ ⚠ Routines execute in whichever account owns the triggering workspace. Caveat: cron-style schedules depend on the owner being online — your Mac for local-owned routines, the remote account's terminal server for remote-owned ones. If you want "always on", own the routine on the always-on machine.
Serve a dashboard (HTML viewer) ✓ ✓ The viewer renders in the CodeSense window on your Mac regardless of where the context lives. For a remote-owned context repo, dashboard HTML is streamed through the terminal-server bridge; the viewer's http://localhost:{port} origin and window.codesense.* contract are unchanged.
Write to context (edit a file) ✓ ⚠ Editor saves (⌘S) are immediate on both sides. Caveat: optimistic-lock conflicts are reported loudly, and remote source refresh runs on a 5–10 s poll by default (15–25 s for the changeset view). Enable git config core.fsmonitor true on the remote to tighten.
Push the context repo ✓ ✓ CodeSense never pushes. An agent you ask runs git where the context repo's clone is, with the credentials already on that machine, and reports with report_context_sync. A remote workspace sends its edits back with reverse_sync_worktree first.
Pull the context repo ✓ ✓ Same shape as push: an agent runs it. A conflict opens a card on the status button of the Mac that holds the clone, whichever side caused it.
inbox_idle wake ✓ ✓ The idle detector runs where the inbox lives. Remote inboxes wake their owning account's agents via the terminal server, so an agent you left running on the build box is prodded exactly the way a local one would be.
Routine schedule (cron-shaped triggers) ✓ ⚠ Scheduled triggers fire in the terminal server's wall clock on the owning side. Caveat: if the Mac is asleep for a local-scheduled routine, that fire is skipped (standard Mac behavior). Remote schedules on an always-on box don't skip. Workaround: own "must-fire" schedules on the always-on machine.
File watching (fsevents / fsmonitor) ✓ ⚠ Local uses native fsevents (instant). Remote uses a 5 s poll (<5K files) or 10 s poll (monorepo); tightenable by turning on git fsmonitor on the remote. Deliberate design — not a bug — but it's a caveat.
Keychain / passphrase storage ✓ ⚠ Your Mac's keychain holds the handles CodeSense uses to unlock keys. The remote account uses whatever credential store is native there (gnome-keyring / libsecret / none). Agent-CLI logins live separately per account.
Host-agent (process broker) ✓ ✕ By design. The host-agent runs exactly once, on the Mac you run CodeSense on. Remote machines use the terminal server for the equivalent brokering. No workaround needed because every workflow the host-agent fronts has a terminal-server equivalent — this gap is where parity is defined, not broken.
System notifications / Finder reveal ✓ ✕ macOS-only affordances. On the remote, "reveal in Finder" is replaced with "open path in a terminal tab" + the Open-With list on the viewer side. Not planned to backfill.
