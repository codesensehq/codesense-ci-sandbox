Arc D · Remote private account

Remote, as first-class as local

A remote machine in private-account mode gives you your own Unix login on the box: your files, your agent CLI logins, your terminal server identity. Teammates on the same host have theirs. CodeSense's parity promise is written against this mode — if a workflow works locally, it works here, with the handful of caveats called out in the parity matrix.

SSH posture

CodeSense talks to your remote machine over ordinary OpenSSH. The posture it takes is deliberately boring:

  • Your public key stays on the machine, your private key stays on your Mac. CodeSense never asks for a private key, a password, or an API token.
  • Host keys are pinned. The first time you test a machine, CodeSense returns the host-key fingerprint; you confirm it, and from then on CodeSense enforces the pin. A mismatched fingerprint on a later connection refuses with "pinned host key does not match."
  • Agent sign-in is first-class. If you already use an SSH agent (ssh-add), CodeSense uses it. If you prefer a key file, you point at it and CodeSense parks the passphrase in your macOS keychain via a one-way handle; the passphrase itself never lands in CodeSense state.
  • Jump hosts are supported — set jump_host on the declaration and SSH's ProxyJump handles the hop.

The CodeSense terminal server

A tiny server CodeSense installs on each remote machine (one per private account) is what makes remote feel like local. It:

  1. Owns the PTYs — each remote tab is a PTY under this server, not a child of your SSH session. If your laptop sleeps, the PTYs keep running.
  2. Streams scrollback — the same emulator contract as local, exposed over a framed protocol over SSH. One codec, one scrollback shape.
  3. Carries a pinned identity — the pinned_server_id on the machine declaration. If the server is replaced (someone wiped the box, or you reset the installation), CodeSense refuses until you re-verify.
  4. Upgrades under control — Machines → Replace terminal server prepares the new binary alongside the live one, then swaps. Older servers get a "terminalServerOutdated" refusal for new verbs so you know to upgrade.

Tabs survive relaunch

Because PTYs are owned by the terminal server (not by your SSH session), remote tabs stay alive across:

  • Your Mac sleeping or losing Wi-Fi.
  • Quitting and re-opening CodeSense.
  • Restarting the host-agent on your Mac.

On reconnect, CodeSense re-attaches, snaps the latest scrollback, and the agent you had running is still running — the remote-saved agent startup story. You see this as "my claude session was still there when I woke the Mac up." The one thing that doesn't survive is a deliberate close tab — closing a tab tears the PTY down.

A remote tab, start to finish

  1. You pick a workspace, open its workspace sheet, and the machine picker offers "this Mac" or any saved remotes.
  2. You pick the remote. CodeSense opens an SSH connection (or reuses the pooled one), asks the terminal server to spawn a PTY in your workspace's hydrated worktree on the remote.
  3. The tab opens. You type claude "fix the build" or just ls — the shell responds exactly as it would in a local tab.
  4. You walk away. The next morning you re-open CodeSense; the tab is still there, the agent is still waiting on your reply, and read_terminal_tab returns the scrollback that accumulated overnight.

Try this now

Open a shell tab on a saved remote machine. You'll need a machine saved already (walk the setup flow first) and an open workspace.

How to do this via MCP 
codesense.invoke('open_remote_tab', {
  requestId: crypto.randomUUID(),
  machineId: 'build-box-01-ab12cd',
  teamKey: 'ops',
  workspaceId: '<workspace>',
  hostCwd: '/home/sam/work/my-repo',
  launch: 'shell',       // or 'claude' / 'codex' / an agentKey
  headed: true,
})

For a saved agent, pass launch: {agentKey} and preparedWorkspaceHandle from a verified hydration.
