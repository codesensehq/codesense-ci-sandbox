When it goes sideways, start here

Remote work has more moving parts than local, so when things wobble it helps to know which part. CodeSense's refusal messages name the layer; this page is the index of what to do when you see each one.

1 · SSH can't connect

You see test_machine_connection fail at step 1 (connect).

  • Try plain SSH first. ssh -o BatchMode=yes <host> 'uname -sm' from your Mac's Terminal.app. If that fails, CodeSense will too — it's a key/host/port problem, not CodeSense.
  • Key not loaded. If you use an SSH agent, run ssh-add -L. If you use a key file, confirm the path on the machine binding (your personal half) matches the key's location.
  • Host alias missing. If you connect by alias, check ~/.ssh/config has an entry with HostName, User, and (if non-22) Port.
  • Jump host. Set jump_host on the machine declaration, or ProxyJump in your SSH config.

2 · "Pinned host key does not match"

CodeSense refuses the connection: the host key the server offered isn't the one you confirmed the first time.

  • Expected cause — the remote machine was reinstalled, re-imaged, or rolled its host keys. Confirm with the admin.
  • Unexpected cause — stop. Someone has rotated that machine's identity without telling you. Leave it blocked and tell your team.
  • Fix (expected case) — in Machines, Review key… shows the pinned key and the presented key. Once the admin confirms it was rebuilt, whoever manages it removes the machine and adds it again. Adding it shows the new fingerprint; check it against the rebuilt machine before you confirm.

3 · terminalServerOutdated

A newer verb (for example permissionMode: 'bypass') isn't understood by the terminal server on the remote. The server is older than this CodeSense release.

  • Fix — Machines → Update terminal server…. It ends every terminal and agent on that server. Tabs reopen as fresh shells, and Agents with resumeAfterRestart relaunch; other agents stay stopped. Save what you need first.
  • If the update won't start — likely a stale pinned_server_id. The declaration pins the server identity; if it was retired manually on the machine, re-run test_machine_connection to re-verify, then update again.

4 · "Permission denied" during setup

Common during /setup-machine or /add-machine-user.

  • Password-prompted sudo. CodeSense never handles passwords. If sudo needs one and you can't make it passwordless, open your own Terminal.app, run the exact command the skill printed, then resume.
  • authorized_keys permissions. The skill sets 700 on ~/.ssh and 600 on authorized_keys. If the key was added by hand with the wrong modes, SSH silently refuses the login. Fix: re-run the skill (it's idempotent) or set the modes yourself.
  • SELinux / AppArmor. On some hardened Linuxes sshd wants restorecon ~/.ssh ~/.ssh/authorized_keys after you create the directory under sudo. The skill names this in the summary when it detects such a system.

5 · Agent CLI isn't signed in on the remote

You launch claude or codex on the remote and it immediately asks you to sign in — even though you're signed in locally.

  • By design. Each person signs in to each agent CLI on each machine. CodeSense never copies agent sign-ins across machines.
  • What to do. Open a shell tab on the remote and run the CLI's sign-in flow (claude /login, Codex's codex login). The sign-in persists in the account on the remote the same way it persists on your Mac.

6 · A remote tab didn't come back

You wake your Mac; most remote tabs are back, one is missing.

  • First suspect — the terminal server was updated or restarted. Either ends every terminal on that server and reopens the open tabs as fresh shells. A tab that couldn't reopen after an update is listed in the update's inbox report.
  • Second suspect — the remote machine rebooted. Confirm with uptime. If so, the PTYs are gone; re-open the tabs.
  • Third suspect — scrollback exceeded limits. The tab still exists; the scrollback is just large. Give it a moment to re-render, or re-attach from the hidden-tabs list.

7 · Scheduled routine didn't fire

  • Routine armed on this Mac, Mac was asleep. Fires missed while the Mac was asleep or the app was closed are recorded as one skipped run; with policy.missed: run_once, one of them also runs as a catch-up. Arm it on an always-on machine with routine_arm_on if the schedule must fire (schedule triggers only, one_mac, no budget_usd).
  • Routine armed on a machine, terminal server was down. Check the machine's status line in Machines, or call terminal_server_status or list_machines. If it bounced during your window, the missed fires follow the same policy.missed rule: one skipped run, plus one catch-up run with run_once.
  • Routine disabled. Open Schedule from the identity menu and pick the routine. A failed run can disable itself; turn it back on there (or call routine_set_enabled) after you've fixed the cause.

8 · The app on this Mac is wedged

  • Symptom — local tabs don't accept input; file watchers stop reporting.
  • Fix — quit CodeSense and relaunch it. If that doesn't help, choose Restart terminal server (or call restart_terminal_server). That ends every terminal and agent running on it, so save what you need first.
  • Remote tabs are unaffected. They live under the remote terminal server; a wedged local app doesn't touch them.

9 · Private-account enrollment stuck

First connection to a remote machine stops at "verifying private account" and doesn't complete.

  • Likely cause — the account's canonical home isn't an absolute path, or uid conflicts with another known enrollment. CodeSense refuses the binding with invalid private account binding.
  • Fix — remove the stale enrollment file (~/.codesense/users/<p>/machines-private-v1.d/<id>.yaml), then re-run test_machine_connection. CodeSense re-enrolls with a fresh id.
