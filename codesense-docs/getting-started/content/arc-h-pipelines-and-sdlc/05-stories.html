What this phase is for

A good story graph is the difference between an epic that ships in a week and one that drags for a month. John runs bmad-create-epics-and-stories to slice the design into shippable units and wire their depends_on lists. That skill comes from BMAD, installed in your own repo; CodeSense doesn't ship it.

A story is a Markdown file with type: story (or bug, spike) in its frontmatter, or an HTML page with <meta name="cs:type" content="story">. The fields CodeSense acts on are story_id, status, source_repo (one of the team's configured repos), depends_on (a list of bare story ids) and supporting_docs. Any other key, such as sprint or parent_epic, is kept as metadata you can query with query_context. The summary is the first ## Purpose or ## Story section. Read the shipped DEMO stories for the shape.

Before handing a story on, have the agent call validate_story. It returns findings such as MISSING_SOURCE_REPO, UNPARSEABLE_FRONTMATTER or DUPLICATE_STORY_ID. The same findings show in the metadata band when you open a story, and in the New story form as you type.

Local vs remote

Local

John writes the stories under <team>/content/<epic>/ in your context repo. A folder is an epic when it has a README.md (or index.md, README.html, index.html). The story-board.html dashboard reflects them live via subscribeContext.

Remote (private-account)

Same file layout on the remote repo. The remote's dashboard reflects remote state; your local story-board shows local state. The remote agent publishes new stories with reverse_sync_worktree; that call is the only bridge.

Try this now

Slice an epic you've been meaning to write. The skill asks for the spec + architecture docs and produces a stories folder.

How to do this via MCP 
codesense.invoke('runSkill', { skill: 'bmad-create-epics-and-stories' })
// Then check each story the skill wrote.
validate_story { path: 'content/<epic>/<story>.md' }
