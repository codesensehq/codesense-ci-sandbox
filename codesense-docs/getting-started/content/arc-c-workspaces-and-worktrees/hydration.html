Arc C · Hydration

Only the docs this story needs, when an agent asks

Creating a worktree copies no context, and an agent's launch copies only what its context asks for. A story's docs arrive when an agent calls hydrate_story: it copies the story's epic folder from team content into the worktree, and an optional policy widens that to referenced epics, parent epics or the surrounding epic, up to a cap. One comparison, one batched copy, and nothing moves afterward until an agent asks again.

What hydration is

Your context repo holds everything: epics, stories, architecture docs, retros, team references, agent configs. Most of that is irrelevant to a single story, and none of it reaches a worktree by itself. Hydrating is an explicit copy from team content into a workspace that an agent asks for:

  • hydrate_story copies a story's epic (or the wider closure its policy names). This page is about it.
  • hydrate_worktree copies exact paths or whole sets (folders such as .claude/skills or docs). With neither, it copies the runtime default set: CLAUDE.md, .claude/{commands,hooks,agents,skills}, AGENTS.md and .agents/skills.

Either way, each file lands at its path inside its content tier, so default/content/sample-epic/DEMO-1.md becomes sample-epic/DEMO-1.md in the worktree. The copies are added to the clone's .git/info/exclude (shared by all its worktrees), so they never show up in git status.

The policy

Without a policy, hydrate_story copies the story's own epic folder (the folder the story file sits in) and every file under it. A policy turns on up to three wider axes, bounded by a cap. When you pass one, give all four fields.

Axis · referenceDepth

References

Follow the story's supporting_docs frontmatter this many hops, and copy the epic folder of each story reached. 0 is off. Cycles are walked once.

Axis · ancestryLevels

Parent epics

Add the parent folders of the story's epic, this many levels up, never past the team's content/ root. 0 is off.

Axis · siblingBreadth

The surrounding epic

true adds the whole folder around the story's epic, so sibling epics come along. false is off.

Cap · maxMembers

Epic-folder ceiling

The most epic folders one closure may hold (the default policy uses 64). When the walk hits it, it stops there rather than grow without bound. 

// the default: just the story's epic folder
{ "referenceDepth": 0, "ancestryLevels": 0, "siblingBreadth": false, "maxMembers": 64 }

// the story's epic plus every epic its supporting_docs point at, one hop out
{ "referenceDepth": 1, "ancestryLevels": 0, "siblingBreadth": false, "maxMembers": 10 }

How CodeSense decides what to copy

1

Find the story

CodeSense looks the storyId up in the team's story index and takes the folder the story file sits in as its epic. That folder is always copied.

2

Walk the policy

References first (following supporting_docs up to referenceDepth hops), then parent epics (ancestryLevels), then the surrounding epic (siblingBreadth). An epic folder reached twice is copied once. The walk stops at maxMembers.

3

Compare, then copy once

CodeSense compares every file in those folders with what the worktree holds and copies the new and changed ones in one batch. It never overwrites a file the repo tracks or a copy someone edited in the worktree: those are reported as kept. The epics it hydrated are recorded, so list_hydrated can show them later.

After the copy

When team content changes (say the architecture doc gets amended), the worktree keeps its old copy until an agent calls hydrate_story or hydrate_worktree again. Nothing re-hydrates on its own. A repeat call is cheap: unchanged files are left alone, new ones land, and a file you edited is kept. A copy the team deleted is removed only by a hydrate_worktree call that passes prune: true, and only under that call's paths.

Agents can edit the hydrated docs in the worktree. The edit stays there until the agent previews it with preview_reverse_sync_worktree and publishes it with reverse_sync_worktree, which writes it back to the team file it came from.

A routine that needs fresh docs says so in its prompt: its agent calls hydrate_story as its first step. To make that a habit, wrap the calls in your own sync skill.

How to do this via MCP

Agent-side equivalent

The target names the workspace: {kind:"local", codeRepoPath, sessionId} on this Mac, or {kind:"remote", machineId, workspaceHandle} on a machine (the handle from prepare_remote_workspace). 

// Hydrate a story's epic, plus the epics it references (one hop).
codesense.invoke('hydrate_story', {
  target: { kind: 'local', codeRepoPath: process.cwd(), sessionId: process.env.CODESENSE_TAB_SESSION_ID },
  storyId: 'DEMO-1',
  policy: { referenceDepth: 1, ancestryLevels: 0, siblingBreadth: false, maxMembers: 10 },
})
// → { operationId, status: 'ready',            // or 'failed' / 'cancelled'
//     wanted: 4, written: 4, unchanged: 0,
//     keptModified: [], skippedTracked: [], failed: [], …,
//     writtenPaths: ['sample-epic/DEMO-1.md', …], note: '…',
//     story: { storyId: 'DEMO-1', epicDir: '…/sample-epic', filesScoped: 4, outsideTeamContent: 0 } }

// Which epics this workspace has hydrated so far
codesense.invoke('list_hydrated', { target })

See hydrate_story, hydrate_worktree and list_hydrated for the live schemas.
