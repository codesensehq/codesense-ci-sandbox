When a workspace is being difficult

Worktree creation is deterministic, but it reaches across your filesystem, your git clone, and the worktree.yaml setup. When something refuses to open or hangs on step 4, the message almost always names the layer. This is the index of what each symptom means and the smallest thing you can try first.

Where to look first

  1. The progress line while the worktree is created. On this Mac it reads Setting up worktree…; on a remote machine it names the step (Fetching <repo>…, Copying <repo> to <machine>…, Creating the worktree on <machine>…) and, when it stops, says which step and why.
  2. list_worktrees. Returns every managed worktree with its status, last-check-in, and the resolved disk path. If the row isn't there, CodeSense doesn't think the worktree exists; if it is, the status tells you why it isn't ready.
  3. read_worktree_config. Prints the resolved worktree.yaml the setup step will run — handy when a surprise setup: line is tripping things.
  4. The terminal tab bound to the worktree. If the agent is stuck inside pnpm install, the terminal tab tells you more than any dashboard.

Common issues

Problem 1

The worktree starts from an old commit, or a remote fetch is stuck

On this Mac CodeSense adds the worktree from local refs and never fetches, so a new story branch starts from whatever your clone last fetched. A remote machine gets its copy from that clone, so it needs the same fetch (see git is yours).

  • Expected cause — on this Mac, nobody has fetched lately. Fetch with your agent or in a terminal (git fetch origin) before you open the story. If the story's branch exists only on origin and was never fetched, CodeSense starts a new local branch from the start point instead; to recover, remove that worktree and its new local branch, fetch, then open the story again.
  • Expected cause — on a remote machine, the copy never arrived. The progress line names the step that stopped, usually the connection or the machine's free disk.
Fix — fetch first, or fix the connection or disk the progress line names, then open the story again. Creation starts over from the first step.
Problem 2

"fatal: '<path>' is already checked out"

Step 2 (git worktree add) refused because the branch is already checked out somewhere else — usually a stale CodeSense worktree from a previous attempt or a manual git worktree add you ran at the command line.

Fix — run git worktree remove <path> in a terminal tab against the source-repo clone (or git worktree prune if the path is already gone), then open the story again.
Problem 3

Hydration landed, but the agent says "no docs"

The agent called hydrate_story, yet the story's docs aren't in the worktree and list_hydrated shows no epic for it.

  • Expected cause — the call failed: the story id isn't in the team's story index, or its epic folder has no files. The result's status is failed and says why.
  • Expected cause — the files were there already and someone edited them in the worktree, or the repo tracks them. Those are reported under keptModified and skippedTracked and are never overwritten.
Fix — read the result of the hydrate_story call, fix the story id or the story's location in the context repo, then call it again on the same target. A repeat call only copies what changed, so there's no need to recreate the worktree. To replace edited copies with the team's version, call hydrate_worktree with overwriteModified: true for those paths.
Problem 4

The worktree's setup failed

One of the setup: lines in worktree.yaml exited non-zero. The error names the step that stopped.

  • Expected cause — a missing tool (pnpm isn't on PATH for the setup shell). The env.PATH in worktree.yaml may need the tool's install dir added.
  • Expected cause — timeout_seconds fired. The setup took longer than the ceiling and was killed.
Fix — reproduce the failure in the terminal tab bound to the worktree (same shell, same cwd), fix the worktree.yaml in the source repo, then open the story again so the setup runs once more.
Problem 5

Second open hangs with "busy"

open_workspace returns { status: 'busy' } and the tab waits. Something else is holding the worktree's write-lease — usually a Builder agent still mid-run on that story, sometimes a stuck hydrate_worktree from a terminated session.

  • Expected cause — a parallel agent on another Mac has the lease. Check the list_worktrees row's machine column.
  • Expected cause — a crashed previous session left the lease unreleased. The lease TTL (default 10 min) will expire; or you can kill it.
Fix — on the row, Release lease (if yours), or Kill lease-holder (confirmed) if an agent is wedged. The tab retries automatically once the lease clears.
Problem 6

Index entry lost its directory

list_worktrees shows a row whose path no longer exists on disk (you rm -rf'd it, or restored from a backup that excluded the <repo>-wt/ folder beside the clone).

Fix — open the story again: CodeSense re-runs git worktree add in place, from local refs. Context comes back at the next agent launch, or when an agent calls hydrate_story. Local uncommitted work in that worktree is gone (there isn't anything to recover — it's not on disk), but the branch and its pushed commits are untouched.
Problem 7

Rename refused — the new name collides

rename_workspace refused because another workspace already uses the target name, or the new slug would collide with a reserved form (_epic/*, _worker/*).

Fix — pick a name that isn't in use (the refusal message lists the clashing handle). Reserved prefixes are the ones with a leading _; see workspace kinds → how to tell them apart.

Diagnostic one-liners

# All worktrees CodeSense knows about on this Mac
list_worktrees {}

# Which epics have been hydrated into a given worktree
list_hydrated {
  target: { kind: 'local', codeRepoPath: '../sample-source-repo-wt/feat-DEMO-1-foundation', sessionId: '<your session id>' }
}

# The resolved worktree.yaml the setup step will run
read_worktree_config {
  repoPath: '~/code/sample-source-repo'
}

# Open a terminal tab in the worktree to run git by hand
open_terminal_tab { workspaceId: 'story:DEMO-1' }

Try this now

If something feels off, start here: list the worktrees CodeSense tracks on this Mac. The status column names the step; the machine column names the holder. Everything else on this page descends from one of those rows.

How to do this via MCP

Agent-side equivalent

An escalation routine (or a human operator) runs the same four tools against the same handle. The output is the full triage sheet for a workspace. 

// Full triage of a single workspace
list_worktrees {}
list_hydrated {
  target: { kind: 'local', codeRepoPath: '../sample-source-repo-wt/feat-DEMO-1-foundation', sessionId: '<your session id>' }
}
read_worktree_config {
  repoPath: '~/code/sample-source-repo'
}

See list_worktrees, list_hydrated, and read_worktree_config for the live schemas.
