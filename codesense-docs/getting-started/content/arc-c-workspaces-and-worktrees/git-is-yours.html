Arc C · Git is yours

CodeSense never commits, pushes or merges. Your agents do.

Every commit, every branch, every push in your source repo comes from a process you control — a Builder agent on your Mac, or your terminal, with your credentials. CodeSense runs git only to set up and read your worktrees: it fetches, adds and removes worktrees, reads status and history, and keeps the copies it makes out of git through the clone's .git/info/exclude. It never authors a commit, pushes, merges or rewrites history; that work is yours. This is deliberate, and it changes how you reason about who did what.

Why this is the right choice

Committing and pushing from inside an app would mean borrowing your signing keys and your branch protections, and taking the blame when something went sideways. CodeSense stays on the correct side of a bright line: for anything that changes history or leaves your machine, it asks an agent to do the work. The agent is a process you launched, in a terminal you own, with the identity you'd use at the command line. The git operation is indistinguishable from what you'd have run yourself.

Who does what

CodeSense does

  • Chooses the path on disk a worktree lives at (../<repo>-wt/<slug>/, beside the clone).
  • Resolves the branch name from the story's branch (or the older branch_name / dev_branch), else branch_prefix + the story file's name (feat/DEMO-1-foundation).
  • Copies context into the worktree when an agent launches or asks (file copies, not git history), and lists those paths in the clone's .git/info/exclude, which all worktrees of that clone share.
  • Remembers mappings — story to worktree path to branch — in its own index so a second open_workspace reattaches instead of recreating.
  • Writes worktree.yaml settings via write_worktree_config if you ask it to.

CodeSense does not

  • Author a commit. It runs git fetch, git worktree add and read-only commands like status, never git commit.
  • Hold git credentials. Your SSH keys, your PATs, your signing keys live where they always did.
  • Decide when to commit, push, or merge. That is always a deliberate agent action with your identity on it.
  • Rewrite history. No rebase, no amend, no force-push from CodeSense itself.
  • Touch the source repo without being invited. It only creates a worktree when a workspace is opened against a story.

Then who runs git worktree add?

CodeSense does, and it is the one place it runs git that changes anything on disk. The commands worktree creation needs (git fetch when the remote is reachable, then git worktree add) run on your Mac as you, with your shell, your credentials and your git config, through the host-agent CodeSense installs under your user account (on a remote machine, its terminal server). Setup commands from worktree.yaml run the same way. None of them commits or pushes. 

# What CodeSense invokes
codesense.invoke('open_workspace', { target: 'DEMO-1' })

# What then runs on your Mac, as you
git -C ~/code/sample-source-repo fetch origin
git -C ~/code/sample-source-repo \
    worktree add ../sample-source-repo-wt/feat-DEMO-1 feat/DEMO-1

The host-agent is documented in Arc D; sync is covered in Arc K, which walks the parts of the loop where an agent you ask pulls and pushes the context repo with git.

Your audit trail stays yours

Every commit in your source repo is authored by the identity whose agent made it: your git config (for interactive sessions in a terminal tab), or the agent's configured git.user block in its agent.yaml (for routine-driven builds). The CodeSense app never appears as an author anywhere in your history. If you want "Amelia built this" to literally mean Amelia, you set Amelia's git identity in agents/amelia/agent.yaml and the commits say so.

Signing keys

Signed-commit workflows (git commit -S) continue to work: CodeSense never fingers your signing key, and the agent that commits picks it up from the same gpg-agent or ssh-agent your terminal does.

What this means in practice

  • Branch protections apply. If your source repo requires PRs with reviews before merge, agent commits are no different — the push lands on a branch, the review happens as normal.
  • Local git hooks fire. Pre-commit, pre-push, and commit-msg hooks all run against the agent's shell session the way they would yours.
  • GitHub Actions attribute to the agent. Build artefacts and PR comments show the identity in agent.yaml, not a generic "CodeSense bot".
  • Repo kill switch. If you want an agent to stop touching a repo, revoke its git credentials or disable its routine. CodeSense holds no git credentials of its own to revoke.
  • Nothing to migrate on first install. Your existing clones are left alone. CodeSense creates worktrees beside the clone you point it at (../<repo>-wt/); your original working dir stays exactly where it was.

How to do this via MCP

Agent-side equivalent

CodeSense surfaces the result of git operations through its own tools so agents and dashboards don't shell out either. The underlying git is still yours — it ran under the host-agent — but the summary is a plain JSON response. 

// Agents inspect the fleet without touching git
codesense.invoke('list_worktrees', {})
// → [{ story_id, branch, path, machine, last_commit_sha, last_push_at }, ...]

// Open the real repo in a terminal tab if you want to run git by hand
codesense.invoke('open_terminal_tab', {
  target: 'DEMO-1',
  cwd: '$WORKTREE'
})

See list_worktrees and open_terminal_tab for the live schemas.
