Arc C · Worktree creation

How a worktree appears

You choose Open CLI on a story, or an agent calls open_workspace. If the worktree already exists, you land in it immediately. If it doesn't, CodeSense creates one: it resolves the branch (fetching from the remote when it can), lays the directory, links it to the story, and runs the worktree.yaml setup. Four steps; how long depends on the repo and its setup. Creating a worktree copies no context into it: context arrives when an agent launches there (its context) or when an agent asks for more with hydrate_story or hydrate_worktree.

This is the shape; the live workspaces/worktree-create.excalidraw canvas has the editable version — click the diagram to open it.

What you see in the UI

The workspace shows Setting up worktree… until the worktree is ready, with a line that names each step as it runs (Fetching <repo>, Creating worktree, Running setup) and a checklist of the setup commands. On a remote machine the repo is copied there first:

Fetch Fetching <repo> with an object count when known
Pack & copy Copying <repo> to <machine> after "Bundling <repo> for <machine>"
Check Verifying the copy on <machine> the copy is verified
Create Creating worktree on <machine> then the setup runs

If a step fails, its details say where it stopped (Stopped while) and why (Reason), and Retry creates the worktree again. If a setup command fails, the details name the step, its exit code and the command.

Step-by-step

1

Resolve the source repo and branch

CodeSense reads the story's frontmatter: its source_repo field (e.g. acme/api, a repo the team has configured) and its branch field. With no branch, the branch is the worktree.yaml's branch_prefix (default feat/) plus the story id. The worktree goes at worktree_dir (default ../{repo}-wt/{slug}, beside the clone), where the slug is the branch with / turned into -: 

source_repo:   acme/api
story_id:      DEMO-1
branch:        feat/DEMO-1
worktree path: ../api-wt/feat-DEMO-1/
2

Fetch and add the worktree

CodeSense fetches from origin when the remote is reachable (it falls back to local refs when it isn't), then runs git worktree add at the resolved path on the branch. A branch that doesn't exist yet starts from the branch of the story's first depends_on story, or else from default_start_point (default main).

3

Link the worktree to the story

CodeSense records which story owns the worktree, so a second open reattaches instead of creating another. Nothing is copied from the context repo in this step: there is no automatic sync. An agent launched here gets the files its definition's context (or its runtime's default) names, in one batched copy that never overwrites a file the repo tracks or a copy you edited. The copied paths go into the clone's .git/info/exclude (shared by all its worktrees) so they stay out of your commits. Story docs arrive when an agent calls hydrate_story.

See hydration for the explicit calls.

4

Run the worktree.yaml setup

Finally CodeSense runs each line of the setup: block from worktree.yaml (if any), with the env: block applied and the timeout_seconds ceiling in effect (600 seconds by default).

Exit 0 on every line → the worktree is ready, the index entry is written, and any waiting agent attaches. A non-zero exit stops setup and shows Setup failed with the step; the worktree stays, so you can fix the command and retry.

When the setup came from the team's shared context repo rather than from you, CodeSense first shows the commands: Run setup from your team for …? with Approve & run or Skip setup. It asks again whenever the commands change.

When this happens

  • First open from the UI. You choose Open CLI on the story's right-click menu (on a team with machines, it asks This Mac or a machine); the workspace shows Setting up worktree… until it's ready.
  • First open by an agent. open_workspace creates the worktree if it isn't linked yet. This path lets an orchestrator open a story cold with no prior human open.
  • Never on second open. The worktree index remembers the mapping. A follow-up open_workspace on the same story reattaches to the existing worktree in sub-second time.
  • Not for team or generic workspaces. This page covers story worktrees. Team workspaces reuse the context repo's own clone; generic workspaces are just folders. Epic workspaces are covered in workspace kinds.

How to do this via MCP

Agent-side equivalent

An agent calls open_workspace directly; the trusted-side spine runs the four steps and settles with a typed result. 

codesense.invoke('open_workspace', {
  storyId: 'DEMO-1'
})
// → { handle: 'DEMO-1', mode: 'headed', headed: true, reconciled: null }

// Peek at a worktree's config before letting it run setup commands
codesense.invoke('read_worktree_config', {
  source_repo: 'acme/api'
})

See open_workspace and read_worktree_config for the live schemas.
