Move a workspace to another machine

A workspace stays on the machine it was created on: every open, every launch and every terminal tab lands there. If the work belongs somewhere else (a bigger remote box, a Linux-only build, agents that should keep running while your laptop sleeps), an agent moves it with the move_workspace MCP tool. The branch moves with it; uncommitted work is discarded only when you say so.

When to use it

  • You started a story on This Mac and realised the build only works on your Linux dev box.
  • You want long-running agents to keep running on a remote machine while you close your laptop.
  • You're trialling a story on a small VM and want to promote it to a bigger one without losing branch state.

Preconditions

  • The target machine is connected (or "local" for This Mac).
  • The target machine's terminal server is up and remoteMcpControl is enabled.
  • The source worktree is clean, OR you pass discardUncommitted: true to explicitly discard local changes.

What's preserved

  • The committed branch and its base ref.
  • The workspace record — its id, the agents attached to it, its layout.

What's not preserved

  • Session history on the source machine (terminal tabs there go dead; the move does not try to replay them).
  • Uncommitted changes on the source worktree, unless you commit them first (the bundle path builds from committed objects only).
  • Any machine-local state outside the worktree.

How it runs — the three steps

  1. Prepare the target. On a remote target, this reuses the same bundle-fetch-upload-worktree-create path prepare_remote_workspace uses. On This Mac, it reuses the same local worktree-from-clone primitive an initial local-workspace open does.
  2. Swap the location pointer. Once the target holds a usable worktree, the workspace record's location.machineId flips to the target. From this point every refusal site in the UI and the backend agrees the workspace lives on the target.
  3. Clean up the source. The source worktree is removed via git worktree remove --force (local) or the terminal server's remove_worktree call (remote). A source that is already gone counts as clean; retries are safe.
Partial-failure behaviour. A crash before step 2 rolls the move back — the workspace stays on the source and any target-side state is accepted as orphan (future re-moves reconcile it). A crash after step 2 rolls forward — the boot reaper reads the durable MoveIntent file, finishes step 3, and emits a cleared event to drop the "moving" banner. There is no explicit cancel; a stuck move either resumes or rolls back on the next launch.

Invoke it

Ask your agent to move the workspace. It calls move_workspace with the story id and a machine id from list_machines (or "local" for This Mac): 

move_workspace({
  storyId: "DEMO-X",
  targetMachine: "aws-dev-box",
  discardUncommitted: false
})
→ { moved: true, from: null, to: "aws-dev-box", handle, cwd, cleanupPending?: false }

Non-goals

  • Multi-machine workspaces (one workspace holding worktrees on several machines).
  • Automatic re-home when a machine goes offline — explicit user action only.
  • Replaying session history on the target machine.
