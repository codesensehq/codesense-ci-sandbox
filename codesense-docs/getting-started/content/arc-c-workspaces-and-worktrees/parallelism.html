Five stories, five worktrees, five agents

A worktree per story is the whole point. When the sibling stories in an epic don't depend on each other, nothing stops you from building them at the same time — one worktree per story, one agent per worktree, five tabs across the top of the CodeSense window. The seeded per-agent-kill-switch epic is laid out exactly for this: DEMO-1 is the shared foundation, DEMO-2 through DEMO-5 fan out off it.

Why five tabs instead of one

You could serialize this epic: finish DEMO-1, then DEMO-2, then the rest. The agent would never trip on itself and every build would start from a known tree. But nothing says those four siblings have to wait for each other — their depends_on frontmatter already says they don't. Giving each one its own worktree means CodeSense can keep four Builder agents hot at the same time, one story each, with four isolated branches that merge in whatever order they finish.

What isolation gets you

Independent branches

feat/demo-2 and feat/demo-3 never see each other's uncommitted work. A failed build in one worktree can't poison another.

Independent dependencies

Each worktree runs its own pnpm install inside its own node_modules. One story can bump a dev dep without stalling the others — the merge handles the final version.

Independent terminals

A terminal tab is bound to a workspace. Five open workspaces mean five sets of tabs that remember what you were running (Arc D covers the mapping).

Independent inboxes

Each story thread lives in its own inbox lane. Decisions escalate against a single story without pulling in the others' context.

The ceilings

  • CPU and disk. Five parallel installs plus five test runs stress a laptop. The agent-dag dashboard will show the hot ones; back off by closing the busiest Builder's tab (close_terminal_tab).
  • Not-really-sibling stories. If depends_on contains more than DEMO-1, that story has to wait. The story graph (Arc I) draws the braid; validate_story flags a depends_on id that doesn't resolve.
  • Shared files that shouldn't be shared. If two parallel stories edit the same file, they'll conflict at merge. That's fine when the conflict is semantic; it's a smell when a sibling grabbed a file that belongs upstream in the foundation. Pull that change back into DEMO-1 and re-fan.
  • Review bandwidth. Five simultaneous PRs still want five reviews. Keep the Reviewer inbox tended or the merge queue backs up.

How to do this via MCP

Agent-side equivalent

An orchestrator fans out five open_workspace calls in parallel. Each one settles independently — opened or alreadyLive — and the Builder loop picks up every ready worktree the next time inbox_idle fires. 

// Fan out — one call per sibling, concurrent is fine
await Promise.all(['DEMO-2','DEMO-3','DEMO-4','DEMO-5']
  .map(id => codesense.invoke('open_workspace', { target: id })))

// Inspect the fleet
codesense.invoke('list_worktrees', {})
// → [{ story_id: 'DEMO-1', path: '../sample-source-repo-wt/feat-DEMO-1-foundation', status: 'ready', ... }, ...]
