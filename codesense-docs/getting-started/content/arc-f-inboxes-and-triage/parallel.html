N builders. One queue.

Here's the "massively parallel" claim made concrete. You've got a 50-story epic. You want five Claudes building five stories at once, each in its own worktree, each wired to its own role queue, scattered across however many Macs you have plugged in. CodeSense lets you shard a single builder dispatch by giving every story its own role name (builder-DEMO-1, builder-DEMO-2, …), binding one session per role, and letting inbox_idle wake whichever one has mail. No central scheduler, no shared mutable state, no polling.

Why it scales

One holder per role

exclusive: true gives each shard a dedicated inbox. Zero contention; no "which builder picked it up" ambiguity.

Queue persistence

A builder session dies — the queue is intact. The next register_role resumes with acceptedUnacked in hand.

Machine-agnostic

A role lives in the team workspace, not on a machine. Launch the holding session on any Mac — open_workspace {machine_id}.

Reactive, not polled

A wake routine on inbox_idle wakes its agent's session that has the mail. Idle shards cost nothing.

Sharding the builder role

  1. Pick a shard key. Story ID is the easiest and makes dashboards legible: builder-DEMO-1, builder-DEMO-2, …
  2. Launch one worker per shard. The Manager's loop does this on dispatch: open_workspace {target: "story", story_id, name: "builder-DEMO-1", agent: "builder"}. The worker registers the matching role on startup.
  3. Address each shard by name. The Manager sends the brief with send_role_message {team, role: "builder-DEMO-1", text, replyTo: "role:manager"}. The thread's replies loop back to the manager's queue.
  4. Wake only the ones that need waking. Give the Builder agent a role_pending routine whose task checks role_state and claims its shard queue. That event is broad, without a role filter, so the task must choose its queue. Use inbox_idle only for mail addressed directly to a session. See the role-pending recipe.

Routine & agent — matching snippet

# agent.yaml — one Builder definition reused across shards
id: builder
name: Builder
description: Builds a single story end-to-end, holds a per-story role queue, reports back.
runtime: claude
launch: foreground
startup:
  - CLAUDE.md
  - .claude/skills/bmad-build/
default_prompt: /bmad-build
revision: 1

---

# config/agents/builder/routines/builder-wake/routine.yml — wakes the shard with mail
id: builder-wake
name: Wake the builder
owner: codesense
mode: wake
task: |
  Unread mail on your builder shard. Call claim_role_messages for your
  role and resume /bmad-build.
where:
  kind: team_workspace
  machine: local
triggers:
  - event:
      kind: inbox_idle
policy:
  max_runtime: 30m
runs_on: each_mac
revision: 1

List the sessions; the builder-* ones are the shards. This is the view the manager uses to decide who to brief next.

How to do this via MCP 
// Launch one shard per story (here DEMO-1; repeat for each story)
open_workspace {
  target: 'story',
  story_id: 'DEMO-1',
  name: 'builder-DEMO-1',
  agent: 'builder',
  machine_id: 'mac-B',   // pick a machine per shard (list_machines)
  launched_by: managerSessionId,
}

// Dispatch the story's brief to its shard's role name
send_role_message {
  team, role: 'builder-DEMO-1',
  text: '…the DEMO-1 brief…',
  sender: managerSessionId,
  replyTo: 'role:manager',
}
