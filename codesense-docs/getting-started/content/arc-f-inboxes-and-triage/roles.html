Roles: queue settings and live holders.

A role is a named queue. Registrations are shared by default, so several sessions can claim work from it. When an agent calls register_role {role: "builder", exclusive: true}, it becomes the exclusive builder for the lifetime of that session; another holder's attempt returns alreadyHeld instead of silently clobbering. The queue outlives any particular holder — if you kill the session, the next one that registers picks up exactly where the last one left off, including work that was accepted but not yet acked.

Four seat moves

1

Register

An agent joins the queue. Use exclusive: true for a single holder, such as a resolver; omit it for a shared worker pool. An exclusive registration returns alreadyHeld if someone else is already there. 

// MCP tool: register_role
{"team":{"org":"acme/team-context","team":"dev"},"role":"manager","sessionId":"YOUR_SESSION_ID","exclusive":true}
2

Claim

Pull a batch off the role's queue. Each delivery hands back a deliveryId + claimToken you'll need to accept and ack. 

// MCP tool: claim_role_messages — use instanceId and generation from register_role
{"team":{"org":"acme/team-context","team":"dev"},"role":"manager","instanceId":"YOUR_INSTANCE_ID","generation":1,"limit":10}
3

Hand off

You don't literally hand the role to another session; you just reply with replyTo: "role:manager". The reply lands on the role queue, so whoever's holding it next picks it up. The thread survives the handoff.

4

Release

When the human says stop, finish the current delivery, then release_role. Claimed-but-not-accepted work goes back to pending for the next holder. CodeSense also releases automatically when the session ends. 

// MCP tool: release_role — use instanceId and generation from register_role
{"team":{"org":"acme/team-context","team":"dev"},"role":"manager","instanceId":"YOUR_INSTANCE_ID","generation":1}

Worked example — the Manager

The manager role is the canonical one. The Manager Agent registers it on launch, drains its queue in a loop, launches workers, and releases it when the human stops it. Here's the agent.yaml that ships in the seed (examples/agents/manager/agent.yaml): 

id: manager
name: Manager
description: Watches the manager role queue, triages incoming work, launches and tracks
             workers, and reports to you.
runtime: claude
launch: foreground
startup:
  - CLAUDE.md
  - .claude/skills/manage-team/
default_prompt: /manage-team
revision: 1

The matching manager-ensure routine (examples/agents/manager/routines/manager-ensure/routine.yml) makes sure a Manager is on the queue: a mode: wake routine every hour, it wakes the running Manager to check its queue, and starts one when none is running.

Roles registry: role_save and roles_list

A role has a stable queue id and optional shared display settings. role_save writes <team>/content/roles/<id>.yaml; ids with special characters use percent-encoded filenames. The role id remains the queue address. Any teammate may edit these settings. They change neither queued messages nor existing holders.

id: reviewer
name: Review
icon: builtin-chess:knight
defaultHandler: acme/team-context/dev/reviewer

Call these MCP tools with the shown arguments:

// role_save
{"teamKey":"acme/team-context:dev","config":{"id":"reviewer","name":"Review","icon":"builtin-chess:knight","defaultHandler":"acme/team-context/dev/reviewer"}}

// roles_list
{"teamKey":"acme/team-context:dev"}

name must be nonblank. icon is a face reference such as builtin-chess:knight, or null for the default chess piece. defaultHandler is one saved-agent key or null. It records a preferred handler; it does not automatically launch an agent. roles_list returns configured settings, while role_state returns live holders, counts and delivery state. See the generated role schema and JSON Schema.

Choose the queue a session joins

A saved agent's agent.yaml field role: reviewer is its default queue membership. On open_workspace, omitted queueRole inherits that saved default, queueRole: "builder" overrides it, and queueRole: null joins no queue. The launch argument role is a display label; it does not join a queue. On a story launch, a role that names a reviewer also types the launch's task review (see Tasks). Changing role configuration never changes the saved agent's default role.

// open_workspace: with acme as the active org, inherit the saved agent's role
{"target":"team-workspace","team":"dev","name":"review","agent":"reviewer"}
// Override that membership by adding: "queueRole":"builder"
// Opt out by adding: "queueRole":null

To join or recover a live registration explicitly, use register_role with team: {org:"acme/team-context",team:"dev"}, role and your sessionId. Keep its instanceId and generation for claim_role_messages, accept_role_message and ack_role_message. role_state inspects the queue without claiming anything.

Send new work with send_role_message, using separate team and role arguments. send_message addresses a running session handle or human. Its replyTo: "role:reviewer" remains valid and routes a later reply to the durable queue. See parallel workers, the agent design guide and its skill for choosing responsibilities.

How to do this via MCP

Call the named MCP tool with its JSON argument object. Replace the session id with your CODESENSE_TAB_SESSION_ID, and use the returned instanceId and generation in later calls (the values below are illustrative).

// MCP tool: role_state — inspect one role
{"team":{"org":"acme/team-context","team":"dev"},"role":"manager"}

// MCP tool: register_role — join the role
{"team":{"org":"acme/team-context","team":"dev"},"role":"manager","sessionId":"YOUR_SESSION_ID","exclusive":true}

// MCP tool: role_state — inspect all roles
{"team":{"org":"acme/team-context","team":"dev"}}

// MCP tool: release_role — finish this registration
{"team":{"org":"acme/team-context","team":"dev"},"role":"manager","instanceId":"YOUR_INSTANCE_ID","generation":1}
