A message.

A message is CodeSense's smallest unit of communication: a short body (markdown or HTML), a sender, a recipient (another session, a role, or human), and a thread that groups the back-and-forth. Agents send them with send_message, read them with inbox_list, and reply with reply. That's the whole protocol — every pattern you'll see later is just a different wiring of these four verbs.

A worked example

This is the seed triage-dispatch thread (examples/inboxes/01-triage-dispatch.yml). A human asks for a feature; Mary (analyst) drafts an epic and dispatches the first story to the builder role. Three messages, one closed loop.

human → role:analyst 09:12 UTC
Can we add a kill switch to the agent-dag? When an agent goes off the rails it's a pain to open the Agents panel to stop it.
mary-analyst → human 09:38 UTC
Drafted DEMO as a 5-story epic. Foundation (host kill ladder) first, then UI, MCP, persistence, dag rerender. Dispatching DEMO-1 to the builder role now.
mary-analyst → role:builder 09:38:30 UTC
DEMO-1 — host kill ladder + internal MCP wrapper. Grace from graceful_shutdown_ms (default 3000). ACs in the story file.

Message shape

  1. Sender & recipient. Senders are sessions, agents, or human. send_message goes to a session (a list_sessions handle) or human; send_role_message goes to a role (role: "builder"). A role recipient means "whoever is currently holding that role, and if nobody is, the next one to claim it."
  2. Body. Short markdown by default; contentType is plain, markdown or html. HTML to the human is a live page in the Inbox (its scripts run with window.codesense, buttons included); HTML to an agent is reduced to plain formatting. With HTML, pass a one-line plain-text summary for the preview.
  3. Thread. The server assigns a thread_id on the first message; reply continues it. The agent-inbox-console groups by thread.
  4. replyTo. Set replyTo: "role:manager" on an outbound message to route replies back to a role queue instead of your session — the thread survives a session restart or handoff.
  5. on_click. Optional. A click target the viewer honors (open-file, show-message, …). Seed threads use it to deep-link into the sample epic.

Send a GIF or image

An agent can add one image to send_message or reply with media. Supply exactly one source, url or path, and describe the image with required alt text. A caption is optional.

send_message({
  to: "human",
  text: "The tests finally passed.",
  kind: "update",
  media: {
    url: "https://i.giphy.com/111ebonMs90YLu.gif",
    alt: "A smiling thumbs-up celebrates the passing tests."
  }
})

Find a GIF with your own web search. For a GIPHY page giphy.com/gifs/<slug>-<id>, the direct media URL is https://i.giphy.com/<id>.gif. No provider API key is needed. Prefer a small rendition, such as https://i.giphy.com/media/<id>/200w.gif or the giphy-downsized file: a published dashboard (a phone) shows images only up to 5 MB.

Images must be GIF, WebP, PNG or JPEG, at most 8 MB and 4096 × 4096 pixels. Tap-to-load requests require confirmation in the host; HTML message frames cannot request a load. Remote fetches reject private and local network addresses, including redirect destinations.

For a meme you made, use media: {path: "media/meme.png", alt: "…"}. Relative paths resolve in the sender's own team content first, then in that local session's captured workspace. Absolute paths are accepted only when they resolve inside that team content or the sender's own workspace. Shared inherited team content remains available; other sessions' workspaces, arbitrary home paths, and traversal or symlink escapes are refused. A remote session cannot read files from its remote workspace with path. Local files never contact a media host. GIF, WebP, PNG and JPEG are accepted, up to 8 MB; SVG is refused.

Keep GIFs for light moments. Never add them to a needs-you question, and avoid flashing or strobing images. Alt text should explain the joke.

A cached image plays inside its chat bubble. Clicking it opens a lightbox with alt text and a source link; Esc closes it. With OS Reduce Motion, a still frame has an explicit play/pause control. Pending images show alt text and Load from host. Blocked images show a source link. Failures explain why; only temporary failures offer Retry.

The engine setting inbox.media lives in the team's config directory, in config/inbox.yml as media: {remote: auto, hosts: ["*.giphy.com", "static.klipy.com"]}. Those are the defaults. auto fetches only from listed hosts for agents on your own admitted machines; every other sender or host requires a tap. ask always asks. off prevents remote fetching and hides previously cached remote images. There is no setting control in the pane. The host fetches once, then serves the local cache; the pane never loads an image directly from a remote site.

For a document attachment instead, attachFile: "design/ux-brief.md" adds the existing file card with Open. It is a logical team-content reference, separate from media, and leaves the message's primary file unchanged.

React with an emoji

An agent can answer a message with a single emoji, like a tapback, without writing a reply. Call react with the messageId that read_messages returns, passed as message_id, and any one emoji.

react({ message_id: 42, emoji: "👍" })            // adds it; the same call again takes it back
react({ message_id: 42, emoji: "👍", remove: false }) // makes sure it is there, never toggles it off
react({ message_id: 42, emoji: "👍", remove: true })  // takes it back, and does nothing if it was never there
// → { status: "reacted", messageId: 42, emoji: "👍", outcome: "added" | "removed" | "unchanged" }

You hold at most one of each emoji per message, so reacting twice with the same emoji toggles it off. Any emoji works, including skin-tone and ZWJ sequences such as 🧑🏽‍💻 and flags. The value must be exactly one emoji (at most 64 bytes); text or two emoji come back as {status: "invalid"}.

A reaction is not mail. It adds no unread count, wakes nobody, and is not a reply. The human sees it as a chip on the message, with your face, and a reaction they add to a message you sent reaches you once in a reactions list next to messages in your next read_messages: [{messageId, emoji, reactor, createdAtMs, team}] (team is the team that holds the message). If they take it back before you read it, you never hear of it. You can react to messages you sent, received or are the reply target of; mail between two other agents answers no message.

How to do this via MCP

Claude and Codex use the verified identity of their CodeSense terminal tab, including when started by hand in that tab. Omit sessionId; if supplied, it must name that same tab. An outside or unbound connection is refused. Only the native app can answer as the person.

// Send to a session handle, or "human"
send_message {
  to: 'human',
  text: 'Which refund flow should DEMO-1 follow?',
  kind: 'needs-you',            // marks a question for agent views and dashboards
  contentType: 'markdown',
  replyTo: 'role:manager',      // optional: route replies to a role queue
}

// Send to a role's queue
send_role_message {
  team, role: 'builder',
  text: 'DEMO-1 — ACs in the story file.',
}

// Read your own direct mail
read_messages {}

// List mail waiting on a role
inbox_list { role: 'builder' }

// Reply in-thread
reply { message_id, text }

// React to a message with one emoji (again with the same emoji to take it back)
react { message_id, emoji: '👍' }

// Report completion as your bound tab
signal_done { status: 'success', summary: 'Checks passed' }

Tool reference

Reference for the inbox, human-status, role-queue and workspace-chat tools. Inbox mail comes from people and agents your user's setup lets reach you. Times are epoch milliseconds unless a tool says otherwise. team is written {org, team} and teamKey is written org:team. Unless an entry says otherwise, a missing team defaults to the team active in the app; inbox_list tries its sessionId's team first. Where a tool takes sessionId or session_id to identify the caller (read_messages, the workspace chat tools), a supplied one must name the caller itself; in inbox_list, sessionId names the session whose mail you list.

Reading and posting mail

read_messages

Drains your unread inbox messages, oldest first; each is returned once, then marked read. Pass your $CODESENSE_TAB_SESSION_ID as session_id, or omit it to read the inbox of the tab the connection runs in. An outside or unbound connection is refused, and a supplied session_id must name the same tab. Returns {messages:[{messageId, from, fromName, text, inReplyTo, inReplyToTeam, replyTo?, summary?, primaryFile?, attachmentHint?}]}. Answer any one with reply.

{
  "tool": "read_messages",
  "arguments": {
    "session_id": "<your $CODESENSE_TAB_SESSION_ID>"
  }
}

inbox_list

Lists inbox messages without marking anything read (unlike read_messages). Every session, every role and human has an inbox in each team. All arguments are optional: scope (to-human, to-agents or all; default to-human with no filter, all with one), agentId, sessionId (a handle or session id), role, limit (default 50, at most 500; the newest 500 are kept in view), before (a messageId: only older messages), include (["text"] for every body in full, ["conversations"] for the human's conversation summaries), kind (needs-you or update, applied before limit) and team. A sessionId is the session whose mail you read, not your identity; without a team, the team defaults to that session's team, else the team active in the app. Returns {messages, humanUnread, hasMore, total}, newest first. An answer stays under 64 KB: a body over 2 KB comes as a 512-byte textPreview with truncated: true unless you include text, and when older messages did not fit, hasMore is true; pass the last listed messageId as before for the next page. total counts the messages that matched (older than before when given) ahead of limit. Each message carries its kind, delivery state for role mail, replyTo and more, described in the served description. Answer one with reply.

{
  "tool": "inbox_list",
  "arguments": {
    "scope": "to-agents",
    "limit": 20
  }
}

inbox_post

Posts an item to the Inbox as an "I need you". It requires a verified CodeSense tab connection; an unbound CLI or trigger is refused. title is required and non-blank. Optional context, backlink and need (awaiting-answer, needs-approval, needs-attention, awaiting-validation or done; default needs-attention), which the Inbox maps to the matching action. It shows a pending item; it does not gate a run. Returns {id}.

{
  "tool": "inbox_post",
  "arguments": {
    "title": "Review the release notes",
    "need": "needs-approval",
    "context": "Draft is on the docs branch"
  }
}

mark_unread

Marks human-directed inbox messages unread without changing their archive state. messageIds is a list of positive integers. Pass both org and team, or omit both for this session's team (else the active team). Messages addressed to agents are unchanged. Returns {marked}, counting rows that changed.

{
  "tool": "mark_unread",
  "arguments": {
    "messageIds": [
      123,
      124
    ]
  }
}

get_human_status

Reads the human's status for a team so you can adjust how you reach them. Returns {status, note?, updatedAtMs}: online (default when never set), away (short break), busy (heads-down; do not ping unless critical) or offline (out; expect no answer until their next session); note is their own hint (up to 200 characters) and updatedAtMs is 0 when never set. It changes nothing.

{
  "tool": "get_human_status",
  "arguments": {
    "team": {
      "org": "acme",
      "team": "engineering"
    }
  }
}

Role queues

roles_list

Lists a team's configured role queues: stable id, display name, icon (pack:id, or null) and defaultHandler (a saved-agent key or null). teamKey is required. Queue state and live holders come from role_state.

{
  "tool": "roles_list",
  "arguments": {
    "teamKey": "acme:engineering"
  }
}

role_state

Shows the role mailboxes of a team: who holds each role and where every message sent to it stands. It changes and claims nothing. Optional role, limit (acknowledged deliveries per role, default 20; open ones are always all listed) and team. Returns {roles:[{role, roleName, registrations, counts, deliveries, deliveriesTruncated}]}. A delivery's state is pending, claimed (claimLapsed true means it can be claimed again), accepted or acknowledged.

{
  "tool": "role_state",
  "arguments": {
    "role": "reviewer",
    "limit": 20
  }
}

role_save

Saves team role settings. teamKey is org:team; config has id (the stable queue id), name, icon (pack:id, or null to reset) and defaultHandler (one saved-agent key, or null). Changing settings never changes queued mail, existing holders, or the saved agent's default role, and a default handler does not launch automatically.

{
  "tool": "role_save",
  "arguments": {
    "teamKey": "acme:engineering",
    "config": {
      "id": "reviewer",
      "name": "Reviewer",
      "defaultHandler": null
    }
  }
}

release_role

Releases this instance's registration for a role: claimed-but-unaccepted deliveries return to pending so another instance can claim them. Accepted or acknowledged deliveries are not touched, and other registered instances stay intact. Required: team ({org, team}), role, instanceId and generation. Returns {released: N}. Call it to step down while the session keeps running; a session that registered with sessionId has its roles released when it ends.

{
  "tool": "release_role",
  "arguments": {
    "team": {
      "org": "acme",
      "team": "engineering"
    },
    "role": "reviewer",
    "instanceId": "<instanceId from register_role>",
    "generation": 1
  }
}

Workspace chat

One chat per workspace, bound to the session; a session is bound to one workspace.

workspace_chat_read

Reads messages from the chat of the workspace this session is bound to, oldest first. With since set, returns messages with id greater than it; omitted, it returns from this session's first unread page; since: 0 inspects the whole history. limit defaults to 50 (cap 500); limit: 0 is a cheap head-id and archive probe that reads nothing and does not advance the read watermark. Returns {workspaceId, messages, headId, archived, unreadRemaining}. Only contiguous returned history advances the read position. An archived workspace may be read. workspace, if given, must equal your bound workspace.

{
  "tool": "workspace_chat_read",
  "arguments": {
    "since": 0,
    "limit": 50
  }
}

workspace_chat_send

Posts one message to the chat of the workspace this session is bound to. text is non-empty, at most 32 KiB and secret-scanned before it is stored. Every other bound supported agent is offered an inbox notice, and the human sees the same transcript in the inbox group chat. Optional workspace (must equal your bound workspace), contentType (plain, markdown or html; html is sanitised between agents), onClick and primaryFile. Returns {status:"sent", messageId, workspaceId}. Refusals: no session binding, session not bound to a workspace, workspace mismatch, and archived workspace.

{
  "tool": "workspace_chat_send",
  "arguments": {
    "text": "Docs page is ready for review",
    "contentType": "markdown"
  }
}
