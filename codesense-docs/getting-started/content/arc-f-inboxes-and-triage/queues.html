Four states, one ladder.

Every role carries one queue. Deliveries land pending, a holder claims a batch, decides whether to work it and accepts each one, then acks when it's handled. The queue is the memory: a fresh session can register, claim what's already accepted-but-not-acked, and pick up exactly where the last holder stopped.

The four states

pending

Just landed. Nobody has claimed it. Visible in role_state.counts.pending.

claimed

A holder pulled it off with claim_role_messages; they have a claimToken and a short time window to decide.

accepted

accept_role_message promises to handle it. Returns a receiptId. Survives a session restart.

acked

ack_role_message with the receipt. Delivery leaves the queue; the thread stays in inbox_list.

Ordering, batches, backpressure

  • Order. Pending deliveries come back in send order; a claim is a FIFO cut of the first limit items.
  • Batches. One claim_role_messages yields a bundle of deliveryId + claimToken + messageId triples. You accept each one independently with its own disposition (work, or no_work with a reason for FYIs and dupes).
  • Backpressure. If a holder claims and goes dark, the claim expires — a later call returns StaleClaim and another holder can re-claim. Nothing is lost; the delivery lives in the queue, not in a session.
  • Resumption. On register_role, acceptedUnacked hands back previously-accepted work. The new holder inspects state (via list_sessions, inbox_list), finishes or re-dispatches, and acks.

Peek at the builder queue in your editable context repo: counts by state, who holds the role right now.

How to do this via MCP 
// Peek: counts.pending, counts.claimed, live registrations
role_state { team, role: 'builder' }

// Full loop
claim_role_messages {
  team, role: 'builder', instanceId, generation, limit: 10,
}
// → { deliveries }; for each delivery d:
inbox_list { role: 'builder', include: ['text'] }   // full bodies; d.messageId picks d's
accept_role_message {
  team, deliveryId: d.deliveryId, claimToken: d.claimToken, instanceId, generation,
  disposition: { kind: 'work' },
}
// → { receiptId }
// … do the work, reply, launch a worker, whatever …
ack_role_message {
  team, deliveryId: d.deliveryId, claimToken: d.claimToken, instanceId, generation, receiptId,
}
