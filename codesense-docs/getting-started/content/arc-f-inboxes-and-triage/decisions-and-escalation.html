Escalate once. Resume.

Fully autonomous flows die the moment a worker meets an under-specified acceptance criterion. The Resolver pattern is the fix: when a builder hits a decision it can't make, it posts a crisp question to the resolver role — options listed, recommendation stated — and waits. A human (or an agent running bmad-loop-resolve) picks it up, replies in-thread, and the builder resumes. The verdict lives in the story, not in anyone's head.

The seed escalation thread

Verbatim from examples/inboxes/02-decision-escalation.yml. The builder hits a PermissionDenied vocabulary question in DEMO-3; the human replies; the builder updates the story and continues.

amelia-builder → role:resolver 11:03 UTC
Escalating DEMO-3 AC-2: the story lists PermissionDenied as an error case but there is no admin / non-admin distinction in agent.yaml today. Do we add an admin: bool field, or do we interpret "admin" as "the agent that opened the session"? Blocked until this is decided.
human → amelia-builder 11:21 UTC
Interpret as "the human who owns the session." No new field. The host already threads principal through — reuse that. Update AC-2 copy to clarify, then resume.
amelia-builder → human 11:24 UTC
Got it. Rewriting AC-2 in the story and continuing. Thanks.

How to escalate well

  1. Name the AC. Which acceptance criterion, which story. Resolver opens the exact file; no scavenger hunt.
  2. Options, not a question. List 2–3 concrete options with a one-line consequence for each. "Do what you think" is not an option.
  3. State a recommendation. Even if you're wrong, it anchors the conversation. The resolver can accept or push back in one line.
  4. Say what unblocks you. "Blocked until this is decided." Resolver treats it as a priority delivery.
  5. Set replyTo explicitly. Usually replyTo: "role:builder-{storyId}" so the verdict lands on your shard's queue — survives a session restart.

The Resolver agent

You don't have to be the human. bmad-loop-resolve is a skill that holds the resolver role, picks up an escalation, runs an interactive clarification pass (reading the story, the architecture, the deferred-work ledger), and either answers in-thread or kicks it to a human when it genuinely can't decide. This is how a fully-autonomous loop stays unblocked overnight. 

# agent.yaml for a Resolver agent
id: resolver
name: Resolver
description: Holds the `resolver` role queue, resolves spec ambiguity against the story
             and architecture, and escalates to the human only when it genuinely cannot.
runtime: claude
launch: foreground
startup:
  - CLAUDE.md
  - .claude/skills/bmad-loop-resolve/
default_prompt: /bmad-loop-resolve
revision: 1

Pair it with a routine on inbox_idle for the resolver queue and you've got a self-driving decision loop with a human safety net.

How to do this via MCP 
// Builder escalates
codesense.invoke('send_message', {
  to: 'role:resolver',
  text: `Escalating ${storyId} AC-2 — options: (A) …, (B) …; recommend (B). Blocked.`,
  sessionId,
  replyTo: `role:builder-${storyId}`,
})

// Resolver claims and answers
const { deliveries } = codesense.invoke('claim_role_messages', {
  team, role: 'resolver', instanceId, generation, limit: 10,
})
for (const d of deliveries) {
  codesense.invoke('accept_role_message', { ..., disposition: { kind: 'work' } })
  codesense.invoke('reply', { messageId: d.messageId, text: verdict, sessionId })
  codesense.invoke('ack_role_message', { ..., receiptId })
}
