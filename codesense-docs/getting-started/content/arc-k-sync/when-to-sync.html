When to sync

You rarely need to sync "whenever." The CodeSense SDLC — the 14-phase factory loop Arc H walks — has a small number of sync checkpoints, each with a clear reason and a single call. Nothing syncs on its own, so each one is a call an agent (or you) makes. This is the page to bookmark; the one you'll check mid-sprint when you want to know whether now is a sync moment.

At a glance

Checkpoint Phase (Arc H) Direction Call
After spec written 02 Spec out reverse_sync_worktree
After story graph generated 05 Stories out reverse_sync_worktree
Mid-build, pattern adopted into team 08 Build out reverse_sync_worktree with paths
Pre-review 10 Review out · GitHub an agent commits and pushes
Post-ship 13 Ship out · GitHub an agent commits and pushes
Reorient after reconnect any read the status button
Absorb a teammate's push any in an agent pulls

The checkpoints, in order

1
Phase 02 · Spec

After a spec is written

Your spec exists only in your worktree until it is published. A Builder on another machine can't pick up a story whose spec they can't see. Publish it to team content as soon as it stops moving: preview first, then publish.

reverse_sync_worktree {paths: ["_bmad-output/<epic>/spec.md"]}
2
Phase 05 · Stories

After the story graph is generated

A Scout generated stories and inferred the dependency graph. Publish them before any Reviewer or Builder reads the next sprint plan — otherwise they'll trip over missing depends_on edges.

reverse_sync_worktree {paths: ["_bmad-output/<epic>/stories/"]}
3
Phase 08 · Build

Mid-build: a pattern deserves to be a team skill

You wrote a one-off helper and it's clearly useful beyond this story. Publish it to team content so the next sprint has it. A file CodeSense didn't copy in is new, so name the folder it lives in with sets.

reverse_sync_worktree {sets: [".claude/skills/story-helper"]}
4
Phase 10 · Review

Pre-review: push the branch

Review is the first time another agent reads your worktree. The Reviewer pulls via its own agent, so team content needs to be current. Publish the workspace's edits with reverse_sync_worktree, then ask an agent to commit and push the context repo.

"Commit and push the team context."
5
Phase 13 · Ship

Post-ship: push the closing edits

A story merged. Its retro notes and status changes reach teammates only once they're pushed. Publish the workspace's edits first, or they stay on that machine, then ask an agent to push (Arc H · 13 Ship).

"Commit and push the team context."
6
Any phase

Reorient after a reconnect

You rebooted, closed the lid, or lost the plot. The status button reads ⎇ branch | ↑N ↓M: ↑ is what GitHub doesn't have yet, ↓ what's new on GitHub, and a third count appears for conflicts. Its tooltip says when the clone last heard from GitHub. Nothing writes.

context_repo_status {}
7
Any phase

Absorb a teammate's push

A teammate shipped and the ↓ count went up. Ask an agent to pull the context repo. Your worktrees get it at their agent's next launch, or when an agent calls hydrate_worktree.

"Pull the context repo."

When not to sync

If a file is still moving, let it move. Publishing a half-written spec hands unfinished work to every teammate who hydrates it next. Publish at phase boundaries, not every keystroke.

You also don't need to publish a worktree-local scratch file. A publish never writes a file the repo tracks, and only looks for new files under the workspace's declared context or the sets you name.

How to do this via MCP

Agent-side equivalents 
const target = { kind: 'local', codeRepoPath: '<worktree>', sessionId: '<session>' }
// Preview each publish first with preview_reverse_sync_worktree and the same inputs.

// Phase 02 · Spec
reverse_sync_worktree { target, paths: ['_bmad-output/<epic>/spec.md'] }

// Phase 05 · Stories
reverse_sync_worktree { target, paths: ['_bmad-output/<epic>/stories/'] }

// Phase 08 · Build (share a new skill)
reverse_sync_worktree { target, sets: ['.claude/skills/story-helper'] }

// Phase 10 · Review and 13 · Ship: run git yourself, then report
report_context_sync { state: 'ok' }

// Reorient: branch, ahead/behind, conflicts
context_repo_status {}
