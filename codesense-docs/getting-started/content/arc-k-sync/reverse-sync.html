Reverse sync — worktree into context

Reverse sync is the direction out: an agent publishes the context files it edited in a workspace back to team content. It happens only when an agent calls reverse_sync_worktree, and nothing else ever takes a workspace's edits. No git add, no commit; other workspaces see the change only when they hydrate it.

What a publish does

reverse_sync_worktree compares the workspace with what CodeSense copied into it, and writes the differences to team content:

  • A file CodeSense copied in and you edited goes back to the team file it came from.
  • A new file under the workspace's declared context goes to team content, or to the tier to names: team, repo or personal.
  • A team file that changed since it was copied is a conflict. It is never written; it comes back in conflicts for you to resolve.
  • Team content is never deleted unless you pass includeDeletes: true. Without it, files you removed in the workspace come back in withheldRemovals.
  • Files the repo tracks, symlinks and files over 4 MiB are skipped.

preview_reverse_sync_worktree takes the same inputs and writes nothing. Call it first. No git command runs. The change is in your context repo on this Mac; committing and pushing it is a separate step that you or an agent do with git. See agent-driven git.

Where the file goes

File Goes to Why
A file CodeSense copied in The team file it came from The managed record says where it came from.
A new spec, story or skill Team content (default), or the tier to names Pass to: "repo" for files only this repo's agents should get.
Source code — (source repo) Source code goes through the branch's PR. A publish never writes a file the repo tracks.

A worked moment

A Builder's agent wrote a new skill in its worktree and the team should get it. Three calls and no git add in sight.

1
Edit lands. The agent writes .claude/skills/release-notes/SKILL.md inside its worktree. .claude/skills is in its declared context, so the file is a candidate.
2
Preview. The agent calls preview_reverse_sync_worktree with paths set to that file. The preview says add, its team path and its size, and shows no conflicts.
3
Publish. You say yes; the agent calls reverse_sync_worktree with the same inputs. The file is in team content. Other workspaces get it when their agent next starts or calls hydrate_worktree.

Walking it back

A publish writes team content, and team content is a git tree: until someone commits and pushes it, the change is only in your local context repo, so git there can undo it. To throw away a workspace's edit instead, call hydrate_worktree with that path and overwriteModified: true; it replaces your copy with the team's version.

Local vs remote

The same call works for a workspace on a machine: pass target: {kind: "remote", machineId, workspaceHandle}. CodeSense reads the changed files from the machine in one batch and writes team content on this Mac. The commit and push happen in the context repo on this Mac, with git.

How to do this via MCP

Agent-side equivalent 
const target = { kind: 'local', codeRepoPath: '<worktree>', sessionId: '<session>' }
const paths = ['.claude/skills/release-notes/SKILL.md']

// 1. See exactly what would be written. Writes nothing.
preview_reverse_sync_worktree { target, paths }

// 2. Publish, after the user agrees.
reverse_sync_worktree { target, paths }
