Agent-driven git

CodeSense never commits, pushes, pulls or merges your context repo. It reads files, writes files, and shows you what changed (it reads git status and history to do that). The git is done by an agent you ask, with the same git and gh you use yourself. That split is deliberate: the app stays a plain, auditable content editor, and the version-control decisions sit with an agent you can instruct, or with you.

Why the app doesn't push, pull or merge

Developer tools that call git on your behalf carry a long tail of failure modes: SSH identity drift, stale credential helpers, half-staged merges, hooks that reach into production, surprise force-pushes. More importantly: the agent that wrote a change is in a better position than CodeSense to decide what the commit message should be, whether to open a pull request, which branch to target. So the app has one job: keep the content on disk consistent, and show you what changed.

There are no bundled git skills to install or keep in step. Ask any agent ("commit and push the team context", "pull the context repo") or write your own skill for it under .claude/skills/ if you want the same steps every time.

What CodeSense shows you

The left nav's scope row has the context repo's status button: ⎇ branch | ↑N ↓M. ↑ counts changes GitHub doesn't have yet (edits and unpushed commits), ↓ what's new on GitHub, and a third count appears for conflicts. With nothing to report it reads synced. Its tooltip says the same thing in a sentence, including when the clone last heard from GitHub.

  • A click opens the Changes view: the files the team's context has that GitHub doesn't, each opening as a redline against the last pushed version.
  • A conflict opens a card for each file instead, with Use mine, Use theirs, Keep both, Hand to ‹agent› and Compare. Settling a file writes the side you chose and stages it; the agent doing the sync finishes the merge or rebase.
  • A failure (Sync failed, GitHub sign-in expired, or changes with no remote to send them) offers Retry, Sign in again or Set up. Each one asks one of the team's agents to do it, through its inbox.
  • History, from the left nav's view menu, is the context repo's commit graph and the files each commit changed.

The state comes from what git shows on disk (a merge or rebase in progress counts as syncing, and as failed once it has sat untouched for 10 minutes) and from what the syncing agent last reported with report_context_sync.

Worktrees sit one layer below

Moving files between a worktree and the team's content is not git. Agents do it with MCP calls, and nothing is committed: hydrate_worktree brings team content in, reverse_sync_worktree (after preview_reverse_sync_worktree) sends an edit back. Edits waiting in workspaces show as the scope row's N unsaved counter, with Publish and Discard for each. See hydration and reverse sync.

A worked moment

You asked a Builder to add a routine. The agent wrote the file into its worktree, then, because the routine is team configuration rather than source code, it sent the file to team content with reverse_sync_worktree.

1
The agent writes. The Builder edits config/agents/builder/routines/review-nightly/routine.yml in its worktree.
2
The agent sends it to the team. It calls preview_reverse_sync_worktree, shows you the result, then calls reverse_sync_worktree. The file is in team content, uncommitted, and the status button's ↑ count goes up.
3
An agent pushes. You ask an agent to commit and push the context repo (or do it yourself). It runs git, then calls report_context_sync so the status button shows how it went.
4
A teammate pulls. Their next git pull of the context repo (theirs, or their agent's) brings it in. Their worktrees get it at the next agent launch or hydrate call.

At no point did CodeSense itself run a git command, and nothing moved without a call.

How to do this via MCP

Agent-side equivalent

An agent reads the same state the status button shows, does the git itself, and reports back: 

// Branch, ahead/behind, conflicts, sync state. Read-only.
context_repo_status {}
// Uncommitted files, grouped. Read-only.
get_publish_set {}
// Commit history.
context_repo_history { limit: 20 }
// After running git: tell the status button how it went.
report_context_sync { state: 'ok' }
