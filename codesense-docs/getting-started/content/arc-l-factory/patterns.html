Role patterns

Six roles. Pick the ones your work needs; ignore the rest. A tiny factory might run one Builder. A busy one runs a Triager, three Builders, a Reviewer, a Resolver, and a Scout — each on their own inbox queue, each wakeable by a routine.

Why roles instead of named agents

Roles are what the inbox is for, not who's doing it. "Review" is a role; Winston (reviewer) is one agent that currently plays it. A role lets you fan work out to N agents without rewriting the dispatcher — any session that joins the reviewer role (register_role) can claim a review message. If one agent dies, another picks it up.

Every role lines up with one inbox queue. A routine with a role_pending trigger starts an agent for each message queued for its role; one with inbox_idle wakes a long-running agent that has unread mail. The whole factory is six queues of work and a bunch of agents happily claiming off them.

The six roles

Builder

Writes code. Reads a story + its frozen spec, creates a worktree, runs bmad-build, pushes a PR. The workhorse of the factory — you run as many as your inbox has stories.

Scout

Reads the world and writes to context. A Scout reads community issues, release notes, telemetry, failing dogfood runs, or an upstream repo and files findings into the context repo. The eyes of the factory.

Resolver

Answers escalations that Builder sessions can't safely resolve alone — a frozen spec contradiction, a missing fixture, a decision only a human can make. A Resolver can be a human or an agent that calls bmad-loop-resolve.

Reviewer

Reads a PR, runs multi-lens review, posts findings. Gates the merge. A Reviewer is cheap to parallelize — three Reviewers on three Macs clear a backlog in minutes.

Triager

The dispatcher. Reads anything that lands in a generic inbox and routes it to the right role queue. The Triager runs the closed loop — see the dispatch flow on the inbox-flows page.

Synthesizes. Reads a batch of Scout findings, retrospectives, or sprint output and distills them into a brief, spec, or decision. Where Builder is tactical, Analyst is strategic.

How roles compose

A role on its own is a worker. Roles compose through inboxes: the output of one agent is a message to another role's inbox. Builder posts a "review-this" message to reviewer. Reviewer posts a "decide-this" message to resolver. Resolver posts a "rebuild-with-this-decision" message back to builder. The Triager reads the top-level team inbox and routes.

Nothing in this graph has a special wire. It's all the same inbox primitive. See the four shipped inbox-flow shapes for the dispatch / HITL / SDLC / one-shot patterns that compose into every recipe on the composition recipes page.

How to do this via MCP

Each role is just an agent + a routine. Both are authored via MCP:

agent_create { id: 'winston-reviewer', name: 'Winston (reviewer)', runtime: 'claude', … }
// → config/agents/winston-reviewer/agent.yaml

// A scheduled routine: routine_create { agent: 'winston-reviewer', name, task, when: 'hourly' }
// A role_pending routine is written as a file:
//   config/agents/winston-reviewer/routines/reviewer-claim/routine.yml

CodeSense picks up files you or an agent write on save, no restart.
