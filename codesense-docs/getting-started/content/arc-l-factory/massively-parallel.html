Massively parallel shipping

Pick a story graph. Spin up N Builders. Watch the DAG light up like a Christmas tree. This is Phase 8 of the factory playbook, with a per-story worktree keeping each Builder's checkout clean and the builder inbox serializing who claims which story.

What makes parallel safe

Running five agents against the same repo without stepping on each other sounds hard. In CodeSense it's four invariants:

  1. Per-story worktree. Each story claim creates its own git worktree. Builders never share a working tree.
  2. Inbox claim-and-ack. A message in the builder inbox can only be claimed by one Builder at a time; claim is atomic.
  3. Depends-on frontmatter. Stories declare upstream dependencies; a Builder won't claim a story whose upstreams are still open.
  4. agent-dag ground truth. One dashboard shows all live agents, their worktrees, their current story, their last check-in. If anything looks off, you see it.

Step-by-step: turn a 5-story epic into 5 PRs

  1. Freeze the spec. You've got an epic with a dependency graph (each story's depends_on field, written when the stories were sliced).

  2. One Builder definition, many sessions. One amelia-builder agent definition is enough: each launch is its own session in its own story worktree, and every one of them claims off builder.

  3. Add the claim routine. One routine.yml with a role_pending trigger in fresh mode: each message queued for builder starts a Builder session that claims it.

  4. Open the agent-dag. Within a minute, the DAG shows Builder-1 claiming DEMO-1, Builder-2 claiming DEMO-2 (its upstream was DEMO-1's dep-free sibling). DEMO-5 stays grey — it's waiting on an upstream decision.

  5. Watch for amber. If a Builder session hangs for > 10 minutes without a worktree write, the DAG shades amber. One click reclaims the story to another Builder.

The parallel braid

Each Builder is a strand. Strands run in isolation (per-worktree) and only cross at the inbox. The braid is what you watch when you want to feel the factory move. 

Builder-1 ──[DEMO-1 ✓]── open PR ──→ reviewer inbox
Builder-2 ──[DEMO-2 ✓]── open PR ──→ reviewer inbox
Builder-3 ──[DEMO-3 ⚠ escalated]──→ resolver inbox
Builder-4 ──[DEMO-4 claim]── (running)
Builder-5 ──[—]── waiting on DEMO-5 upstream
How to do this via MCP 
// The Builder definition
agent_create { id: 'amelia-builder', name: 'Amelia (builder)', runtime: 'claude',
               startup: ['.claude/skills/bmad-build/'] }

// The claim routine: write it as a file, since routine_create takes only a
// schedule (`when`) and a role_pending trigger lives in routine.yml:
//   config/agents/amelia-builder/routines/builder-claim/routine.yml
//   (the phase 8 snippet in the factory playbook)

// Queue the five stories
send_role_message { team: '<team>', role: 'builder', text: 'Build DEMO-1' }   // … one per story

Each parameter's exact shape is in the MCP explorer.
