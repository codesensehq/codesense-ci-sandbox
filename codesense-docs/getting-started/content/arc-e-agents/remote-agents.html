Same file. A different machine's login.

A "remote agent" is just an agent whose session happens on a different machine. The file in config/agents/ doesn't change — nothing in it binds a machine. What changes is the launcher: open the agent on a tab belonging to a remote-connected machine, or point a routine at it, and CodeSense starts the CLI on that machine instead of yours. The team chain resolves the same way; the files land on the remote under ~/.codesense/sessions/; the runtime starts with the remote user's own claude or codex login.

The launch, step by step

1

You pick a machine

Open the agent from a terminal tab bound to a remote machine, or set machine: on the routine task. Local is the default; naming a remote is one field. See arc D → machines for how machines are declared.

2

CodeSense opens an SSH session

Over your pinned host key, as your Unix user on that box. Your private key never leaves your Mac — see remote (private account) for the full posture.

3

The context resolver runs — on the remote host

The team-chain walk and the startup resolve happen on the remote machine, against the context repo that lives there (same org, same team, same files). CodeSense never diffs the two sides — if a file resolves, it was present on the box when the session started.

4

The CLI runs under the remote account

The claude or codex binary on the remote box starts, with that user's own login — their keyring, their config, their rate limit. Nothing in your agent.yaml carries a token. Each teammate on the same host launches under their account.

5

The MCP bridge comes along

The CodeSense MCP server reaches your app from the remote session through the terminal-server's reverse channel. The bridge is still "unlisted" — the agent never names it in mcp.servers — but a remote launch is where the bridge really earns its keep: no port exposure on the remote, no shared secret, just the ongoing SSH session.

What usually trips people up

  • No absolute paths in startup. Absolute paths from your Mac won't exist on a remote. The validator refuses them already — this is just the reason it does.
  • Give headless remote Codex an approval policy. A launch: headless agent with no permissions.codex.approval_policy gets never added for you — otherwise it would hang on an approval nobody sees. See agent.yaml.
  • CLI login per teammate. If a teammate's own claude isn't signed in on the remote, the launch fails on their side with the CLI's own error. CodeSense never copies logins across users.
  • The host-agent exception. A couple of workspace setup tools (create_local_organization, attach_context_repository) only work on the account's own Mac. See arc D → parity matrix for the full list.
  • Permissions pass through. The CLI on the remote enforces permissions.claude / permissions.codex itself. CodeSense doesn't double- check. If your remote has a different CLI version with a different allowlist dialect, the CLI's own error points at the bad key.

How to do this via MCP 
// List machines you can launch on. Local shows as a machine too.
codesense.invoke('list_machines', {})

// Open an agent on a specific remote (same agent.yaml you'd launch locally).
codesense.invoke('open_remote_tab', { machineId, agentId })

// Routine-driven launches set `machine:` on the task; see arc K.
// For headless Codex remote agents, make sure approval_policy is set.
codesense.invoke('agent_preview', {
  name, runtime: 'codex', launch: 'headless',
  permissions: { codex: { approval_policy: 'never', sandbox_mode: 'workspace-write' } },
})
