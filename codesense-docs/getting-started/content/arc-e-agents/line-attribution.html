What is captured

For each line an agent wrote, in a commit made while capture was on:

  • the tool (claude or codex);
  • the agent CLI's own session id;
  • the model, when git-ai could read it from the session's transcript.

No prompt text. CodeSense runs git-ai with prompts excluded from every repository, so the note holds who wrote a line and never what was asked. CodeSense also writes nothing into the notes itself. A line nobody tracked (a commit made with capture off, or a line the note does not cover) reads as unknown, never as human.

Capture is on this Mac for the CodeSense-managed worktrees agents launch into. CodeSense does not run git-ai install-hooks and never edits your ~/.gitconfig or ~/.claude: git-ai runs in its own home under ~/.codesense/git-ai/, and a launch gets the hooks in its own private settings. Codex receives trust hashes for CodeSense-injected hooks through launch flags; CodeSense may also add those hashes to its native hooks.state, preserving unrelated configuration. Remote machines and OpenCode report unsupported. git-ai's own telemetry and update checks are switched off.

CLIs without capture. A session of a CLI CodeSense doesn't capture (OpenCode and Hermes) in a managed worktree is launched with GIT_REFLOG_ACTION=codesense-unsupported-cli <cli>, so git-ai never credits its commits to you. Their lines count as unattributed, and why_line names the CLI with reason unsupported_cli while a local reflog still records the commit. Git also records that session's branch switches under that name, so git checkout -, git switch - and @{-N} skip them: in these sessions, and in the same worktree afterwards, switch branches by name.

Only your attached clones. CodeSense's git-ai daemon does work only for the source repos attached on this Mac (by any profile), so repos it does not manage, such as the scratch repos an agent's tests create, cost it nothing. It lists each attached clone's Git directory in git-ai's daemon_repo_roots; a clone's linked worktrees share it, so they are covered. Attaching or detaching a repo updates the list straight away, with no daemon restart, and every launch and app start rebuilds it from the attachments. With no repo attached the list is left out and git-ai tracks every repo. A managed worktree whose repo isn't attached launches with capture off (repo_not_attached): attach its clone and the next launch captures, with no app restart. describe_setup.attribution.daemonRepoRoots counts the clones CodeSense lists (0: no list). If clones are attached but none can be read as a Git repo, the list written before is kept rather than widened to every repo, and the count is null.

If you also run git-ai yourself and installed its hooks (git-ai install-hooks), they stay in your settings and keep working outside CodeSense. In a CodeSense session with capture on (active), they cannot reach any git-ai daemon: the session points GIT_AI_DAEMON_HOME and its sockets at a path that does not exist, Claude and Codex run hooks with the session's environment, so your hooks exit without recording and exactly one checkpoint, CodeSense's, counts per hook event. describe_setup.attribution warns user_hooks_present when it finds them in your Claude settings (user, local, CLAUDE_CONFIG_DIR or an attached checkout's .claude/) or Codex config. In those sessions, your own git-ai commands that need its daemon fail fast. If your git-ai's git shim is on PATH, git commands still run through it; its wait for a note finds no daemon and git carries on. A session with capture off changes none of this.

Line tracking is installed automatically

On macOS with Apple silicon, CodeSense installs its bundled build of git-ai into ~/.codesense/bin/git-ai. It checks the bundled bytes against the app's pinned SHA-256 and exact version before making the copy available. No runtime download or separate git-ai installation is needed. A user's copy on PATH is reported as user_copy_present and is never run or changed. User symlinks are preserved.

Installation runs in the background at startup and when a managed launch needs it. Turning attribution on also requests an install and waits up to 30 seconds. installing means installation is still running: a session launched then needs to relaunch to capture lines. Launches continue even if installation fails.

An own copy whose exact version differs from the bundle is replaced, unless its numeric version is newer. Newer copies are kept with unsupported: newer and capture stays off. Before replacement, the old binary is kept as ~/.codesense/bin/git-ai.prev-<old-version>; only the most recent previous copy is kept. Notes, managed config and user settings are untouched by replacement.

To undo a replacement, run cd ~/.codesense/bin && mv git-ai.prev-1.7.5 git-ai (use the previous filename shown by the doctor). On the next start, CodeSense recognises the restored bytes and reports unsupported: user_pinned, keeping capture off and respecting the restored copy. To release that pin and reinstall the bundled build, use the existing MCP call (with an absolute path to your checkout):

save_source_repo_attachment {"repoPath":"/absolute/path/to/repo","attribution":"on"}

describe_setup.attribution reports the binary, exact version, daemon reachability and any installation warning. It announces replaced git-ai <old> → <new> (previous kept at …) once, including after an app restart before its first read. That read marks the notice shown in the existing replacement receipt; it changes no capture settings. Its previousBinary field keeps {version, replacement, path} readable after an app restart, even after the one-time warning is consumed. The recorded previous path may be absent after you move that file back to undo the replacement. A user_pinned warning names the MCP recovery call above. While the old managed daemon is running, capture stays off and the doctor shows restart pending; the next launch restarts it before capture is enabled. list_worktrees carries the attribution status from each worktree's last launch: active, off, installing, install_failed, not_installed, unsupported_version, unsupported or error.

A missing bundle or checksum/version mismatch reports install_failed with bundle_missing, sha_mismatch or version_mismatch in the message. The last failure remains readable from disk after an app restart until a successful retry. A restart retries installation. During one app run, these failures retry only when attribution is explicitly turned on. Other file or version-probe failures retry after 60 seconds, or immediately when attribution is explicitly turned on. A failed replacement keeps the old binary on disk and capture off until the pinned build is available. Other platforms report unsupported.

At startup, a background sweep imports retained completed checkpoint archives and live logs from attached clones with capture enabled. While the app is open, completed archive events trigger a debounced capture using the same importer. Line queries reconcile on demand. Stored turn links and Claude s_ identities survive later log pruning; logs already pruned before either capture cannot be recovered. No retention interval is assumed.

describe_setup.attribution.capture reports the last completed sweep: lastSweepAt (epoch milliseconds, or null before a sweep), trigger (startup or watcher, or null), clonesSwept, logsSeen, logsNew, traceRowsStored, sessionMappingRowsStored, watchErrors (registration errors in the latest watch reconciliation), and lastError. Counts describe that sweep; logsNew counts first-imported files, and session mapping rows are stored checkpoint rows carrying an s_ identity. This status is retained per CodeSense home in memory since app start. Reading setup does not run a sweep. Capture runs at startup, on completed archive events, and on demand.

A terminal server can keep running across app updates. If the server selected for a Codex launch predates checkpoint-hook trust, that launch reports error with an outdated-terminal-server message and starts without capture hooks. Review the live sessions before restarting the terminal server, then relaunch the agent to enable capture. An app restart alone does not replace that server.

Notes stay on this Mac, unless you opt in to push

Capture is on for every managed worktree, public or private, and its notes never leave this Mac. CodeSense's git-ai writes them to refs/notes/sense, not git-ai's usual refs/notes/ai, and is configured never to push them. So you can analyze everything agents work on, including a public or company repo, without publishing who wrote what.

Pushing is a per-repo opt-in. A repo set notes: "push" pushes its notes to its origin with the branch, so teammates and other machines read the same attribution. Only that origin is allowed (its https and ssh forms); a push anywhere else keeps the notes. A repo with no origin refuses push with no_remote and nothing in that request is saved. The change applies to the next push at once, with no relaunch; the call reports applied: now, pending (saved; git-ai is not installed yet, and it applies before the daemon next starts), unsupported (this git-ai cannot keep notes local) or failed (saved, applied at the next launch). The push list is one per Mac: every local profile's choices count. Choices are shared by all checkouts of the same repository and survive detaching and reattaching a clone. 

save_source_repo_attachment { repoPath: "/path/to/clone", notes: "push" }         // share notes with origin
save_source_repo_attachment { repoPath: "/path/to/clone", notes: "local" }        // the default
save_source_repo_attachment { repoPath: "/path/to/clone", attribution: "off" }    // never capture
save_source_repo_attachment { repoPath: "/path/to/clone", attribution: "auto" }   // the default: on

describe_setup.attribution reports notesRef (sense) and notesPushRepos, the repos set to push. The old private parameter is accepted for one release and ignored: capture no longer depends on whether a repo is private.

The trade-offs

  • Other machines see unknown. A local-only note exists only where it was written. why_line and story_changes elsewhere report basis: unknown with a reason that ends "notes for this repo stay on the machine that wrote them (local-only)"; nothing is inferred. Set the repo to push if other machines should read it.
  • Your own pushes can still send notes. git-ai keeps notes local on the pushes it sees. git push --mirror, or naming the ref yourself (git push origin refs/notes/sense), is git's own push and sends it anyway.
  • Opting in shares the history. git-ai pushes the whole refs/notes/sense ref, so notes written while the repo was local go too.
  • Notes already pushed stay pushed. Repos that pushed refs/notes/ai before keep it on their remote; CodeSense never deletes remote refs. To remove it, run git push origin :refs/notes/ai.
  • A git-ai of your own keeps its settings. Your own git-ai (on PATH, with ~/.git-ai) writes and pushes refs/notes/ai as before and never carries CodeSense's refs/notes/sense.

If the git-ai in use cannot keep notes local (it refuses the local-notes settings), a repo set local reports off with reason notes_would_push and captures nothing; a repo set push still captures. Merges are merge commits only, which CodeSense's repos already require.

Known limitation: GitHub squash and rebase merges

A squash or rebase merge done on GitHub rewrites the commits, and the new commits carry no note, so the exact line → session link is lost for them. A merge done locally, under git-ai, keeps it. A commit with no note resolves as unknown, never as human.
