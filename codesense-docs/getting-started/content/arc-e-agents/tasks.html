Judge agent work by task, not by run.

One run often holds many tasks, and what counts as good depends on the kind of task. Supported local launches get a task record: a plain goal, a type, a parent, targets and, when it ends, an outcome that sits next to those targets. CodeSense records the facts and never scores the agent.

Task records do not cover remote managed launches.

One working example

A lead builds a story, then asks a second pass to review the design. The lead starts the review as a task of its own, relates it to the build and links the review file:

task_start {
  "sessionId": "<your $CODESENSE_TAB_SESSION_ID>",
  "goal": "Review the task store design against the story",
  "type": "review",
  "subject": "design",
  "parent": "<the build task's taskId>",
  "links": [
    {"kind": "relates_to:reviews", "target": "<the build task's taskId>"},
    {"kind": "artifact", "target": "design/DEMO-30/review-r1.md"}
  ]
}

When the review is finished, the lead closes it and records a verdict for the Steward to be calibrated against:

task_update {
  "sessionId": "<your $CODESENSE_TAB_SESSION_ID>",
  "taskId": "<the review's taskId>",
  "acceptanceMet": true,
  "label": {"verdict": "good", "why": "found the real defect, no noise"},
  "status": "done"
}

task_read on the build task now shows outcome.reviewRounds: 1 and the review task below it. A review is just a task of type review: there are no review-specific fields, so a design review, a doc review, a code review and a research pass all read the same.

A reviewer launched with open_workspace {target: "story", role: "reviewer"} (or a saved agent whose queue role or name is a reviewer) gets a review task at launch, with typeSource role or agent. Pass reviews: <the dev task id> to link it exactly (only a task of the same story and team links exactly); without it the task links the story's latest open task of its team and fieldSources.reviews says associated. A restored reviewer keeps the target, and the basis, of the review it continues. A launch that names reviews but whose task is not a review links nothing and says why in unavailable.reviews. A delta round run in the same reviewer session is its own review task: one task_start {"type": "review"} per round, linked relates_to:reviews to the dev task.

What is captured for you

Every launch path writes the session's task once, from what it already knows. Nothing needs to be typed.

  • Goal. The brief's first lines (at most 280 characters, secrets removed). A brief that only points at one .md file ("Read X and follow it") takes its goal from that file's first lines. A routine's goal is its name, then the first line of its task. A story's root task takes the story's title and the first sentence of its Purpose.
  • Type. The first rule that matches: a Task-Type: line in the brief (or type in task_start); a routine; the team policy's skill-to-type map for the task's main skill; the story's type (bug is bugfix, spike is exploratory, story is feature). A story launch whose role or saved agent is a reviewer is review unless its brief or routine says otherwise. Otherwise unclassified, with the reason in unavailable.
  • Story. The launch's own story (fieldSources.story: launch), else the story of the task it continues (continues), else the story of the story worktree it runs in (workspace). Nothing else is guessed: a launch outside a story workspace has none.
  • Parent. The task of the session that launched it (resolved to its session id once, at reservation, so a reused handle never re-parents it). With no launcher, the story's root task story:<id>. parentSource says which, and a fallback says why. A restore relaunch (launchedBy: "CodeSense restore", after a terminal-server restart) keeps its story and team and the parent of the task it continues (parentSource: continues), and links relates_to:continues to that task.
  • Main skill. The first skill the brief names ($x, /x or the bare name) that the launch provides.
  • Layer versions. Copied once at launch: every skill the launch provides with the hash of that skill's own files, the source worktree's commit and the context checkout's commit. task_start copies a named skill's version from the session's launch snapshot. A missing one says unavailable with its reason.
  • Agent layer. task_read.agentLayers.sessions joins each linked session's sessionId, agent (key@revision) and manifestHash from its recorded launch. Missing records or fields give an unavailable reason. With no session links, agentLayers.unavailable explains why this layer cannot be read. These facts are joined, not copied onto the task.
  • Other skills. task_read.otherSkills.skills lists additional skills invoked in the indexed session conversation. Session root tasks read the whole session; other tasks read only invocations within their own interval. Missing evidence says why.
  • Playbook. task_read returns a top-level playbook with skill and hash from the parent's immutable launch snapshot. It says pending while the parent's task is still being captured, or unavailable when there is no parent, the parent names no main skill, or that skill has no launch hash.

The ids are the identities that already exist: a launched session's task is its session id, a routine run's task is its run id, a story's root task is story:<id>. A task made without a story can be given one later with task_update; it then moves under that story's root.

fieldSources records where goal, story and subject came from, alongside typeSource, parentSource and targets.source. Late capture fills provisional facts and preserves explicit task_update refinements.

Targets are your team's policy

Defaults live in your team's content, in tasks/task-types.yml. They are policy, not engine limits, and a task copies them when it is made, so editing the file never rewrites history.

types:
  feature:     { targets: { wall_minutes: 240, cost_usd: 25, review_rounds: 3 } }
  exploratory: { targets: { wall_minutes: 480, cost_usd: 60 } }
  routine:     { targets: { wall_minutes: 10,  cost_usd: 2 } }
skill_types:
  bmad-code-review: { type: review, subject: code }
tamper_globs: ["**/tests/**", "**/*.test.*", ".github/**"]

A brief overrides them with a line such as Targets: wall_minutes=60 cost_usd=5, and task_update can too. targets.source says which won: default, brief, task_start or task_update. With no policy file, targets say why they are unavailable.

The outcome, as facts

A task closes when its session calls signal_done (success is done; any other verdict is abandoned and the raw verdict is kept), when a headless process exits without signaling, when its routine run ends, or through task_update with done, abandoned or superseded. The first close stands. task_read then returns, next to the targets:

  • outcome.scope: session covers the whole linked session, including its subtasks. interval covers every other task's start-to-close interval, including a routine wake on a reused session;
  • time: wall, active and idle, from the linked sessions' turns. An interval task counts only its own interval and stops growing when closed;
  • cost and models: from the same usage session_usage shows. All native conversations attributed to the launch count, including work after /clear. An interval task uses only model calls timestamped inside its interval. Missing timing or attributable usage says unavailable with a reason;
  • review rounds: the review tasks that relate to this one;
  • acceptance: whatever the lead set with acceptanceMet;
  • tamper: whether files matching the policy's tamper_globs were edited between the commit the task started at and the end of the task, committed or not. The files are listed. While evidence is being captured, unavailable.tamper gives a pending reason. If the app stops before capture finishes, that reason remains pending;
  • planned vs actual scope and rework: outcome.plannedVsActual compares the task's commit files with the story's Touchpoints; note session ids link exactly, otherwise commits within its interval are associated. If a selected commit’s note cannot be read locally, interval files remain visible with unknown basis and an attribution-unavailable reason. outcome.rework gives commits and files changed after its first closed review that touch files the task changed. Missing evidence says why in unavailable. Both task_read and task_list return these live facts. outcome.scope remains the time-attribution scope (session or interval). This change-scope evidence is separate from the time/cost coverage in outcome.scope.

A label (good or bad, with why, who and when) is kept for calibration. Judging the work, and finding patterns across reviews, belongs to the agent design team, not to CodeSense.
