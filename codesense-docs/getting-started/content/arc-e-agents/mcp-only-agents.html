No UI. Just the bridge.

The CodeSense MCP server is enough on its own. If what the agent does is "read CodeSense state and act on it" — not "write code," not "poke a repo," not "answer in Slack" — you don't need a filesystem writer, a shell, or any other MCP server. You need the bridge. The result is a tiny, fast, auditable agent you can run on a cron without worrying about scope.

When it fits

  • Dashboard caretakers. Keep a canvas or an HTML dashboard fresh — read inbox counts, re-render the pane, done.
  • Scheduled reporters. Walk open sessions once a day, build a send_message digest to the human.
  • Routine sentries. Watch a role queue; when it crosses a threshold, open a story in the pipeline.
  • Setup wizards (read side). Describe the current setup, point out gaps — writes stay behind a human confirm.
  • Audit / lookback. Walk retrospectives, inbox threads, feedback. Writes markdown to a path via the bridge's document tools — not through a shell.

Three fields do all the work

1

Leave mcp.servers empty

The bridge is on by default. Not listing anything means the agent can't reach any external service — not Slack, not GitHub, not a third-party API — even if the team's .mcp.json defines them. Everything the agent does, it does through the CodeSense bridge.

2

Allowlist the mcp__codesense__* prefix

Claude's tool-name convention is mcp__<server>__<tool>. A single "mcp__codesense__*" allow lets the agent call every CodeSense tool and nothing else. Narrow further with "mcp__codesense__send_message" if the agent really only needs one.

3

Deny filesystem & shell

deny: [Edit, Write, Bash] for Claude. For Codex, sandbox_mode: read-only. The agent still gets Read, Grep, Glob — fine for reading its own skill files and planning — but can't touch the user's tree outside what the bridge offers.

Policy for Codex. CodeSense auto-approves its generated bridge alias even under on-request or untrusted; bridge calls do not prompt. The captured bridge grant plus mcp.bridge_tools control least privilege. Shell and filesystem sandbox settings stay unchanged, but bridge tools execute outside that sandbox. Use an explicit list such as [who_am_i, read_messages, reply, signal_done] to avoid granting mutation tools. Omitted or null permits all bridge tools; [] permits none. A call through codesense_call_tool requires both its own name and the target name enabled. agent_preview shows the effective tools and warns about unknown names or missing completion/inbox tools. See MCP access per agent. This restriction is currently local: remote saved-agent preparation refuses any explicit list, including [], rather than dropping it. Preview warns about the limitation. Omitted or null keeps unrestricted remote behavior.

Full example — sprint-reporter

An agent that walks every open session once an hour and posts a digest card to the human's inbox. Zero filesystem writes, zero external MCP, nothing to spill. 

id: sprint-reporter
name: Sprint reporter
description: Hourly digest of open sessions and inbox state to the human.
runtime: claude
launch: headless
startup:
  - CLAUDE.md
  - .claude/skills/sprint-report/
permissions:
  claude:
    allow: [Read, Grep, Glob, "mcp__codesense__*"]
    deny:  [Edit, Write, Bash]
default_prompt: /sprint-report
revision: 1

The tools you'll actually reach for

Tool What it does
describe_setup What the user has today — orgs, teams, source repos, machines.
list_sessions Open sessions with state, progress, unread mail.
agent_list Every agent the active team can see.
send_message Post a card to an inbox — human, role, or named session.
read_rendered_document See a doc as a reader sees it, not raw HTML / markdown.

who_am_i This session's handle — useful for self-referential digests.

See mcp-explorer for the full catalog; filter by read-only to find the ones safe to pair with a deny: [Edit, Write, Bash] posture.

What it won't do

  • Write code. No Edit / Write / Bash. If the agent has to change a file in the user's source tree, it's not MCP-only — it's a builder (see builder role).
  • Talk to Slack, GitHub, or any outside service. Those need their own MCP server listed on mcp.servers. MCP-only means CodeSense bridge only.
  • Run a shell. No tests, no linters, no git. Point the agent at a builder with send_message instead.
  • Author its own skills. The agent can't write files, so skills have to arrive the usual way — committed by a human or a builder to the team's content.

Tool reference

Reference for the tools an agent uses to ask the human, report progress and results, finish, hand off, spawn workers and read usage. Where a tool takes sessionId to identify the caller, identity comes from the verified MCP connection; a supplied sessionId must name the caller itself, and an unbound caller is refused (start the CLI in a CodeSense terminal). Three tools below are exceptions: in dismiss_agent_mark, session_usage and session_read, sessionId names a target session, not the caller.

Talking to the user

ask_user

Asks the human a blocking question through the CodeSense UI and waits for the answer. Inputs: sessionId and question; optional options (discrete choices) and category/stakes triage hints, which are never used to auto-answer. Returns {action, content} where action is accept (content is the answer), decline, cancel (dismissed, timed out or the session died) or handled (the human settled it outside the question: check the current state before acting). Always branch on action. Contrast post_agent_message, which is fire-and-forget.

{
  "tool": "ask_user",
  "arguments": {
    "sessionId": "<your $CODESENSE_TAB_SESSION_ID>",
    "question": "Which branch should the docs change target?",
    "options": [
      "main",
      "release"
    ]
  }
}

post_agent_message

Posts a progress note to the chat surface bound to your session and to the agent-updates store that dashboards read through codesense.updates(). Notes do not appear in the native human Inbox; to report there, use send_message to human with kind update. Fire-and-forget. Inputs: sessionId, text; optional role (default agent), subclass (review, research, impl or planning) and hasArtifacts: true after report_artifact for better routing, and openDocPath, the absolute context-repo path to open in the viewer.

{
  "tool": "post_agent_message",
  "arguments": {
    "sessionId": "<your $CODESENSE_TAB_SESSION_ID>",
    "text": "Draft of the reference page is ready for review"
  }
}

signal_progress

Reports where in the run you are, mid-task, so dashboards show live per-story progress. Call it repeatedly; contrast signal_done, your final act. phase is planning, dev, review, pr, blocked (call it whenever you stop to wait on the human) or done. Optional step/total drive an N-of-M sub-bar, and note is a short line. Fire-and-forget.

{
  "tool": "signal_progress",
  "arguments": {
    "sessionId": "<your $CODESENSE_TAB_SESSION_ID>",
    "phase": "dev",
    "step": 2,
    "total": 5,
    "note": "Writing examples"
  }
}

signal_done

Reports that your managed task is finished, as your final act. status is success, failed or needs-attention. CodeSense records the outcome and notifies watchers; it does not run tests, validate, or move the story's status. Without it the session is flagged needs-attention. needs-attention records a completed outcome; it does not mean a permission prompt. Optional summary, requestId (a retry key; reuse it after a disconnect) and doneRecord ({dispatchId, leg1Source, leg2Footprint, leg3Packet}, the Weft three-leg verify payload). A routine run is the exception: its task decides whether to call it, and routine_done finishes one routine run without ending the session. Returns {recorded}.

{
  "tool": "signal_done",
  "arguments": {
    "status": "success",
    "summary": "Reference page written and validated"
  }
}

Evidence, usage and Weft workers

report_step_result

Records what a step produced and touched so a reviewer can reconstruct the run without reading the transcript. Repeatable: later reports accumulate, summary and outputs are latest-wins and footprint is union-deduplicated. Optional nodeId (default: your agent node), summary, outputs ([{key, value}], value any JSON) and footprint ([{kind, reference, change?}], kind file, pr or entity, change created or modified). Values are scrubbed and size-bounded. Returns {recorded}, which is false (not an error) for a session with no run. Distinct from signal_done and post_agent_message.

{
  "tool": "report_step_result",
  "arguments": {
    "sessionId": "<your $CODESENSE_TAB_SESSION_ID>",
    "summary": "Wrote the page",
    "outputs": [
      {
        "key": "pages",
        "value": 1
      }
    ],
    "footprint": [
      {
        "kind": "file",
        "reference": "docs/guide.md",
        "change": "created"
      }
    ]
  }
}

report_artifact

Records one named artifact the step produced, so it appears in the run's result view with a stable reference. Inputs: sessionId, kind (file, pr or entity) and reference (a repo-relative path, a PR/MR URL or an entity id); optional nodeId and label. Call it once per artifact; report_step_result records several things at once. Returns {recorded}, false for a session with no run.

{
  "tool": "report_artifact",
  "arguments": {
    "sessionId": "<your $CODESENSE_TAB_SESSION_ID>",
    "kind": "pr",
    "reference": "https://github.com/acme/app/pull/1",
    "label": "Docs PR"
  }
}

dismiss_agent_mark

Dismisses the current crash or failure mark for a visible session. sessionId names that failed target session, not the caller, and crashId comes from the same list_sessions row. The dismissal persists across restart and never dismisses a later crash. It needs no confirmation or ownership.

{
  "tool": "dismiss_agent_mark",
  "arguments": {
    "sessionId": "<sessionId from the failed session's list_sessions row>",
    "crashId": "<crashId from the same row>"
  }
}

story_changes — what a story changed

Call story_changes({storyId: "DEMO-29"}), or from a page await codesense.storyChanges({storyId: "DEMO-29"}). Both read the same backend. The page gets every array in full: all linked sessions in the session_read shape without conversation, each once with basis: exact; tasks oldest first with review task ids and the same outcome as task_read; and totals.

The MCP answer is that read shaped for an agent, and stays under 64 KB. Sessions are summaries (sessionId, nativeSessionIds, basis, agent, cli, model, branch, worktree, timing, costUsd, costReason) unless you pass include: ["sessions.full"]; tasks are summaries (taskId, parentId, taskType, status, goal cut to 200 characters with goalTruncated, mainSkill, createdAtMs, closedAtMs, reviews) unless you pass include: ["tasks.full"]. Every array pages by limit (default 20, at most 500), and pages.<array> gives {total, truncated, cursor}. Pass a page's cursor with the same storyId for that array's next page; that read returns only that array, the others empty. Commits keep nextCursor. prs[].files and commits[].files list 20 with filesTotal when cut; actual pages every file. When the answer would pass 64 KB, the heaviest array ends its page early and its cursor resumes at the first row left out. Totals always cover the full set.

totals contains sessions, costUsd, wallMs, activeMs, idleMs, reviewRounds, reviewTasks, commits, files. Wall time spans the earliest observed session start to the latest observed end; active and idle time sum each session, including overlapping sessions. Time is milliseconds. Missing timing has an explicit reason and covers only observed sessions. No observed timing gives null totals. An empty story has zero sessions and time, and null cost. Cost is null with unavailable.costUsd when any session has unknown cost: a partial sum is never called the total. reviewRounds counts the story's complete review-rounds markers of phase: review (every stamp present or named in stampNote; the rule is check_records.py review_rounds()), so document, design and human-lens review rounds count too, while wave and use observations (round 0) never do; it is null with unavailable.reviewRounds when the markers cannot be read. reviewTasks counts distinct review tasks (cost and time). When no task is typed as a review, it counts the distinct tasks the review-rounds markers name (warnings.reviewTasks says so), and is null with unavailable.reviewTasks when rounds are recorded but name no task; it is never a 0 that recorded rounds contradict. When the two disagree, warnings.reviewRounds says how; it is never a gate.

Durable story links survive worktree removal and restart. Line tracking installs automatically on macOS with Apple silicon; a session launched while installation is running needs to relaunch for capture. Launch capture must have recorded the link. branches and worktrees preserve recorded links even after worktree removal; absent refs carry reasons. commits gives sha, subject, author, authoredAt (epoch ms), files, sessionIds and basis (exact with git-ai notes, associated when absent; unknown with an unavailable reason when note objects are not local). Merges on origin's default branch (refs/remotes/origin/HEAD, else origin/main or origin/master) identify PR numbers and merged SHAs within scanLimit: 2000 first-parent commits; what the checkout has checked out never matters. A merge links to a story branch when its subject names the branch, or when its second parent is the live head of one of the story's branches or one of its recorded tips (each story worktree's branch head, kept per story at agent launch, at a trail read, at close and before removal, apart from the worktree's record), so a custom merge subject or a deleted branch, worktree and record still link (basis: exact). A subject naming another branch (GitHub's from owner/branch, git's Merge branch 'b' or Merge remote-tracking branch 'origin/b') wins; a merge whose tip is also another story's branch head is not linked by its tip, for either story, and unavailable.prs says so. A tip found only by branch naming convention is associated; a recorded tip is exact. A two-parent merge under the story's squash-style title (STORY: title (#N)) whose second parent is no tip is reported as source: merge-commit, branch: null, and its M^1..M^2 commits are read. The PR number is the subject's #N, else a local PR head ref (refs/remotes/pr/N, refs/pull/N/head) at the second parent, else null with numberReason. prs lists every matching PR in that scan, newest first: {number, url/urlReason, mergedAt/mergedAtReason, mergedSha, source, branch}. Merge subjects name an exact branch; each branch lists its PR numbers in prs and current availability: local|remote|missing. Repeated merge ranges and later live commits are combined. Recorded/live-index branch and worktree links carry basis: exact; convention-only branches carry associated. Merge PRs inherit their branch basis; squash PRs are associated. Squash subjects give a story-only PR (source: squash-subject, branch: null, commits: {unavailable: "squash-merged"}); they never claim a later missing branch. Squashes report squash-merged; open PR lookup needs GitHub and is unavailable here. Nothing calls GitHub. Reads use local history only, with one exception: opening the trail of a landed story (status: done or merged, any case) whose merge is missing here (the scan stopped at a shallow boundary, or no merge was found) fetches origin, bounded at 10 seconds across all its checkouts; if that fails, unavailable.historyFetch says why and the trail answers from what is local. A fetch that fully landed and still found no merge is not repeated until origin's head moves (through refresh_history or an attach); until then unavailable.historyFetch is already fetched at this origin head; call refresh_history. A failed fetch is tried again on the next open. A story still in progress never fetches: it reads its branch, and when the scan reached the boundary with merges seen or no branch here, it gets the shallow reason too. When the scan found some merges but reached the boundary, the reason is history past shallow boundary; older merges may be missing; call refresh_history. historyAsOf gives {fetchedAt, originHead}. History cut off by a shallow copy reports history past shallow boundary; call refresh_history. On the page, limit pages commits only, defaults to 100 and caps at 500; pass cursor: result.nextCursor with the same storyId to continue. Stale cursors are refused. total and commit totals cover all discovered commits across pages; the file total also includes selected landed-diff paths. planned lists backtick paths from Touchpoints, stripping line suffixes; directories and globs match descendants. plannedBase is only an explicit Paths are under `X/` declaration, otherwise null. Tokens keep their original spelling and match either root-relative or with that declared base. The declaration is metadata, not a broad touchpoint. Decisions may use that same explicit base-relative file name; dated Decisions headings are accepted. actual lists path, inPlanned, area (first two path segments), and the first matching Decisions number; plannedUntouched lists unmatched planned tokens. Missing Touchpoints carries unavailable.planned. These are facts, with no scoring. Private MCP and page reads accept include: ["ranges"] to enrich only the current page of commits. Each commit adds ranges (path, inclusive start/end, introducing commit and the resolver’s native/session IDs, basis and reasons), rangesBasis and, when needed, rangesReason. Only newly added lines introduced by that SHA are returned; unchanged lines between hunks are excluded. No-note commits return empty ranges with unknown basis and a reason (unsupported_cli: <cli> for a commit an OpenCode or Hermes session made); merge commits return empty ranges with reason merge commit. Missing local clones, revisions, files or objects preserve the durable contribution facts with range unavailability. Missing or empty include preserves the default response. Calls use each changed file’s added-line bounding span, split into at most 2000 inclusive lines; the underlying resolver still attributes the full file internally. Use session_read for conversation and task_read for task outcomes. Each task’s outcome includes measured time, cost, reviewRounds and unavailable, using its own session or interval scope. Two subtasks sharing a session keep separate interval actuals; story totals still count the session once. Missing measurements remain null with the existing reasons. Published dashboards may declare live.queries: [storyChanges]; their projection shares session ids, models, cost, timing and task ids/reviews, alongside commit SHAs/dates, repo-relative tracked files and planned/actual facts, and PR/merged SHAs plus worktree state/basis. Published queries reject include and never expose ranges. Host paths, worktree paths, branch names, commit subjects, account data, goals and summaries stay private.

{
          "tool": "story_changes",
          "arguments": { "storyId": "DEMO-29", "limit": 50, "include": ["ranges"] }
        }

story_totals — many stories' totals in one read

Call story_totals({storyIds: ["DEMO-29", "DEMO-140"]}) (1 to 500 ids), or from a page await codesense.storyTotals({storyIds}). It answers every story's totals from the Mac's story totals index without walking git, so a Stories page reads all its rows in one or two calls instead of one story_changes per row. Each story's totals equals story_changes({storyId}).totals, and its unavailable reasons are the same, each given as an index into the answer's reasons list so 500 stories fit in one answer. Beside the totals each story has mergedAt (the latest merge time of its merged PRs, or null with mergedAtReason), prs (its newest 5 merged PRs as {number, merged}) with prsTotal, and runtimes (the ids of the CLIs that reported its sessions' usage).

A story not indexed yet answers {pending: true}: it is queued, so show it as loading and ask again; never read it as 0. indexing: {done, total} counts this scope's indexed stories while the backfill runs. refreshing: true means a commit, merge, session, task or review marker changed the story since computedAtMs; a recompute is queued and the values shown are the last computed. The index computes a story the first time it is asked for, then again after a change (after a few seconds of quiet, at most every 30 s); it computes one story at a time with a rest after each, so it never takes more than a core, and a story too large to count its lines in the background keeps its other totals with unavailable.lines (it is tried again later); branch, remote and default-branch refs of the repositories it read are checked every 15 s without fetching. A cut answer (past 240 KB) carries truncated: true and rest, the ids to ask again. Published dashboards declare live.queries: [storyTotals] with a storyTotals.storyIds pin (literals or {epic}/{team} selectors, every id must pass); they share the totals and only the reasons storyChanges publishes. A hosted ask holds only the ids that fit its 2 KB of args (about 120 to 150), so a page calls CS.storyTotals(ids) (hosted) or codesense.kit.storyTotals(ids) (in the app): both take any number of ids, ask in parts and merge one answer. When every query slot on the owner's Mac stays taken for 3 s, a hosted read answers mac_busy, and a relay with every slot taken answers rate_limited; CS.query, CS.storyTotals and the kit ask again after 1, 2, 4, 8 and 8 s.

{
          "tool": "story_totals",
          "arguments": { "storyIds": ["DEMO-29", "DEMO-140"] }
        }

session_read

Ask about one session with a CodeSense or native CLI sessionId. The id names the session being read, not the caller. A dashboard calls await codesense.sessionRead(args) with the same arguments and receives identical JSON from the same backend.

{
  "tool": "session_read",
  "arguments": {
    "sessionId": "your-session-id",
    "include": ["conversation"],
    "limit": 20
  }
}

The result joins session (the stored launch record, including its account provenance, allowed tools, provided skills, timing and unavailable reasons), nativeSessionIds, story, run, models, cost, tools, retries and unavailable. A native id and its CodeSense launch id resolve to the same answer. Usage covers every native id attributed to that launch. It adds no copy of the usage data.

  • Each model has model, calls, tokens (input, output, cacheRead, cacheWrite), costUsd, costSource and reason. Costs sum the stored calls and are never priced again from aggregate tokens.
  • cost has state, totalUsd, source and reason. Source is reported, rate_table, mixed when both contributed, or null when no call has a known source. An unpriced call makes totalUsd null with an unpriced models: … reason. No usage gives null with no usage events for this session. A real zero-token call can cost 0; unknown cost is never called free.
  • tools.allowed keeps the record's mcpAllow and effective bridgeTools with unavailable reasons. tools.used groups indexed calls by name and mcpServer, with calls, errors and errorUnknown. tools.usedState and tools.usedReason describe index availability: absent, unsupported or unavailable means used: null; present with no calls means []. Expired conversation text keeps the indexed counts and an expired state; truncated captures keep their indexed counts and a truncated state. Only a known true error flag counts as an error. Codex can leave the flag unknown: errorUnknown counts that explicitly and never treats it as success.
  • session.timing gives wallMs, activeMs, idleMs, turnCount, toolCallCount, timingSource and idleGaps with waiting reasons. Durations are milliseconds. For an open session wallMs ends at the last finished turn. retries is null with unavailable.retries: not recorded: no retry signal in the session timeline.
  • run.state is present with the existing run outcome, unlinked with a reason when there is no run, or absent with a reason when the linked run has no recorded outcome yet. Use session.runId with read_run for the transcript and output.
  • A session with usage but no durable record returns session: null with an unavailable reason. Hand-started sessions keep their unknown account/model/tool facts and their reasons. An id with neither a record nor usage is an unknown session error.

tasks contains the existing task records linked to the session, including goal, taskType, parentId and outcome/status facts, through the same task-store reader. It is [] when there are none; CodeSense and native session ids return the same tasks.

Omit include for facts only. include: ["conversation"] adds the existing conversation page unchanged: turns, nextCursor, counts, lookup, sourceFormat, truncated and unavailable metadata. State is present, truncated, absent, expired or unsupported, with a reason when there are no turns. The tool-call index survives conversation expiry.

Continue with cursor: conversation.nextCursor (a turn index), or jump with turn (zero-based) or toolUseId (the CLI-native call id). Choose only one selector. limit is 1–200 turns, default 20 for a page or 1 for a jump. Selectors and limit require the conversation include. Conversation is omitted from the response otherwise.

Read scope: this matches session_usage. Every local agent can read every session on the machine; these runtime facts are not filtered by org or team. Caller content scope only gates story-file enrichment. This tool adds no new isolation boundary.

session_usage

Reads token use and spend per agent session on this Mac and its connected machines, from each agent CLI's own reports. It is read-only and covers only sessions CodeSense launched. Optional sinceMs/untilMs (counted by whole local day; the untilMs day is excluded), sessionId (a filter for one target session, not the caller's identity), cwd (exact path), story, and limit (the most sessions returned, newest first; totals still cover all). Returns {sessions, days, totals}. costUsd is null for a model with no confirmed price, and unpricedModels names it; see model_rates and set_model_rate.

A session keeps the first stored story link. Without one, usage looks for the story worktree containing its working folder, then the story on its durable session record, with the live launch registry as a fallback. Reading a record-only story creates no link. At launch, a known worktree story takes precedence over the launch story and the link is stored even before the first usage event, so it survives closing the workspace or restarting CodeSense. An explicit story_id on open_workspace also links a team-workspace session. Without an explicit story, a worker inherits its launcher's recorded story only within the same org and team; otherwise its story stays null. An explicit story wins across teams too. The session record and task keep that launch story. A session with neither stays null: story ids are never guessed from workspace names, branches or prompt text. Routines have no launch story. An explicit story id remains linked if its scoped source is unavailable; title, status and epic are then null. A failed lookup never creates a durable link for an inherited id. Past sessions are not backfilled.

{
  "tool": "session_usage",
  "arguments": {
    "story": "DEMO-5",
    "limit": 10
  }
}

why_line: committed line attribution

Ask who introduced committed lines and inspect the linked session facts, even when your agent has no source checkout. This is read-only: CodeSense answers from the history of its bound local copy (its git common dir), with no network or fetch, whatever branch the checkout has checked out. Every local agent can read every attached repo's attribution.

Required inputs are repo (a configured slug from list_source_repos; use its host/owner/repo remote key if the name is ambiguous), path relative to that repo, and start/end. Lines are 1-based and inclusive, with end - start ≤ 2000. Optional rev accepts a local commit or ref and is honored as given. Without it, optional story picks the revision: the story's merged SHA, else its branch head (local, else origin/<branch>), else origin's default branch (origin/HEAD, which a fetch records when it is missing, else whichever of origin/main and origin/master exists; no branch name is assumed). An omitted rev never reads the checkout's HEAD; revSource says which was used (explicit, mergedSha, branch or defaultBranch). Revision and path cannot start with a dash or contain NUL.

{
  "tool": "why_line",
  "arguments": {
    "repo": "acme/api",
    "story": "DEMO-19",
    "path": "src/lib.rs",
    "start": 40,
    "end": 60
  }
}

From a dashboard, call await codesense.whyLine({repo, rev, story, path, start, end}) with the same arguments to receive identical JSON from the same backend. Published dashboards can declare the whyLine query: it shares range evidence and session ids, models, cost and timing, while omitting native session ids, records, accounts, host paths, commit subjects and conversation.

The result contains repo, rev, revSource, historyAsOf ({fetchedAt, originHead}: the last CodeSense fetch, epoch ms or null, and origin's default branch head), resolvedCommit, path, notesRef (an opaque snapshot id of the notes refs read, sense=<sha> ai=<sha>), ranges and sessions. Each range reports its introducing commit, tool, native session id, model, story id, and attribution basis:

CodeSense supplies git-ai automatically when needed. Check describe_setup.attribution for installing or install_failed before relaunching a session for capture.

A dashboard reads the same attribution and capture status with await codesense.setup(), returning {attribution}. A published dashboard declares the setup query and receives only the allow-listed fields: status kind (with a reason only if the status is off; per-launch states are on worktrees rows), git-ai version, daemon state, supported versions and the capture counters. The git-ai path, warnings and status message text stay on this Mac.

  • exact: a git-ai note records the lines, including human lines. Blame follows renamed and moved lines to their introducing commit before reading its note.
  • associated: the introducing commit has no note, but its story-prefixed squash subject or pull-request merge branch identifies a story. candidateSessions lists up to 20 sessions associated with that story; it never claims one session wrote the lines. GitHub-side squash and rebase merges can lose exact attribution. This fallback is a story association, not recovered exact evidence.
  • unknown: the lines have no readable attribution. Notes are read from refs/notes/sense (CodeSense's local notes) first, then refs/notes/ai. If the local copy has neither, every range is unknown with no git-ai notes in local copy and notesRef: null. For a repo whose notes stay local, a missing note adds "notes for this repo stay on the machine that wrote them (local-only)"; a note that does not cover a line says no attribution in note. Lines a session of a CLI CodeSense doesn't capture (OpenCode, Hermes) committed have no note by design and read as unknown with that CLI as tool and reason unsupported_cli, while a local reflog still records the commit. They are never credited to a person; while a local reflog records the commit they are also never associated with a story.

An exact agent range is linked when its native id resolves to a durable CodeSense record. Its sessionId keys one facts-only session_read result in sessions, shared by all ranges from that session. This includes models, tools, account, cost, story and run facts, without conversation text. Otherwise sessionId is null and link is unlinked, with no session record (hand-started or older session), human, or no native session id in note. Unknown and associated ranges retain their basis-specific explanation.

Unavailable reads return {status: "unavailable", reason}: no local copy, revision not in local copy, path not in revision, objects not in local copy (including missing promised objects in a partial clone), notes changed during read after bounded retries, origin default branch not known locally; call refresh_history (no origin/HEAD, origin/main or origin/master here), or history past shallow boundary; call refresh_history (a story with no branch whose merge lies past the boundary). An explicit rev that is not here is revision not in local copy. In a shallow copy, ranges that blame folds into a boundary commit are unknown with that same reason. The reader never fetches missing commits, blobs or notes.

refresh_history: fetch an attached checkout's history

Reads never touch the network. When history is missing, call refresh_history({repo, storyId?, timeoutMs?}) (an MCP tool; pages have no verb for it). It runs git fetch origin into refs/remotes/origin/* only (no tags, notes or local branches; the working tree, index and HEAD are untouched) and sets a missing origin/HEAD from origin. With the storyId of a landed story, a shallow copy deepens only until that story's merge scan (2000 first-parent commits) is inside the boundary, then unshallows if that was not enough; for a story still in progress it is a plain fetch. timeoutMs bounds the call (default 60000, from 1000 to 300000). When the first fetch landed but a deepen did not, the answer has status: "partial" with the reason, and fetchedAt is recorded. It never prompts: terminal and askpass prompts are off and ssh runs in batch mode (added to GIT_SSH_COMMAND or core.sshCommand; a GIT_SSH program is left as you set it), while your credential helper still answers. It returns {repo, historyAsOf, shallow, deepened}, or {status: "unavailable", reason} with fetch needs credentials, fetch skipped, repo busy (another git command holds a lock; there is no retry), fetch timed out or fetch failed. CodeSense also fetches once, in the background, when you attach a checkout.

{
  "tool": "refresh_history",
  "arguments": {
    "repo": "acme/api",
    "storyId": "DEMO-19"
  }
}

A linked exact agent range can carry turn: {sessionId, toolUseId, turn, basis, taskId, taskBasis, reason?}, where the inner turn is the zero-based conversation index that session_read {turn} and {toolUseId} page by (never the prompt-turn count). basis: "edit" is the call of the recorded edit, from the git-ai trace and the conversation index; it does not load conversation text. A Codex exec-… file-change id resolves to the enclosing call_…, and session_read {toolUseId: "exec-…"} jumps there too. taskId is the innermost sub-task (task_start) of the session whose interval holds the call's time (taskBasis: "interval"), else the session's own task ("session"); an open sub-task ends at the next sibling task_start (same parent) in the session, else at the session's end. Trace ids stay internal. If no edit mapping is available, the range has unavailable.turn and turn: null unless the commit turn below applies: checkpoint log not available (pruned, another machine, or before capture) when no live or archive directory was ever seen for the commit, edit not recorded by git-ai when one was seen but holds no record of the edit, or ambiguous turn link for conflicting mappings. For edit not recorded by git-ai, turn may be the commit's turn with basis: "commit": the linked session's last Bash, exec, exec_command or shell call at or before the committer time that started at most 10 minutes before it, and only when that time lies inside the session's observed span; otherwise turn stays null. A commit turn is never the edit turn. Other ranges do not carry unavailable.turn. story_changes {include: ["ranges"]} and the dashboard whyLine return the same turn objects.

A known tool id without a conversation index keeps its pointer with turn: null and reason: "conversation not captured". An expired conversation keeps its numeric index with reason: "conversation expired". When truncation dropped the pointed turn's text, its index is retained with reason: "conversation text truncated"; a turn whose text was retained has no truncation reason.

At startup, CodeSense sweeps retained completed checkpoint archives and live logs for attached clones whose attribution setting enables capture. Exact agent queries remain the on-demand reconciliation path, including warm raw-cache reads: they inspect the introducing commits and their parents and resume appended logs; unchanged logs need no content read. Stored trace and Claude s_ identities survive a store reopen and later log deletion. Logs pruned before a startup sweep or eligible query cannot be recovered; no retention interval is assumed. Capture runs at startup, on completed archive events while the app is open, and on demand. The coverage caveat is: directory label = base, mapping inferred, unverified without a binary. Inspect describe_setup.attribution.capture for the last sweep's counters and error; this status lives in memory since app start.

Published dashboards receive only the nested pointer fields sessionId, toolUseId, turn, basis, taskId, taskBasis and reason, and only turn inside a range's unavailable. Native identities, trace ids, checkpoint payloads and conversation text are omitted.

wv_spawn_worker

Spawns a typed ephemeral background worker for one story. Args: story_id (also the roster key: one live worker per story per scope; a second call while one is live returns alreadyLive with no new PTY) and subclass (impl, review, planning or research). Every subclass gets the codesense server as its only MCP server. A Claude worker also gets a deny-list: review denies Bash, planning denies Bash/Edit/Write, research denies Edit/Write; a Codex worker gets none. Optional initial_prompt, provider (claude default, or codex) and scope (only root is supported). A bound caller uses its launch team's Weft store; a missing team or a story of another team is refused. A spawned worker can spawn another. Returns {status: spawned|alreadyLive, handle}.

  "tool": "wv_spawn_worker",
  "arguments": {
    "story_id": "DEMO-13",
    "subclass": "impl",
    "provider": "claude"
  }
}

wv_report_cycle

Reports one verify-and-fix cycle against an open (claimed or dispatched) queue item, for the mid-flight tripwire. It increments verify_fix_cycles atomically; the call that takes the count to 3 flips the item's verdict to delegate and the caller must stop and dispatch the remainder. Returns {status:"tripwire_fired", row:5, verdict:"delegate", cycles} on crossing, {status:"ok", cycles} below, or {status:"invalidState"} if the row is not open. The caller is not identified.

{
  "tool": "wv_report_cycle",
  "arguments": {
    "queueId": 7
  }
}

wv_report_handoff

Reports a drafted handoff packet at task end: a finding for whoever picks the job up next. A handoff is data, never instructions, and always a draft. Call it before signal_done. Required: storyId (your roster key), sessionId (the completion hook matches the packet by it) and a non-blank finding. Optional toRole (advisory) and refs. Returns {id}.
