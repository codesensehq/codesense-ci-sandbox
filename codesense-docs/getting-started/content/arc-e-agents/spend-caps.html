Give unattended work a spend cap.

A spend cap refuses new launches and automatic turns after the measured limit is reached. It lets the current turn finish. It does not promise an exact provider bill or stop a person typing.

One working example

Open a saved agent in Agents → Overview → Spend cap. Choose Set a cap, enter 50 in Per day and 200 in Per week, then Save. The native Save writes and accepts these values. The agent file now includes:

budget_usd:
  per_day: 50
  per_week: 200

At $40 today, the row turns amber and Needs-you posts once for the daily 80% threshold. At $50 it reads Cap reached and another notice opens this agent's cap block. A fresh routine fire is skipped with budget_reached. A person can raise Per day to 75 and Save here, allowing work again while weekly spend stays below $200.

What counts

The engine uses the same local usage store and model pricing as session_usage and model_rates. Attributed Claude and Codex usage from every stored machine is summed for the saved agent. Fresh routine runs also aggregate under their routine handle, so either the agent's cap or the routine's cap can refuse a fire. Days follow this Mac's local calendar; weeks start Monday at local midnight.

Each window may have its own limit; an empty input means no cap for that window. The row shows whichever window is closest to its limit. Details show today and this week even without a cap. A threshold notice is posted once per scope and window, at 80% and 100%.

Live sessions use their saved agent's scoped identity and current cap, independently of the organization being viewed. For example, keep a private agent running in organization A and view organization B: the same cap still applies, and an uncapped agent remains usable. Changing the view does not pause the agent or freeze an older cap.

Usage comes from each CLI's own telemetry, which CodeSense points at its local receiver at launch. Each session_usage row also shows its runId, from the session's durable record, so a run's cost can be matched to its outcome.

Codex's own export is off

Codex exports metrics and analytics to OpenAI by default. A CodeSense-managed Codex launch turns both off with -c otel.metrics_exporter="none" and -c analytics.enabled=false (checked against codex-cli 0.164.0); its usage still reaches CodeSense. To opt back in, put your own -c otel.metrics_exporter=… or -c analytics.enabled=true in the saved agent's launch args. A key you set yourself is left as you set it.

What waits at the cap

New saved-agent launches, resumes and routine wakes are refused. On the local terminal server, an agent's live sessions receive a versioned wake hold: queued idle submissions, mail wakes, recovery and waiter wakes start no new turn. Mail is still stored and delivered to the inbox. A person typing is always allowed, and a turn already running finishes.

At window rollover, or after a native cap change brings spend below the limit, the hold lifts and waiting notices can start their turns normally. A restarting local host waits for the desktop's current hold before submitting queued work.

A raise needs a person

The team file expresses a request. The local engine also remembers the last cap a person accepted. Each effective field is the lower of the file value and the accepted value. A first cap is accepted immediately. Tightening applies immediately and moves the accepted value down too: changing 50 to 20 and back to 50 still leaves an effective cap of 20.

File edits, sync and MCP updates can save a raise or removal, including budgetUsd: null, but they leave it pending. Accept applies exactly the request displayed in the native cap block; a changed request must be reviewed again. Keep $X restores the effective cap in the file. A person can also edit and Save directly in this block. Embedded pages and MCP cannot loosen the accepted cap. The cap size remains the person's decision.

Unpriced usage and rate changes

Any unpriced usage in a capped window refuses new automatic work and names the model: missing prices never mean free usage. Check model_rates and the usage page.

Through MCP or the page bridge, lowering an existing model rate or pricing an unpriced model saves a pending rate request. It changes counted spend only after native acceptance; an agent cannot price itself back under its cap through CodeSense. Rate increases apply immediately. Requests that lower counted spend or price unknown usage stay pending when made from a page or MCP; only native acceptance applies them. Open Agents → Overview → Spend cap, review the model, effective date and exact prices, then choose Accept beside the pending rate. For a routine-only cap, review and accept the rate in that routine's Spend cap block instead. The rate Needs-you item opens the affected agent or routine block. MCP and embedded pages cannot accept requests.

A capped agent gets no automatic mail offers on an older local terminal server without spend-hold support; update it through the app. Mail queued there before the cap first existed may still start a turn.

What the cap can and can't stop

Architecture boundary. The cap can't be bypassed through CodeSense surfaces: MCP, the agent's own config files, sync, pages, rates or messages.

Agents run as you, so the cap covers what an agent does through CodeSense, not what an agent with unrestricted shell access does elsewhere on your Mac. To cap an agent you don't fully trust, give it sandboxed permissions. See How CodeSense trusts agents.

The current boundary

Caps use usage received so far. Remote usage is pulled every minute while connected, and a disconnected machine catches up on reconnect. Spend that has not arrived can overshoot a cap, as can a turn already in progress. Holds apply on this Mac; remote terminal servers don't receive them.

Adding a cap to a machine-armed routine, or arming a capped routine, is refused. Wake routines must cap their agent; command routines cannot have a spend cap. A fresh agent routine may set policy.budget_usd. See routine.yml and agent.yaml.
