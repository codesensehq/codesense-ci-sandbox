Shape a seat around its job.

This is the appendix to the agent-design guide. Choose a small context, the tools the job needs, and a clear handoff. One agent can cover several seats when the work is small.

Six useful starting seats

SeatContext and taskDefault and trade-off
TriagerSelected inbox sources. Classify, summarize and route.Read sources; send bounded handoffs. Broad access makes triage easier but increases exposure.
BuilderOne assignment, acceptance criteria and its workspace.Allow the project's build and test tools. Keep scope small; ask before release actions.
ReviewerOne artifact, its diff, acceptance criteria and evidence.Report reproducible defects or green. Independent context costs another pass but reduces shared assumptions.
ScoutOne source and one output.Use a command when the check is fixed. Use a model only for judgment.
ResolverThe decision, alternatives and relevant constraints.Work with a person when goals conflict. Do not turn ambiguity into silent policy.
AnalystSelected sources and a bounded question.Cite evidence and uncertainty. More sources can help; prune irrelevant material.

The solo-founder starter has copyable planner, builder and reviewer YAML with self-contained prompts. It needs no separately installed slash command or workflow skill.

Isolate launch settings

A saved agent chooses runtime, args, env, startup, context, mcp.servers and native permissions. Environment values must be strings and are visible to anyone who reads the definition. Never put credentials in them.

Each launch receives its own generated permission settings. Agents sharing a folder do not share those settings. CodeSense-owned launch variables take precedence. A launched agent's PATH is your login shell's PATH, with CodeSense's own tools first. This is launch configuration, not isolation of data or a substitute for the CLI sandbox.

startup: [] and context: [] request no content from those lists. Omitted context uses runtime defaults. Preview the resolved files; do not assume an empty list removes files already present in the workspace. Add only paths that exist in the user's content.

See agent.yaml and the context resolver. Test permission choices at launch. A prompt saying “review only” does not prevent writes.

Roles carry durable work

A role is a queue address; an agent is a launch definition; a session does the work. Save role settings with role_save. A default handler names an agent but does not start it automatically.

A worker calls register_role with its own session id and chosen shared or exclusive mode. Use the returned instance and generation to claim with claim_role_messages, accept with accept_role_message, and acknowledge handled work with ack_role_message and its receipt. See the manager recipe.

Use send_role_message for durable work and reply for an existing thread. Direct messages use current session handles from list_sessions. The launch's role label is display-only; queue_role chooses a queue at launch.

Start fixed work without a model

For a known metadata transition, use a metadata trigger. For a fixed check, use routine_create with action: "command" and a command argv array. A second routine can use after to follow a successful or finished run. See triggers.

role_pending is available through MCP events and YAML. Omit role to hear every queue in reach, or set role:"reviewer" for reviewer mail only. A team routine watches its own team. The wildcard starter inspects {{trigger.role}} to decide what to do. A queued message alone does not launch its handler. The starter shows a wake routine and explicit worker launches.

Preview agents, dry-run routine creation, then save routines disabled. Enable only after approval. Check actual outcomes and the visible app state. Choose intervals and handoff rules with the user.
