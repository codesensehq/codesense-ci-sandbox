Optional spend cap

budget_usd: {per_day: 50, per_week: 200} sets positive finite USD limits. Either field may be omitted. Spend is shared across this saved agent's sessions and machines, using local calendar days and Monday weeks. Lower values apply immediately and ratchet the locally accepted cap down. A raise or removal in this file or through MCP stays pending until a person accepts it in the native app. MCP spells the field budgetUsd, with perDay and perWeek.

Caps count recorded usage. When this Mac's managed Claude settings send Claude's usage to your organization's own collector, a Claude agent's cap counts usage from Claude's session log instead, which appears when each turn ends.

Usage exporter settings are engine-owned for every launch: saved OTEL_* and telemetry enable/disable environment variables are refused with a message naming the variable. CodeSense also forces its exporter endpoint and enable settings at launch.

These settings cover launches through CodeSense. Agents run as you; give an agent you don't fully trust sandboxed permissions. See Spend caps: Architecture boundary and How CodeSense trusts agents.

See Spend caps for counting, wake holds and acceptance.

Every agent you can see — the six starters (builtin/claude, builtin/codex, builtin/opencode and their -unattended twins), your team agents, your Only-me ones — is this one file, kept at config/agents/<id>/agent.yaml (the starters live in the app, not on disk). You rarely open it by hand: the agent_preview and agent_create MCP tools take the same fields and refuse anything the file would refuse. The table below is the whole shape, straight from the Rust validator. Where a value is normalized on save ("whitespace-trimmed", "no duplicates"), that normalization is what the preview also returns.

Hermes (preview)

Hermes support is a preview: it is not yet available for saved agents or launches, and the setup below stays inactive until it is.

The prepared integration uses runtime: hermes, with builtin/hermes and builtin/hermes-unattended templates, selected context and a private per-session home. The unattended template passes Hermes's --yolo flag.

Install the pinned Hermes Agent v0.22.5 source release (commit bf0203a794a07aac3ff764972ab9087baa4e4f4e) following its upstream instructions. Keep hermes on PATH. CodeSense does not install it.

Before launch, set a keyless local OpenAI-compatible endpoint and model in Edit → Runs on. These non-secret selectors are saved with this agent as startup_settings.model (provider: custom, base_url on loopback, and default for the model). A selected startup config.yaml also works; inline settings override it, and explicit --model args win. A starter without a model endpoint is blocked before launch.

Remote launch, activity and automatic inbox delivery, usage, permission and headless integration, and accounts are not part of the preview. Inbox mail waits for the agent's next turn; the preview does not show Ready or a waiter. Hand-typed hermes stays unmanaged.

OpenCode permissions

With runtime: opencode, permissions.opencode is the permission config. Its one supported key is permission: a map from a tool pattern (an OpenCode tool name or glob; CodeSense MCP tools appear as codesense_<tool>) to ask, allow or deny. A decision outside those three is rejected when the agent is saved, and so is any other key under the OpenCode block. A permissions.opencode block on an agent with a different runtime is not checked and is kept untouched.

CodeSense converts the map into OpenCode 2's ordered permissions rules in OPENCODE_CONFIG_CONTENT, alongside the launch's MCP configuration. More specific rules follow the default rule, and the last matching rule wins. CodeSense adds a rule only where you set none for that pattern: "*": ask on a foreground launch (a headless one differs, below); allow for its lifecycle tools (codesense_who_am_i, codesense_list_sessions, codesense_signal_progress, codesense_signal_done, codesense_ask_user, codesense_post_agent_message, codesense_read_messages, codesense_reply); and, only when mcp.bridge_tools is declared, "codesense_*": deny, with an allow for each listed tool. With bridge_tools omitted or null, CodeSense tools follow *.

A headless launch (a routine run with no tab) starts from a different base, because opencode run answers the first ask by rejecting it and stopping with no answer: "*": deny, allow for read, glob, grep, list and todowrite, and external_directory: deny, beside the CodeSense allows above. A tool the map denies does not park or empty the run: the denied call ends in an error turn, which shows in the run's turns, and the run goes on. Your own permission map still wins, key by key: set shell: allow to let a routine agent run shell commands. A foreground launch keeps "*": ask. For an OpenCode agent that routines run, set a short max_runtime on the routine (30m suggested): a provider 5xx retries silently until it.

Unattended OpenCode. The OpenCode unattended starter keeps --auto. An escalating agent (--auto in its args, or an all-allow permission map) gets an "*": allow base on a headless launch instead of the deny base, because --auto alone does not override a deny. The CodeSense allows still apply and your own keys still win, so an escalating agent with shell: deny keeps shell commands denied. Such an agent can run any tool, so pair it with a sandbox. Each of its routines still needs a short policy.max_runtime (30m suggested). 

runtime: opencode
permissions:
  opencode:
    permission:
      "*": ask
      shell: allow

OpenCode activity

An OpenCode tab shows Working, Ready, Needs approval and Working · N subagents like a Claude or Codex tab. CodeSense lists its own plugin directory, ~/.codesense/opencode/, in the inline plugins config of every OpenCode it launches, using its server.js entrypoint, saved agent or typed in a CodeSense terminal (unless you set OPENCODE_CONFIG_CONTENT yourself). The plugin tells CodeSense when a session starts, a prompt is sent, a tool runs, OpenCode asks for permission or puts a question to you, a session goes idle or errors, a compaction runs, and when a subagent starts or goes idle. It sends only ids, tool names and an error kind: never prompt text, tool arguments or output, or permission patterns. CodeSense rewrites the file when it updates and never touches the plugins in your own OpenCode config. Managed launches use --standalone, so their private server receives the tab's context, tools and activity settings.

If one of your own OpenCode plugins also reports activity to CodeSense, remove that duplicate integration so the tab is not told twice.

OpenCode usage and cost

An OpenCode session launched by CodeSense shows in session_usage with cli: "opencode", and its spend counts toward the agent's spend cap like a Claude or Codex session. The same plugin reports each finished assistant message once: its model and token counts (input, output including reasoning, cache reads and writes) and the cost OpenCode itself worked out. It sends no prompt text or output.

The cost is OpenCode's price for the model, not what you were billed. On an OpenCode Go subscription it is a notional price: the subscription's flat fee is not in it. When OpenCode reports no cost for a call, CodeSense prices it from the model rates on file (model_rates), seeded with the OpenCode Zen list prices for the common Go and Zen models. Allowance windows are not shown.

OpenCode inbox

New mail reaches an OpenCode agent the same way as a Claude one: an idle agent wakes to a short notice, and a working one hears it at its next queued turn. The same CodeSense plugin does it. It waits for mail from the tab's CodeSense host, and when mail arrives it queues the notice through OpenCode's native session.prompt API for its main session, confirming delivery only after OpenCode returns the accepted inbox item. Nothing is typed into the terminal, so a draft you have half written stays as it is. The notice only says you have mail; the agent reads it with read_messages. list_sessions shows inboxWaiter: true while the plugin is waiting, and false if the plugin did not load, the agent has exited or it is a one-shot opencode run. Subagent sessions never wait. A session restored with --continue or --session starts waiting at boot, and cancelling a turn that mail started leaves it waiting. Deleting the conversation a tab follows retires its waiter. Mail counts as delivered only once OpenCode has taken the notice, so a notice that had nowhere to go (a deleted conversation, a refusal, OpenCode quitting) stays unread and reaches the next conversation you work in. The plugin works out whether OpenCode was started to resume a session, or as a one-shot run, from OpenCode’s own command line, so those checks are tied to the OpenCode versions CodeSense qualifies and are rechecked when it qualifies a new release.

OpenCode version support

The CodeSense plugin relies on events and hooks of the OpenCode releases it was checked against (2.1.4 and newer 2.x). CodeSense uses the native OpenCode 2 API; a 1.x install needs updating. The dependency check requires at least 2.1. A release outside the qualified range (for example 3.x) still starts, but says so first: the launch preview, the launch itself, agent_get and agent_preview carry a warning with the code cli_version_unqualified that names the version found and the supported range, and the CLI's row in Settings shows “Not a supported version”. The same warning appears for Claude and Codex releases outside their ranges, and nothing is refused because of it.

For OpenCode the plugin is also left out of a managed launch of an unsupported release, and a typed OpenCode's plugin checks its host at start and disables itself with one log line. Either way the tab shows no activity or usage, and list_sessions shows inboxWaiter: false, instead of a status that is not true. Settings and get_viewer_state report each CLI's qualified (true, false, or null when its version cannot be read) and supported range.

A saved-agent session started on such a release says so on its list_sessions row, and the Agents list shows “Limited” where it would show “Ready”, with the same note as its tooltip: 

{
  "handle": "_worker/acme/app/t1/oc1",
  "state": "idle",
  "inboxWaiter": false,
  "releaseQualified": false,
  "releaseNote": "This CLI version (3.0.1) isn't supported yet (supported: OpenCode 2.1.4 or a newer 2.x release). Status, inbox wake and usage may not work."
}

releaseQualified is only ever false, and releaseNote comes with it. Both are absent when the release is qualified or not known: a CLI typed into a plain tab records no version, so it has no flag and keeps its normal status. Absent therefore means “nothing is known to be wrong”, not “verified supported”. Read state and inboxWaiter as before; the flag adds the reason.

A newer OpenCode release is supported once every event, hook and client call in the plugin's contract.json has been checked against it and the OpenCode adapter's version range is widened.

What breaks a save

A validation error is {ok: false, error: {code: "invalid", message, field}} and writes nothing. The field names exactly where to fix it. The common ones:

  • id — doesn't match [a-z0-9][a-z0-9-]{0,63}.
  • runtime — not claude, codex or opencode (and no sessionId to infer from).
  • args[n] — contains shell syntax (pipe, redirect, quote), NUL, or an empty string.
  • mcp.servers[n] — codesense (the bridge), a duplicate, empty, or NUL.
  • startup[n] — absolute path, .., a glob, inside a reserved top-level dir, or overlaps an earlier entry.
  • permissions.<runtime>.<key> — a key the runtime doesn't have.
  • revision — < 1, or (on update) doesn't match baseRevision → conflict.

Anything that isn't an error but looks off comes back in warnings and manifest: a huge startup entry or binary files in a directory, a /name the agent doesn't start with, permissions that would block CodeSense's own tools. CodeSense never caps or edits what you asked for; the user decides.

Codex hooks and trust under CodeSense

A project or team .codex/hooks.json hook is untrusted until Codex records its hash. An untrusted hook puts a Hooks need review screen in front of the TUI, and Codex records "Trust all and continue" in its own config.toml. CodeSense keeps that write working: a scoped launch hands Codex one mcp_servers override that switches off every server the Codex home already lists and adds only the ones the agent selected. Each switched-off entry still names a complete server of its own type (a no-op command for a stdio server, a dead local url for a remote one), because Codex validates the merged configuration on every write, and an entry with no transport fails it with invalid transport in mcp_servers.<name>. The placeholder never carries the server's real args, url, working directory or env: those would land in the process list.

  • Trust a project hook once, from a CodeSense launch. It then stays trusted across relaunches (the override is not saved into config.toml).
  • An unattended agent cannot answer the review screen. Trust the hooks before the agent runs unattended, or leave them out of that agent's project.
  • Hooks CodeSense generates itself (its activity observers) are trusted by CodeSense and never prompt.
