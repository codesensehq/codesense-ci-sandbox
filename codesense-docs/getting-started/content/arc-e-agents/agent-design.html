Agent design: start with the work.

Decide what your agents should do, what they may touch, and how you will know they helped. Start with one seat. Add more when the work needs them.

CodeSense provides mechanisms: saved agents, roles, routines, inboxes, panes, grants and content layers. You and your agents decide policy: priorities, handoffs, approvals and when to sync. There is no special manager agent or required workflow.

Saved changes should show immediately in the app. Check the visible result as you work. Startup files and launch permissions apply when a session launches; editing a definition does not rewrite a running session.

Use the agent-design skill to walk through this guide. The seat templates appendix helps shape individual agents.

2. The loop

Write the expected result before building. Preview the setup, ask for approval, then apply it. A failed proof changes the design; it does not justify more autonomy.

3. Discover the work and data

Read the current setup first: codesense_overview, describe_setup, agent_list and routine_list. Reuse what fits. If a section reports an error, resolve it before editing that part of the setup.

  • What work repeats? How often? What would a useful result look like?
  • What needs your judgment? Which actions may run alone?
  • Which repos, tools and machines are involved? Who owns them?
  • Where does the data live? Is it public, internal, personal, financial or health data? Does the task need read access or write access?
  • Which MCP servers are already available? Which tools can do the job with the least access?
  • What is the time and money budget? How will you stop or pause the work?

Ask in batches of at most three questions. Use codesense_search_tools to find CodeSense tools. Inspect the team's MCP choices in agent.yaml and an existing agent's agent_get result. Verify external tool contracts with the connected server. An example server name is not proof that the user has it.

Minimize data. Give each seat only the sources and fields its task needs. Keep secrets out of prompts, design notes and agent environment values. Use the user's existing service login. Share counts, ids or summaries when raw personal records are unnecessary.

4. Shape the smallest team

Determinism first

Use a command routine, script or check when the steps and result are fixed. Spend model calls on judgment. For an event chain, a metadata trigger can run a command routine; an agent routine can follow with after when judgment is needed. Use routine_create with action: "command" and a command argv array. Commands run directly, without a shell or model.

Newer apps support command actions, metadata triggers and after. Check the running tool schema. If these fields are absent, use an approved schedule-only agent routine that checks state and runs the script.

Example: a story enters review → a command checks the artifact → an agent reviews the result. Choose after.on: "succeeded" to continue only after a passing check, or "finished" to let an agent explain either outcome. See routine triggers. These are design choices.

Safety tiers

Use these tiers as a design checklist. They are not engine-enforced agent permissions.

TierDefault boundary
R0 · Read and analyseRead selected sources. Produce advice with evidence.
R1 · Reversible private workDraft notes or code within an agreed workspace and limits.
R2 · External effectsSending, posting, calendar writes or publishing need explicit human approval of the action, recipients and limits.
R3 · High consequenceMoney movement, trading and deletion need explicit human approval of the exact action and hard limits. Keep them out of unattended seats.

Record allowed amounts, destinations, scope and expiry. Pause when approval is missing. A prompt is policy, not a security boundary: restrict available tools and use CLI permissions too. A read-only sandbox does not make MCP tools read-only. For code-host work, verify GitHub MCP or gh access before a proof run. Separate agents that read untrusted mail or web content from agents that can act on private data. Pass only validated ids and bounded fields across that handoff.

5. Choose models and budgets

Choose per seat. Compare quality on the same task, response time, total cost per accepted result, context needs and tool access. Read model_rates for prices on file and session_usage for observed tokens and spend. A null cost or an unpriced model is missing information, not free work. Verify prices before making a budget promise.

Decide by task type

  • Fixed transforms and checks: use code first.
  • Classification and extraction: test a small model on bounded cases.
  • Building and review: compare candidates on real acceptance cases, including tool use and corrections.
  • Ambiguous planning: test reasoning quality and ask a person to resolve missing goals.
  • High-consequence work: keep approval boundaries whatever model you choose.

Set routine maxRuntime, maxWakes, maxWakesPerDay and minGap deliberately. Use overlap: "skip" when another run would repeat work. No aggregate dollar or minute cap exists. maxRuntime is per run. Check session_usage before each launch and stay within the agreed budget. Time and wake limits do not enforce that total. Read routine_runs and pause with routine_set_enabled when results or spend exceed the agreed budget.

Claude agents can call who_am_i with no arguments. Their MCP connection supplies session_id for who_am_i and sessionId for signal_done and routine_publish_result when omitted. Use this connection identity for Claude; headless permissions can deny shell variable expansion.

Codex agents should pass their own session identity explicitly: send_message and reply take session_id; signal_done takes sessionId. For every send_role_message, set sender to your own handle from who_am_i.handle. Run echo $CODESENSE_TAB_SESSION_ID in your shell to get your id, then pass it explicitly. If it is empty, match your own tab name and workspace in list_sessions and use launchTelemetry.sessionId. If there is no unique match, ask instead of guessing. Pass the id to who_am_i and keep its returned handle for role-message attribution and replies. Read each tool's current input schema.

6. Choose what people see

Start with the human Inbox and the agent list. Put decisions in Needs you and progress in Updates. Add a custom pane only when it answers a repeated question better: what is waiting, what changed, or what needs approval?

Use your first dashboard, pane shapes and reacting to state. Give each action a clear result. Verify that changes appear immediately. Reuse the bridge's subscriptions; do not add a polling loop per pane.

7. Permissions and inheritance

Keep private work in personal scope. Team agents are shared; any teammate can edit them. created_by is attribution. The CLI enforces native agent permissions. Pane capabilities and grants govern pane actions; they do not replace CLI permissions. See agent.yaml and calling CodeSense from a pane.

Only content follows the parent-team chain. Setting a parent does not inherit its saved agents, roles, routines or other config. Put shared teaching and skills in content, then select the needed paths in each agent's startup/context. Verify with agent_preview in the destination team.

A child receives only the content its ancestors declare in their config/sharing.yml; each team in between must share it onward. A parent relationship is not a privacy boundary: everyone with the context repo can read every team's files. Keep personal and finance memory in private content, not team content. Changing a parent with set_team_parent is optional and needs the user's approval.

8. Write the design down

Keep a short design note in content the user owns. Record goals, data sources and sensitivity, seats, tool boundaries, risk tiers, handoffs, budget, stop conditions and proof cases. Say who chose each policy and why. Include saved agent and routine ids after creation.

Optional structured form: team-design.yaml is an optional record of intent. It holds goals, a data map with sensitivity, the risk tier, members by id, evals and the optimization mode. DESIGN.md is its human-readable companion. Neither is a required runtime file. The real agent.yaml and routine.yml remain the source of truth; do not copy their launch or schedule fields into the design.

CodeSense has no built-in designer agent; follow the agent-design skill yourself.

The learning and context loop uses this note when it proposes improvements for a person to approve.

9. Build in small steps

  1. Show the design and dry-run plan. Ask for approval before saving anything.
  2. Preview each definition with agent_preview. Check manifest.errors, warnings, resolved context and required skills. Use agent_create with dryRun: true before saving; keep the returned ids.
  3. Save matching roles with role_save. Newer apps offer this tool. If it is absent, copy the matching role YAML from the starter and keep explicit worker registration. A default handler does not launch itself. Each worker uses register_role to claim queue work.
  4. Use routine_create with dryRun: true and enabled: false, then save disabled. Newer apps support schedules, metadata triggers, command actions and after through MCP. Check the running schema. If advanced fields are absent, use an approved schedule-only agent routine. Event triggers such as role_pending accept the MCP events parameter or YAML; see the starter walkthrough. Read the running tool schema before applying.
  5. Write an optional pane with pane_write. Check its capabilities and grants before opening it.
  6. Change team inheritance only if the design needs it. Preview from the child team again.

Give every resource a stable, recognizable id. Keep routines disabled until the user enables them one at a time. Tell the user which writes are local context-repo edits; sharing them is a separate git action.

10. Prove it works

Agree on one normal case and one stop case per seat before launch. First validate definitions without running them. Creation dry runs write nothing; routine_run_now is a real run, not a dry-run switch.

After approval, send a clearly labelled test with send_role_message through each queue. Verify registration, claim, acceptance receipt and acknowledgement. Confirm a fresh worker gets enough context. Check that a reviewer can return a visible defect and that a missing approval stops action. Bound the test's cost and clean up its messages.

Open a pane with pane_open and check the visible result. Inspect routine_runs and routine_run for routine outcomes. Use list_runs and read_run_evidence for story-run evidence when available; a run with no recorded evidence is not proof. Show the user the result, the ids and any unverified step.

11. Iterate from evidence

Watch failed runs, missed handoffs, repeated Needs you items, time to an accepted result and cost per outcome. Split a seat when it needs conflicting tools or too much context. Merge seats when handoffs cost more than the separation helps. Change one thing, replay the same cases, and compare.

To stop the setup, call routine_set_enabled with enabled: false for its routines. This stops future starts. For each running session you intend to end, take its handle from list_sessions, then call close_terminal_tab with that handle. It ends the CLI and keeps the worktree files. Disable routines and close active sessions separately; there is no single kill switch.

Learning and context

Keep instructions short. Load only relevant skills and sources. Record durable lessons as small notes with their source, date and confidence. Recheck old facts before loading them. Give each seat a context budget; more history is not always more useful.

An improvement loop you can build: a fresh-context evaluator grades agreed cases. A steward collects structured run and usage signals, proposes a diff with evidence, then waits for human approval. A monthly prune keeps, merges, summarizes or expires notes to an archive. Git history provides the audit trail. Untrusted-source facts stay quarantined until a human promotes them. Personal and finance memory stays private. This guide does not install evaluator or stewardship skills.

This loop uses the record of intent. A weekly or monthly review can be done manually. An optional review routine needs the user's approval and may propose changes; it must not expand its own access or apply policy changes alone.

12. Worked examples

Solo founder

Use a planner to turn goals into acceptance-ready work, a builder in one story workspace, and a reviewer for independent checks. Start with one active assignment. Scope and release decisions stay with the founder. The solo-founder starter includes all three definitions, matching role YAML, exact launch fields and one immediate role-queue wake. Its prompts need no extra skill. Add selected project context before real work. A notes backlog must first become a managed pipeline story: read get_story_format, choose a configured repo with list_source_repos, validate with validate_story, then save it in team content. Confirm query_context finds its story id before launching the builder.

Small dev team with a review queue

Builders share a role queue; one reviewer starts with an exclusive registration. Use claims and receipts to track deliveries. A metadata transition can run deterministic checks before review. Start with a concurrency limit of one; increase it when evidence shows the queue is the bottleneck. Independent review adds cost, so bound fix rounds and escalate unresolved decisions.

Non-dev desk

A family desk can read chosen calendar entries and school notices, then draft a weekly brief in private content. A pane shows upcoming tasks and Needs you decisions. Use a command for fixed totals and an agent for summarizing. Keep untrusted notice text away from calendar-write tools. Ask before changing events or sending the brief; record exactly which recipients and dates were approved.

Finance-analysis desk sketch

A read-only analyst compares selected account exports and drafts a cash-flow summary with sources and uncertainty (R0). It may save a private draft within an agreed budget (R1). Sending a report outside the desk needs approval of the report and recipients (R2). Transfers, trades and deletion require explicit approval of each exact action, amount, account and limit (R3); exclude those tools from unattended agents. Keep finance memory private and use deterministic arithmetic for totals. These are workflow boundaries, not investment recommendations.
