Where the status dot comes from

In a CodeSense terminal tab, the shell runs claude and codex through CodeSense's activity helper, whether a saved agent launched them or you typed them, on this Mac or on a machine. The helper adds CodeSense's status hooks to a private copy of the CLI's settings (your own --settings are kept), or passes them to Codex as -c hooks.*, and the dot follows those events. When the helper can't attach, the CLI runs as normal with no status. The status dot is still in Beta.

The notify hook on this page is Claude Code only. Where the activity observer sees a session, its reports win, so the hook matters only for a claude the observer missed. Codex has no notify hook.

What ships

The CodeSense binary carries the reference hook as embedded bytes. Each time CodeSense starts, it writes the hook into its own activity root, beside activity-helper, with mode 0o755. On a machine, the session server does the same in its own install. Every CodeSense terminal tab exports $CODESENSE_ACTIVITY_HOST, the path to that root, so the hook command finds the script there. Your worktrees and team content get no copy, so there is nothing to keep out of git or to publish.

The settings that run it are in the worktree's .claude/settings.local.json for a hand-typed claude, kept out of git, and in a private per-session settings file for a launched agent. Your repo's .claude/settings.json is never written. The hook runs no matter how claude ends up running in a CodeSense tab:

  • Saved-agent launch (open_workspace with an agent name) — the normal path.
  • Plain terminal tab (open_terminal_tab) + hand-typed claude, through the shell or as command claude — the tab points at the installed hook, so Claude Code finds it on the first run.
  • Remote tab (open_remote_tab) + hand-typed claude on the remote machine — the machine's session server installs the hook the same way.
  • Any claude re-run after an agent exits, or one that outlived an app restart — the installed hook stays put.

The secret-file guard

CodeSense ships a second hook beside the status hook, codesense-secret-guard.sh, and merges it wherever the status hooks go: one PreToolUse group scoped to Read, Grep, Glob and Bash. It stops an agent reading a credential-shaped file into its transcript. One list of protected families drives both the hook and Claude's own permissions.deny rules, so they cannot drift apart:

  • .env and .env.*
  • *.pem and *.key
  • id_rsa* and id_ed25519*
  • anything under ~/.config/codesense-mcp/

The hook lets the templates through (.env.example, .env.sample, .env.template, .env.dist) and the public halves (*.pub), and checks a Bash command for what it reads: copying a template to .env, deleting .env or echoing into it only writes, so it is allowed. On a match the call is denied with a reason the agent can pass on to you.

The native rules are broader than the hook. A deny rule has no exceptions, so Read, Grep and Glob also refuse the templates and the .pub files. They stay readable through Bash (cat .env.example), which the hook allows. The native rules are what keep a directory search from walking into a credential file, which the hook cannot see.

The guard is a convenience that keeps credential files out of an agent's ordinary reads. It is not a sandbox: it guards reads only, and only for Claude. To keep an agent away from your secrets, run it with sandboxed permissions. See How CodeSense trusts agents.

No per-team override

Teams don't ship this file. The hook comes with CodeSense, so your context repo needs no hook file and no hook wiring in .claude/settings.json. A file your team keeps at .claude/hooks/codesense-notify.sh is ordinary team content: CodeSense never runs it, and deleting it is safe.

The hook is wire-level infrastructure, like the MCP bridge registration: CodeSense's own code depends on exactly what it posts to exactly which endpoint, so a drifted team copy would silently break status reporting. Keeping ownership centralized means every CodeSense install speaks the same contract.

If you need custom status reporting (quieter notifications, an extra endpoint, event filtering), file a feature request. The current design doesn't take per-team overrides, but we can add a configuration seam if there's demand.

What the hook does

  • Reads the Claude Code hook event from stdin and posts it as JSON to the local CodeSense API (CODESENSE_API_PORT, or CODESENSE_STATUS_URL when the agent runs on a remote machine).
  • Degrades gracefully. When the CodeSense app isn't running the hook writes one legible line to stderr and exits 0, so the Claude lifecycle event never stalls.
  • Logs post failures to ~/.codesense/logs/notify-hook.log (capped at 512 KB) so a missed status dot is diagnosable without turning on anything extra.

Where the source lives

The reference bytes are at scripts/codesense-notify.reference.sh in the CodeSense source repo. The app binary includes them at compile time via Rust's include_str!, so an upgrade to a new CodeSense version with a different hook body is picked up the next time CodeSense starts: the installed file is compared with the embedded bytes and rewritten if it differs.
