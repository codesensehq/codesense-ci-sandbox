Arc I · Dashboard primitives

Your HTML file is a first-class pane.

A CodeSense dashboard is a single .html file. In your team's content/ it opens as a centre tab; in the team's panes/ folder it's a custom right pane; sent with send_message and contentType: "html" it renders live in an Inbox message — same page, three shapes. The viewer injects window.codesense, applies the theme as CSS tokens, and routes clicks to the app. There is no build step, no bundler, no framework required. If you can write a <script> tag, you can ship a dashboard.

What this arc teaches

Enough to write a working dashboard in ten minutes and understand why it works. We walk through the three pane shapes, the window.codesense bridge, how to react to app state, how to theme without authoring colours, how to deep-link between docs, and how to iterate on your file inside the app. The exhaustive reference — every verb, every token, every event — lives in the primitives-explorer. These pages teach the story the explorer sorts.

You will not need

  • A build step. The viewer loads your .html as-is.
  • A framework. Vanilla <script> works; so does React in a CDN tag.
  • A theme file. CodeSense pushes --cs-* tokens; you consume them.
  • Service credentials. Declare the capabilities your pane needs; the host grant and slot ceiling bound every call. Rate guards stop runaway loops.

Story trail

The bundled story-trail dashboard is a tab-only file, listed by pane_list as built-in. It declares no slots, so slot menus and pickers do not offer it. It reads storyChanges({storyId}) and shows a keyboard-accessible task tree, sessions in time order or grouped by task, timing spans and totals split by basis. Unknown prices stay unknown; Set a rate uses setModelRate.

Right-click a story and choose Trail. Select a session to open its facts and recent turns, then choose Open conversation or a recorded turn link. The conversation has earlier/later paging, tool disclosures, redaction markers and a live-terminal action only while that session is running. Pages contain up to twenty turns, aligned within each retained contiguous interval and split at dropped turns. A jump highlights its turn on that aligned page. Earlier moves one page back; Later follows only the reader's returned cursor.

The page routes #story/<id> and #session/<id>?from=<first>[&turn=N]. File fragments reach HTML viewers on first open and when reopening an existing tab, including across teams. A verified bundled page may reopen its exact own file; all other paths retain normal admission.

// Inside the bundled story-trail page:
codesense.openFile({path: "story-trail.html#session/SESSION_ID?from=20&turn=37", newTab: true});

Missing conversation states and lookup misses show the reader's reason. Fields the CLI did not record are omitted. Task rows show each task's recorded outcome from the shared read. File-and-line chips, changed-file rows and commit SHAs open a read-only diff through openDiff; line ownership arrives in a later change.

The private storyChanges reader returns file lines: {added, removed} | null with linesReason. Stacked branch ranges count once. After a PR lands, counts describe lines changed by this story’s merged PRs, comparing each merged commit with its first parent once. Branches with no single final tree keep counts unknown; binary files and missing local objects have explicit reasons. The same selected diff supplies actual file paths and the file total, including after a squash or deleted branch. Commit history availability remains separate. Commit rows include the recorded author; PR URLs and merge times use local origin and commit metadata, with reasons when unavailable. Published dashboards retain their existing field allowlist.

Live reads patch a stable route skeleton. Lists use codesense.kit.keyed with structural versions and fact updates, keeping unchanged rows, form drafts, selection and scroll in place. While a primary pointer gesture is active, the whole passive refresh waits, so neither reparenting nor growing facts move the pressed target. Native click, auxiliary click and drag completion release it; pointer-up uses one macrotask so the click lands first. Leaving the frame, cancellation and window blur also release it. Keyboard focus keeps row-scoped structural deferral. Loading uses kit.skeleton. Async completions respect a later move to another control or the host. Pricing confirmation updates the owning story and request even while its route is away. An explicit route, fragment or turn target wins over saved reading positions; otherwise the displayed page restores its own position, or starts at the top. Reading positions use the returned session, first and last turn indices, independently of the request and highlight. Remove highlight keeps that page without a new read. The page focus helper owns conversation thread and rail restoration. The HTML host yields to fragments and restores document scroll only when there is no fragment.

Try this now

The simplest thing a dashboard can do: ask CodeSense where it lives. Save this as hello.html in your team's content/ and open it. 

<pre id="out"></pre>
<script>
  codesense.context().then((where) => {
    // { org, team, layer, contentRoot } (team is null in your private space)
    document.getElementById("out").textContent = JSON.stringify(where, null, 2);
  });
</script>

How to do this via MCP

Agent-side equivalent

Dashboards use the browser bridge; agents use MCP tools. Both resolve to the same underlying Tauri commands — the UI↔MCP cross-reference is enforced by the generator that renders ui-mcp-crossref. 

# What's going on: org and team, sessions, agents, routines, inbox
mcp.call("codesense_overview", {})

# How to write a live page, then lint it before saving
mcp.call("get_live_data_contract", {})
mcp.call("validate_live_data_doc", { ... })

# Write a custom right pane and show it
mcp.call("pane_write", { id: "sprint-board", html: "..." })
mcp.call("pane_open", { id: "sprint-board" })
