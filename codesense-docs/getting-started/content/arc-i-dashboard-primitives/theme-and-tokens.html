Arc I · Theme

Consume tokens. Don't author colours.

You don't ship a theme file. The viewer pushes a palette of --cs-* custom properties on every doc, swaps them when the user switches dark ↔ light, and keeps them in sync across every pane. Your job is to reach for the right token — background, surface, border, accent — and let the viewer paint. The same HTML renders correctly on both themes with zero conditional code.

How the theme reaches your doc

The viewer sets every --cs-* token at :root before your first paint. The frame and its host container use the same resolved surface background. Use background: var(--cs-bg) for the body; never hard-code a white body background. You can rely on them in any CSS without a script. If you want to react to a change, subscribe: 

codesense.onTheme((theme) => {
  if (!theme) return;
  // theme.scheme === "dark" | "light"
  // theme.tokens is the full palette object
  console.log("accent is now", theme.tokens["--cs-accent"]);
});

You rarely need the explicit callback — the CSS tokens update by themselves. Reach for onTheme only when you draw into a <canvas> or generate inline SVG whose fills can't read a CSS variable.

The cs-* classes

Where tokens are the atoms, the cs-* classes are the molecules — pre-themed building blocks every dashboard shell uses so three dashboards side by side feel like one app. Reach for them before you author your own class names.

Group Classes What it is
layout cs-page, cs-topnav, cs-main, cs-footer The shell every dashboard body wears.
sidebar cs-sidebar-item & its -selected / -active / -ready siblings List rows inside any left/right nav. Themed from the viewer sidebar palette.
tabs cs-tab-item, cs-tab-item-active Tab strip buttons. Pair with aria-selected.
cards cs-workspace-card, cs-workspace-card-selected Raised card surface for tiles / workspace rows.

prose cs-redline-add, cs-redline-del, cs-note-link Diff spans and scratch-note links.
terminal cs-terminal-display Container that wraps the xterm.js display with viewer-matched colours.

Each class in the classes tab lists the tokens it consumes — your handy map from "visible element" back to "token to tweak".

Elevated surfaces

Use --cs-shadow-lg for floating overlays and --cs-shadow for small controls. Both are shared layout tokens, available in the host and page kit. Keep the surface opaque and pair elevation with a theme-derived edge. 

.floating-preview {
  background: var(--cs-bg);
  color: var(--cs-fg);
  border-radius: var(--cs-radius-lg);
  box-shadow: var(--cs-shadow-lg);
}

What your dashboard looks like on both themes

Same markup, same tokens — only the token values change. If a surface disappears on one theme (e.g. a near-white card on a near-white background), you're authoring a colour instead of consuming a token. Fix is almost always: background: var(--cs-surface) on a cs-bg body, or vice versa.

How to do this via MCP

Agent-side equivalent

Agents can't flip the viewer theme, and there is no MCP tool that reads it. A page reads the current palette from the theme's CSS variables: 

getComputedStyle(document.documentElement).getPropertyValue("--cs-bg")
// → "#0d1117" (dark)
