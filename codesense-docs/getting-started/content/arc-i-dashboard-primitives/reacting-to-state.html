Arc I · State

You don't poll. The host nudges.

CodeSense dashboards are read-models over long-lived state: orgs, teams, worktrees, sessions, inbox threads, routine runs. Instead of polling, you register a listener for the kind of change you care about, and the host sends a nudge event the moment that state moves. Your handler re-reads via invoke and re-renders. That's the whole loop.

Two shapes to subscribe

The bridge exposes two subscription idioms. Pick the one that matches your dashboard:

  1. subscribeContext — one listener for "anything moved"

    Use when you want to re-read on any change to the context index — stories, agents, teams, routines, worktrees. The handler is called once immediately with initial rows, then again every time codesense:context-changed fires upstream. 

    codesense.subscribeContext({ text: "DEMO" }, (rows) => {
  renderStoryBoard(rows);
});

// Returned handle lets you unsubscribe:
const off = codesense.subscribeContext({}, reload);
// later:
off();

    The filter object narrows the initial payload only — you still get a nudge for every context change. The pattern pays off because the handler re-reads via a verb anyway, and you want tight scope on the first paint.

  2. Typed on* helpers — one listener per concern

    Fine-grained listeners wrap a single event name. Prefer these when a specific change kicks a specific re-read — they keep the handler small and the intent obvious: 

    codesense.onAgentsChanged(() =>
  codesense.agents().then(renderRoster));

codesense.onInboxChanged(() =>
  codesense.inbox({}).then(renderThreads));

codesense.onRoutineResult(() =>
  codesense.routineResult({ key: "acme/web/rt-nightly" }).then(renderStatus));

codesense.onWorktreesChanged(() =>
  codesense.worktrees().then(renderWorktrees));

codesense.subscribe("sessions", {
  onChange: (snapshot, delta) => renderSessions(snapshot.snapshot)
});

    onAgentsChanged follows saved-agent rows in the shared hub. A save, an external agent.yaml edit, or a git pull updates agents() even when that agent has no running session. The callback's agents() read uses the cached projection. By default, hidden pages make no reads; they catch up when shown. The rich agent({key}) call stays a fresh read of resolved startup and login state. Keep the cleanup function and call it on teardown: 

    const stopAgents = codesense.onAgentsChanged(async () => {
  renderRoster(await codesense.agents());
});
codesense.onTeardown(stopAgents);

    Sessions use one cached Rust projection shared by native UI and MCP. A subscription returns {topic, viewKey, rev, snapshot}, followed by codesense:delta {topic, viewKey, rev, upserts, removes, requestId?}. Rows have stable ids. Revision gaps resync automatically. By default, hidden frames receive one stale marker, make no reads and resync when shown. The host can inject firstPaint with the same snapshot shape. Use ui:<slotId> and setUiState(topic, patch, requestId) for shared selection and folds; prefs() stays page-private. Change helpers follow the same hidden-delivery policy as subscription data.

    codesense.setBadge publishes a count; setBadge(null) clears it. By default, hidden panes pause and catch up on show.

    Keep a badge fresh while hidden

    Architecture: declare <meta name="codesense:badge" content="live"> in the pane's head. The host passes the resolved declaration to the page shim, so a manifest's badge: live works too. Its existing subscriptions deliver their own data and invalidations while hidden; subscribe and page remain available. This adds no topic, store or watcher. Keep the subscription cleanup on teardown.

    Policy: opt-in is off by default. Use it only for an attention badge, as the built-in Inbox does. The host coalesces delivery to one flush per frame every 2 seconds, keeping the 4 most recently shown hidden frames live. The oldest-shown frames become stale until shown again or capacity opens. The cost is retaining those frames' existing subscriptions and doing badge work at each flush; there is no timer polling when nothing changes. 

    <meta name="codesense:badge" content="live">
<script>
const cs = window.codesense;
let visible = false;
cs.onVisibility(shown => {
  visible = shown;
  if (shown) refreshFullInbox();
});
// Architecture: reuse the Inbox read; hidden updates only publish the badge.
cs.onInboxChanged(async () => {
  if (visible) return refreshFullInbox();
  const inbox = await cs.inbox({scope: "to-human", limit: 500});
  const count = inbox.conversations.filter(thread => thread.unread).length;
  cs.setBadge(count ? {count} : null);
});
</script>

    Architecture: the built-in Inbox coalesces its callbacks before reading its existing Inbox view, then computes only the unread conversation count while hidden. It leaves list, thread and composer rendering until show. Private cross-team Inbox copies use their existing inboxRollup() read instead. A live-badge pane's closed-edge count updates without opening it.

  3. Follow the left nav — onNavSelectionChange

    A dashboard or right pane can follow what the left nav has selected: the open file and the folder the nav is drilled into, each with the story or epic it is. The selection is always your page's own team, and a path outside that team's content reads as null. Nothing is sent until you ask, so the call costs nothing for pages that don't. 

    // Feature-detect: an older CodeSense has no nav selection.
if (typeof codesense.onNavSelectionChange === "function") {
  const off = codesense.onNavSelectionChange((sel) => {
    // sel: { org, team, file, drill } | null
    highlightStory(sel?.file?.kind === "story" ? sel.file.id : null);
    scopeToEpic(sel?.drill?.epic?.id ?? sel?.file?.epic ?? null);
  });
  // off() when done: the last unsubscribe stops the host's work.
}

// One-shot read (resolves null rather than wait past 5 s):
const sel = (await codesense.getNavSelection?.()) ?? null;

    To select a file in the nav from your page, call codesense.openFile({ path }): it opens the file and expands its folders. The Pipeline pane in a team's panes/ is a working example.

  4. Remember your own settings — prefs / setPrefs

    A dashboard's localStorage doesn't survive a restart (its frame gets a new origin each launch). Keep view settings with prefs instead: one small object per dashboard, in your own app state, never shared with the team. A team copy and a private copy of the same dashboard each keep their own. 

    // Keep persistent settings with the host across frame remounts.
const { details = "off" } = codesense.prefs ? await codesense.prefs() : {};
await codesense.setPrefs?.({ details: "compact" }); // null removes a key

    Story overviews come from the index, not from reading each file: add "summary" to a query's select and every story, bug, spike and epic row carries summary — the text under its first configured summary heading (Purpose, then Story, by default). 

    codesense.subscribeContext(
  { where: { kinds: ["story"] }, select: ["status", "summary"] },
  // summary is plain text; an older CodeSense omits the key.
  (r) => render(r.rows.map((row) => [row.id, row.summary ?? null])),
);

If the helper doesn't cover your event

The on* helpers are convenience wrappers over window.addEventListener("message", …). If an event ships before the wrapper does — or you need to inspect the payload — listen directly: 

window.addEventListener("message", (e) => {
  const msg = e.data;
  if (!msg || typeof msg.type !== "string") return;

  if (msg.type === "codesense:theme") {
    applyTheme(msg.theme);
  }
  if (msg.type === "codesense:visibility") {
    msg.visible ? resumeAnimations() : pauseAnimations();
  }
  if (msg.type === "codesense:restore-scroll") {
    window.scrollTo(0, msg.y);
  }
});

Posted messages the shim recognises are listed in the explorer's events tab. Every event there has a direction (parent-to-doc, doc-to-parent, reply), a payload shape, and a timing note.

Lifecycle — register, unsubscribe, clean up

Every on… listener and subscribeContext return an unsubscribe function. The viewer drops subscriptions automatically when the iframe is torn down (close the tab, close the pane, replace the inbox message); you only need to unsubscribe explicitly if your dashboard swaps views in-place: 

const subs = [];

function mountStoriesView() {
  const h1 = codesense.subscribeContext({ where: { kinds: ["story"] } }, renderStories);
  const h2 = codesense.onAgentsChanged(renderRoster);
  subs.push(h1, h2);
}

function unmount() {
  while (subs.length) subs.pop()();
}

A listener registered after the frame hides keeps working — onVisibility exists for the opposite reason: pausing expensive renders while the doc is off-screen. Reach for it when your handler re-ranks or re-sorts a large list: 

let visible = true;
codesense.onVisibility((v) => (visible = v));

codesense.subscribeContext({}, (rows) => {
  if (!visible) return;        // skip the expensive sort while hidden
  renderBigList(rows);
});

A worked example — a live worktree counter

Six lines of logic. Opens as a centre tab or a right pane; shows the number of managed worktrees; updates the moment a new one lands: 

<div id="count">…</div>
<script>
  function reload() {
    codesense.invoke("worktrees", {}).then((wts) => {
      document.getElementById("count").textContent =
        wts.length + " worktree" + (wts.length === 1 ? "" : "s");
    });
  }
  reload();
  codesense.onWorktreesChanged(reload);
</script>

Materialise a new worktree in another tab, come back — the counter has already ticked. Nothing in your doc polled; the host notified.

How to do this via MCP

Agent-side equivalent

Agents don't subscribe through the browser bridge; they poll MCP tools at an interval chosen by the routine (or run on inbox-idle triggers that only fire when something actually changed). The same read is reachable from both sides: 

# Dashboard: nudged by the host, re-read on demand
codesense.onWorktreesChanged(() => codesense.worktrees().then(render));

# Agent: polled by a routine, same shape
list_worktrees {}  // MCP tool

See the events tab for every parent-to-doc event and the kit method that wraps it.

Configuration is live too

The app owns three configuration topics in the same LiveHub as live lists. Open Settings, shortcut bindings, slot choices and the team main-document convention follow snapshots and versioned field deltas. There is no reload, read-on-mount refresh or polling interval.

TopicOwner and storageWhat publishes
prefsGlobal viewer settings and shortcuts in app-state; dashboard policy and workspace choices in the current principal's app-state section. save_app_state (including dashboard-policy saves), or a file edit to app-state.json in the app's data directory.
profileCurrent principal and org's private config/profile.json.write_dashboard_profile or an edit to that file through the existing scratch watcher.
workspaceConfigApp-owned mainDoc configuration in ~/.codesense/workspace-config.json.save_workspace_config or an edit to that file.

These are native app-owned views. A pane grant cannot choose another principal or org by supplying a view key. Global settings and shortcuts stay global when profiles change. Hidden native consumers release their subscriptions, then catch up from their revision on reveal; an expired revision gets a fresh snapshot. External edits enter the existing shared watcher, with unrelated root writes rejected before debounce.

Example: patch one preference

A native integration uses the normal app-state writer with a field patch and its captured principal. This preserves newer fields written by someone else. This is a native command example, not an additional pane or MCP verb: 

await invoke("save_app_state", {
  expectedPrincipal: currentPrincipal,
  patch: true,
  state: JSON.stringify({ viewer: { settings: { editorLineWrap: "on" } } })
});
// The visible Settings control and editor follow the prefs delta.
// Global settings are never nested inside localProfileWorkspacesV1.

For an outside file edit, read the current JSON and change only the intended fields; preserve its other global and principal sections. Profile slot writers likewise patch only the changed slot, and workspace-config writers patch only the changed repo's mainDoc. See the generated topic reference for the exact producer inventory.
