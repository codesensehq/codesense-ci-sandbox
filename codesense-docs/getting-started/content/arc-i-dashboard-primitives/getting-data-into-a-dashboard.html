Getting data into a dashboard

Pick the source before you write the page: an engine query for what CodeSense already knows, a content folder for files an agent writes, or records for structured items. This page says which to use, shows one example of each, and lists the limits that apply today.

Which path to use

Path Pick it when Agent side In-app dashboard reads with Hosted dashboard reads with
Engine query The data is something CodeSense already holds and must be live: sessions, inbox, runs, usage. Nothing to write. sessions(), inbox(), runs(), sessionUsage(), subscribe(topic), onSessions, onInboxChanged The declared catalog queries sessions, inbox, runs, sessionUsage; the inbox stream
Content folder Anything else: a report, a feed, a JSON or Markdown file an agent produces. create_content_file into a team content folder files.list, files.read, subscribe('files'), queryContext, subscribeContext Frontmatter fields through queryContext only (no file text), or a data file listed in the manifest
Records Many small structured items with named fields: tasks, events, checklist rows. records_create, records_write, records_set_fields subscribe('records', {collection}), records.list, records.read Frontmatter fields through queryContext; no collection selector, so mark each record with a shared field (see example c)

Core, fast data comes from the engine's queries. Everything else is content an agent writes, and the dashboard reads it back through the generic files and records reads, with no Rust change and no new query.

In-app versus hosted

An in-app dashboard runs in CodeSense on the Mac and has window.codesense. A published (hosted) dashboard has no window.codesense: it asks a fixed catalog of read-only queries through the live link and the Mac answers them. publish_dashboard refuses a page that calls window.codesense. Hosted answers are redacted and cut to fit 256 KB, each list query has its own row cap, and a hosted query is refreshed by polling no faster than every 15 seconds. Only the streams push. Private records and private notes are not reachable from a hosted dashboard at all: the hosted queryContext reads the dashboard's team content only.

Build and check the page in-app first, then publish. Anything that depends on a verb or a field the hosted catalog does not offer will not survive the move; the limits below say where the two differ.

Pin a hosted query's arguments

live:
  queries: [storyChanges, whyLine]
  args:
    storyChanges: {storyId: [DEMO-46, {epic: DEMO}]}
    whyLine: {repo: [acme/codesense]}

Before adding viewers, pin storyChanges.storyId and whyLine.repo, including with queries: all. Owner-only publishing and owner asks may omit these pins. Once present, pins apply to owners too. Every pinned argument must be sent; a missing argument or a value outside its list returns arg_not_allowed. Lists hold 1–64 literal strings or integers, matched by exact JSON type and value: 5 differs from "5". Other arguments remain open, so pin whyLine.path too when only one path should be shared.

The generated starter sends the first literal for each pinned argument of its selected query, preserving JSON types. A selector-only argument gets a named placeholder such as SET_storyId in app.js. The rendered error, creation warnings and next steps name the argument to configure and the epic or team it must belong to.

The Mac checks before running a query. The relay checks before serving live or cached answers, and never serves a cache fallback for this refusal. Edits take effect when the watcher saves the block, without republishing; until then asks fail closed. Changing a query's pins deletes its cached answers. Unknown live keys and invalid pin declarations are refused. These pins cover queries only; streams are unchanged.

Only storyChanges.storyId also accepts {epic: DEMO} or {team: web} selectors, mixed with literals. Selectors need a known saved team scope at publish; the team selector must name that team. The Mac resolves current stories through the context-query engine in that scope, by parent_epic/epic or epic folder. Unknown ids, another team's stories, a moved folder scope, and an index that is not ready are refused. Editing a story's epic takes effect without republishing. A selector satisfies the viewer pin rule. Requests carry live_scope, an opaque SHA-256 fingerprint of the saved org and team. A changed or removed scope retires all cached and in-flight query answers, even with identical selectors; an unchanged scope preserves them.

The share server checks literal args and leaves selector args to the Mac. While the Mac is offline, viewers see the last answer it approved under the current pins, which can still include a story that has since left the epic; the Mac's next answer replaces it. Online rate limits, timeouts, failures and oversized answers never use a selector cache fallback. Changing the pins deletes that query's cache and prevents new asks from joining old requests. The relay also checks the viewer permission computed on the Mac. An authoritative arg_not_allowed or not_approved deletes that exact cached answer and prevents pending older answers from restoring it, including after a disconnect.

Session identity and tool failures

Internal sessions() rows and agent instances expose an optional sessionId for matching a stored conversation to its live terminal. Do not use reusable id or handle values as conversation identity. Published session rows retain their existing allowlist.

sessionRead() tool summaries include firstError: {turn, toolUseId} from the tool-call index, or null when no confirmed failure is recorded. firstRetainedError: {turn, toolUseId} is the first failure outside the conversation's dropped-turn interval, including a failure before the recent excerpt. It is null when no failure text is retained. The original firstError and counts keep their full-index meaning. Confirm a retained jump with sessionRead({sessionId, include: ['conversation'], toolUseId, limit: 1}); omit the link when that lookup is unavailable or missing. errorUnknown counts calls without a recorded success/error status and does not mean zero errors.

(a) Engine: recent sessions and the inbox

Read the built-in sources directly. onSessions pushes the session list and calls back again on every change; inbox({limit}) returns the newest messages as {messages, hasMore}, and onInboxChanged tells you when to read again. Declare the grants in the page's meta tag (Calling CodeSense lists them). 

<meta name="codesense:capabilities" content="sessions:read inbox:read:team">
<ul id="sessions"></ul>
<ul id="inbox"></ul>
<script>
const cs = window.codesense;
const sessionList = document.getElementById('sessions');
const inboxList = document.getElementById('inbox');

function showSessions(rows) {
  sessionList.replaceChildren(...(rows || []).map((row) => {
    const li = document.createElement('li');
    li.textContent = row.displayName + ' · ' + row.state;
    return li;
  }));
}
async function readInbox() {
  const view = await cs.inbox({limit: 20});
  inboxList.replaceChildren(...view.messages.map((m) => {
    const li = document.createElement('li');
    li.textContent = m.fromName + ': ' + m.text;
    return li;
  }));
}

const stopSessions = cs.onSessions((rows, error) => { if (!error) showSessions(rows); });
const stopInbox = cs.onInboxChanged(() => readInbox());
cs.onTeardown(() => { stopSessions(); stopInbox(); });
readInbox().then(() => cs.ready());
</script>

The first-paint read and later changes both come from the same engine: you do not poll. subscribe('sessions') and subscribe('inbox') give the same data as topics with deltas; see LiveHub topics and rows. Always render message text with textContent. On a hosted dashboard the same sources are the catalog queries sessions and inbox, declared in the manifest's live block and read with CS.query or the inbox stream (see the "Agent builds a dashboard" handbook guide and get_live_data_contract, section hosted).

(b) Content folder: an agent writes a file, the page shows it

The agent writes a JSON or Markdown file into a team content folder. If the agent writes with its own filesystem tools instead, it calls refresh_frontmatter_cache so the index sees the file.

create_content_file

The agent writes the feed. Use an absolute path inside the team's content folder; the example creates feeds/standup.json. With onCollision: "fail" a second create of the same path is refused; keep-both writes the next free numbered name instead. The tools are listed in Content file tools. 

{
  "tool": "create_content_file",
  "arguments": {
    "path": "/abs/context/_team/engineering/content/feeds/standup.json",
    "content": "{\"date\":\"2026-10-26\",\"items\":[\"Ship the docs page\",\"Review DEMO-27\"]}",
    "onCollision": "fail"
  }
}

The dashboard lists the folder, reads the file and re-renders when the folder changes. files.list returns {rows} (each row has id, path, name, kind); pass a folder row's path as dir. files.read returns {text, truncated, size, sha256}. 

<meta name="codesense:capabilities" content="files:read">
<pre id="feed"></pre>
<script>
const cs = window.codesense;
const out = document.getElementById('feed');
const rootOptions = {scope: 'team', window: [0, 200]};
let folderOptions = null;

function fail(error) { out.textContent = String(error.message || error); }

async function show() {
  const root = await cs.files.list({scope: 'team'});
  const folder = root.rows.find((row) => row.kind === 'dir' && row.name === 'feeds');
  if (!folder) { out.textContent = 'No feeds folder yet'; return; }
  if (!folderOptions) {
    // The folder appeared (or was there at load): watch inside it from now on.
    folderOptions = {scope: 'team', dir: folder.path, window: [0, 200]};
    await cs.subscribe('files', {...folderOptions, onChange: () => show().catch(fail)});
  }
  const listing = await cs.files.list({scope: 'team', dir: folder.path});
  const file = listing.rows.find((row) => row.name === 'standup.json');
  if (!file) { out.textContent = 'No standup yet'; return; }
  const read = await cs.files.read({path: file.path});
  const feed = JSON.parse(read.text);
  out.textContent = feed.date + '\n' + feed.items.join('\n');
}

// Watch the team root first, so a feeds folder created later is picked up.
cs.onTeardown(() => {
  cs.unsubscribe('files', undefined, rootOptions);
  if (folderOptions) cs.unsubscribe('files', undefined, folderOptions);
});
cs.subscribe('files', {...rootOptions, onChange: () => show().catch(fail)})
  .then(show).catch(fail).finally(() => cs.ready());
</script>

If the feed has frontmatter (a Markdown file with status, owner and so on), subscribeContext over a queryContext query is simpler: it reruns the query whenever the context changes. It sends no deltas, so the whole result arrives each time (Your first dashboard). The files and queryContext reads are the in-app path; a hosted dashboard gets only frontmatter fields through its queryContext query, or a data file the manifest lists and the agent rewrites.

list_context_content

The agent can check what it wrote with the same listing the page uses: by context id, or by scope and dir like files.list. 

{
  "tool": "list_context_content",
  "arguments": {
    "context": "team:acme:engineering"
  }
}

(c) Records: an agent syncs a calendar, the page shows it

Declare the collection once, then let the agent write one record per event. The schema file is the one Records describes; write it with create_content_file at the team's content/schema/calendar.yaml. Add a source field. In-app pages do not need it, but it is the discriminator a hosted page will need below. 

collection: calendar
scope: team
folder: content/calendar
id: slug
title: title
fields:
  title: { type: text, required: true }
  starts: { type: date }
  source: { type: text }
order: [starts]

records_collections

The agent confirms the collection is declared before it writes.

{
  "tool": "records_collections",
  "arguments": {}
}

records_create

One call per new event. Slug collections need an id; use the calendar's event id. Creating an id that already exists fails ("record already exists"), so on a later sync use records_write or records_set_fields for events that changed. Keep the same requestId when you retry an uncertain create. 

{
  "tool": "records_create",
  "arguments": {
    "collection": "calendar",
    "id": "standup-2026-10-26",
    "fields": {
      "title": "Standup",
      "starts": "2026-10-26",
      "source": "calendar"
    },
    "body": "Daily sync, room 4",
    "requestId": "calendar-sync-standup-2026-10-26"
  }
}

records_list

Read back what the page will see. records_list pages with window ([start, end]), not limit: it ignores limit. 

{
  "tool": "records_list",
  "arguments": {
    "collection": "calendar",
    "window": [
      0,
      50
    ]
  }
}

In-app, the dashboard subscribes to the collection and renders the rows; this is the same pattern as Records › Read and subscribe: 

<meta name="codesense:capabilities" content="records:read:team">
<ul id="events"></ul>
<script>
const cs = window.codesense;
const list = document.getElementById('events');
function receive(view) {
  list.replaceChildren(...view.snapshot.map((record) => {
    const li = document.createElement('li');
    li.textContent = (record.fields.starts || '') + ' · ' + (record.title || record.id);
    return li;
  }));
}
cs.onTeardown(() => cs.unsubscribe('records', receive, {collection: 'calendar'}));
cs.subscribe('records', {collection: 'calendar', onChange: receive}).then(receive).finally(() => cs.ready());
</script>

What a hosted dashboard can do with records today

A hosted page has no records topic and no folder or collection selector. Its only route to records is the catalog query queryContext, which reads the dashboard's own team content, returns only the frontmatter fields the manifest shares (never the body, preview or file text), and accepts where.kinds, eq/in filters, match, sort, limit and select. A record does not store which collection it belongs to, so you cannot ask for "the calendar collection".

The workaround is a shared discriminator field. The agent sets source: calendar on every record (the schema above declares it), the manifest shares the fields the page needs, and the page filters on the discriminator. Rows that are not calendar events never match. Share only keys you want public to the invited viewers; summary, body, text, path, content and relationships can never be shared. To show a short text, have the agent copy it into a shared frontmatter field such as previewText. 

# dashboard.yml, the live block
live:
  queries: [queryContext]
  fields:
    queryContext: [title, starts, source, previewText]
// inside the published page; CS comes from the cs-live.js the starter ships
// markup: <ul id="events"></ul>; a rejection's message is the error code, e.g. mac_offline
const list = document.getElementById('events');

function render(rows) {
  list.replaceChildren(...rows.map((row) => {
    const li = document.createElement('li');
    // Frontmatter fields sit under row.fields; only title is also top level.
    li.textContent = (row.fields.starts || '') + ' · ' + (row.title || row.fileName)
      + (row.fields.previewText ? ' — ' + row.fields.previewText : '');
    return li;
  }));
}

CS.query('queryContext', {
  filters: [{key: 'source', op: 'eq', value: 'calendar'}],
  select: ['title', 'starts', 'previewText'],
  sort: ['starts'],
  limit: 100
}).then((reply) => {
  const answer = reply.answer;
  render(answer.rows);
  if (answer.truncated) list.append('Showing ' + answer.rows.length + ' of ' + answer.total);
}).catch((error) => { list.textContent = 'Could not load events: ' + error.message; });

Filtering happens on the Mac before the row cap, so the discriminator is reliable. Filtering in the page after the query is not: the cap has already dropped rows. Use the shared paging helper for continuation and honest coverage; see Limits for per-answer bounds.

Page any list with the shared kit

const list = kit.partialList({ container, render: c => kit.h('li', {}, c.sha.slice(0, 7)),
  subscribe: cb => kit.subscribeAll('storyChanges', {storyId, limit: 20}, 30, cb, {manual: true}) });
// Hosted: replace kit with CS; render with document.createElement and textContent.

Here kit = codesense.kit; container and storyId belong to your page. This paints the first 20 commits, then gives the reader Load more. Hosted pages declare live.queries: [storyChanges] and load cs-live.js. Use CS.partialList and CS.subscribeAll with the same arguments; CS has no h helper, so the renderer creates its own element. 

const list = CS.partialList({ container, render: c => Object.assign(document.createElement('li'), {textContent: c.sha.slice(0, 7)}),
  subscribe: cb => CS.subscribeAll('storyChanges', {storyId, limit: 20}, 30, cb, {manual: true}) });
window.addEventListener('pagehide', () => list.stop(), {once: true});

In-app pages use const sdk = codesense.kit;. Hosted pages load their local cs-live.js before the page script and use const sdk = CS; instead; list the SDK in publish.files and declare live.queries: [queryContext] for this example. Both expose the same API below. The hosted SDK uses wire envelope v: 1.

Default partialList styling is bundled in the SDK and installed once when needed; no extra stylesheet or published asset is required. It honors inherited --cs-* tokens and the page's color scheme. Binding existing status and button elements keeps your authored controls and styles and does not install the default component styles. 

<div id="items"></div>
<button id="refresh" type="button">Refresh</button>
<script>
const sdk = codesense.kit; // hosted: use CS instead
const view = sdk.partialList({
  container: document.getElementById('items'),
  subscribe: receive => sdk.subscribeAll('queryContext', {}, 15, receive, {manual: true}),
  render: row => {
    const item = document.createElement('div');
    item.textContent = row.title || row.fileName || row.id || row.path;
    return item;
  }
});
document.getElementById('refresh').addEventListener('click', () => view.refresh());
window.addEventListener('pagehide', () => view.stop(), {once: true});
</script>

The component binds the callable handle returned by subscribeAll: its loadMore() fetches one next page, refresh() begins a fresh walk, and calling the handle stops it. manual: true keeps continuation behind Load more; omit it for automatic sequential paging. Heads remain live at the requested interval (hosted minimum 15 seconds); default automatic reconciliation walks again at restEveryS (60 by default) or a changed total. Manual head updates retain loaded depth and a usable deeper cursor. An identical cached head does not overwrite newer continuation rows or summaries.

For a one-time walk use await sdk.queryAll('sessionUsage', {}, {maxRows: 5000}) inside try/catch. Results contain rows, total, returned, complete, truncated, loading, error, canLoadMore, atCeiling, plus authoritative usage totals and days. Hosted results retain actual source, answered_at and server_time when supplied; do not invent freshness. Totals are replaced by the latest accepted summary, never summed from loaded pages.

Built-in list shapes are sessionUsage.sessions (identity: CLI/session pair), queryContext.rows (ID or path), and storyChanges.commits (SHA). These producers support the same paging contract in the app and on hosted pages. Other answer facts stay in the result: for example, storyChanges.sessions stays alongside the accumulated commit rows. Only the selected rows key and paging bookkeeping are removed from metadata. In-app context and usage keep their existing subscriptions; other verbs poll while visible. Hosted subscriptions keep their existing minimum interval of 15 seconds and limit of 20.

Option on queryAll / subscribeAllMeaning
rowsRows key path (such as 'data.items') or answer => array. Enables paging for an unknown verb.
idRow key string or row => stableId. Overrides the built-in identity.
cursor: {arg, next}Request argument name and response key path or answer => cursor|null. For example {arg:'after', next:'continuation'}.
totalResponse key path or answer => number. Omit when unknown; exhaustion alone does not claim complete coverage.
 
const result = await sdk.queryAll('myList', {}, {
  rows: 'data.items', id: 'key', cursor: {arg: 'after', next: 'continuation'}, total: 'count'
});

Options override built-in shapes too. An undefined option keeps its default; cursor merges its arg and next fields individually. An unknown verb without rows keeps its previous single-answer behavior. Each traversal keeps filters and its cursor argument together.

App-only inbox paging uses caller options for its messages and before/hasMore shape. This example uses codesense.kit directly: 

const result = await codesense.kit.queryAll('inbox', {scope: 'to-human', limit: 50}, {
  rows: 'messages', id: 'messageId',
  cursor: {arg: 'before', next: a => a.hasMore ? a.messages.at(-1)?.messageId ?? null : null}
});

The app's routineRuns similarly uses rows: 'runs', id: 'run_id' and cursor: {arg: 'before', next: a => a.next_before}. Hosted inbox answers are bounded and have no continuation cursor; the hosted catalog has no routineRuns query. Caller options describe an available producer's shape; they do not add a query or continuation support to the hosted catalog.

One owner per resource and scope

Keep one handle for the selected story. Stop it before changing scope or rebinding a partialList to the same status and button. Stopping the component also stops its handle. In-flight pages settle without emitting into the replacement view; the revision fence keeps an older page from overwriting a newer head's rows. 

let view;
function selectStory(storyId) {
  if (view) view.stop();
  const resource = 'story:' + storyId, scope = resource;
  view = sdk.partialList({status, button,
    subscribe: cb => sdk.subscribeAll('storyChanges', {storyId, limit: 20}, 30, cb, {manual: true}),
    onResult: result => store.run(resource, scope, async () => result)
  });
}
window.addEventListener('pagehide', () => { if (view) view.stop(); }, {once: true});

Here store is your application's resource store: run(resource, scope, fn) owns each slot's value, error, token and scope, accepting only its current completion. Render charts from that slot. The paging handle owns continuation; the resource store owns accepting the result into application state. Other resources keep their own tokens. For a one-time resource, wrap the whole read: store.run('story:'+storyId, scope, () => sdk.queryAll('storyChanges', {storyId})). This pattern uses the existing paging options and your store; no extra paging API is needed.

Completion requires a known numeric total equal to distinct loaded rows and no next cursor; zero is complete, an unknown total or an overshoot stays partial. Usage identity is the exact (cli, sessionId) pair; context uses stable ID/path. The helper preserves filters and effective limit (default 100), makes one explicit page request at a time, tries one stale-cursor restart and at most two full same-limit mismatch recovery walks, and stops at maxRows (default and hard maximum 5000). This is a moving view, not a snapshot. Old membership disappears only after a successful complete fresh walk.

The component shows loading, unknown totals, exact completion, partial coverage, the row ceiling and Retry. It handles rejected controls without an unhandled Promise and prevents double clicks. To keep an existing layout, pass status and button elements instead of container/render, with onResult(result) for your charts; no duplicate row list is created. Explicit page asks back off 5s × retry, up to six retries. Server-owned hosted head errors remain visible until the next subscription tick (at least 15 seconds). queryAll rejects ordinary errors; live results expose error and retain rows. view.stop() stops its handle, settles its pending lifecycle promises and clears its own retry timers; an already dispatched protected transport may finish.

Limits that apply today

These are the bounds at this build. Where a bound is missing, the table says so and what to do about it; none of them is a promise of new behaviour.

Records tools

CallBound
records_list Reads window only, [start, end], default [0, 200]; at most 200 rows per call. limit is ignored. The answer carries total (the whole collection), so page by moving the window.
records_search limit defaults to 20 and is capped at 200.
records_create, records_write, records_set_fields At most 64 fields per call; a larger call is refused with at most 64 fields per write.
records_history limit defaults to 50 and is capped at 500.

In-app dashboards

ReadBound now
inboxDefault and maximum 500 newest messages; hasMore is true when there were more. Pass limit for fewer.
runsDefault 50, maximum 500, no flag when more exist.
sessionsNo cap: every session in the engine snapshot. Filter and slice in the page.
setupNo args, no rows: {attribution}, this Mac's line-attribution and capture status. In-app it matches describe_setup.attribution; a hosted dashboard declares live: {queries: [setup]} and gets the allow-listed subset (no git-ai path, warnings or status messages). Capture counts are since the app started. See setup-status.html.
sessionUsageReturns sessions, total, totals, days, nextCursor?. Pass the same filters and limit with the next cursor; kit.queryAll or kit.subscribeAll handles the walk with a default page size of 100 and hard collection ceiling of 5000.
files.readText up to 1.5 MiB (maxBytes cannot exceed it); truncated says it was cut.
files and records topicsA view starts with at most 200 rows; ask for more with page(topic, cursor).
queryContextDefault 200 rows, up to 10000 per direct call, with a cursor to page. The shared helper uses a default page size of 100 and a hard 5000-row collection ceiling.

Hosted dashboards

  • Size. An answer is at most 256 KB as JSON. List queries (sessionUsage, sessions, runs, inbox, queryContext) keep the rows that fit, measured after redaction, and cut from the end of their own order. When rows were cut for size the answer object carries truncated: true and returned (the rows sent). The first row is always kept, so a later row that does not fit just ends the list early, flagged as above. Only a first or only row over the cap, or a single non-list value over it, is an error, answer_too_large: show "too big, narrow the query".
  • Row caps. sessionUsage, runs: default 50, maximum 500. sessions and inbox: at most 500. queryContext: limit defaults to 500 and is capped at 500.
  • Cuts that are not flagged. runs is a bare array, so it has nowhere to say it was cut: compare its length with your limit. sessionUsage carries full-window total, totals and days even when rows are partial; its nextCursor allows continuation. Use the helper rather than inferring completeness from page length. sessions cuts in handle order, not by recency.
  • queryContext marker. truncated means the query matched more rows than it returned (total is the match count), and returned appears only when a size cut was added. Treat truncated as "the list is partial".
  • Paging. Hosted queryContext and sessionUsage accept cursor and returns nextCursor when rows follow the last row sent, including after a size cut. Pass it back as cursor with the same other arguments until nextCursor is absent. If the index changes, the cursor is refused; restart without a cursor, or use queryAll/subscribeAll for bounded recovery and status. Narrow with filters, match and where.kinds when needed. A hosted collection or folder selector is not available yet.
  • Freshness. A hosted query repeats by polling, no faster than every 15 seconds (every_s is raised to 15), with at most 20 subscriptions per page. Only streams such as inbox push.
