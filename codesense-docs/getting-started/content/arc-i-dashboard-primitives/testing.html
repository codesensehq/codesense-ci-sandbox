Arc I · Loop

Edit. Reload. Confirm.

A dashboard is a text file in your context repo. You edit it in any editor, the open tab in CodeSense reloads, you see the change. There is no build step, no hot-module tooling, no sourcemap drama. This page walks the loop end to end — probing the bridge, catching errors, previewing the file standalone before you plug it into the viewer.

The inner loop

  1. Edit the HTML in any editor

    Your dashboard file lives under dashboards/ (or wherever you put it) inside the active context repo on disk. CodeSense doesn't lock the file; open it in your editor of choice, save normally.

  2. Watch the tab reload

    When the file changes on disk, the open tab reloads its iframe, re-injects the bridge, and your doc runs fresh. State you kept in JS memory resets — persisted state (via codesense.setField or your own localStorage) survives.

  3. Confirm the change in place

    If your dashboard renders a list, add a row via the matching write verb and watch the list update. If it reacts to state, make a small change in another surface (toggle a routine, send a message) and watch the handler fire.

  4. Error? Inspect in place.

    The viewer forwards window.onerror and unhandledrejection to the host via codesense:doc-error, which renders a red banner inside the frame with the message, source, and line.

Probing the bridge from a script

The shipped app has no web inspector, but any script in your dashboard can call window.codesense. Probe a verb from a scratch copy of the page before you wire it into UI code, and print each result into the page to read it. Put it in a <script type="module">, which allows await at the top level: 

// Print each result into the page, one block per result.
const show = (label, value) => {
  const pre = document.createElement("pre");
  pre.textContent = label + ": " + JSON.stringify(value, null, 2);
  document.body.append(pre);
};

// What verbs are exposed?
show("members", Object.keys(window.codesense).sort());

// Dry-run a verb to see the result shape
show("worktrees", await codesense.invoke("worktrees", {}));

// Snapshot the current theme palette
show("theme", await codesense.theme());

// Simulate what a parent nudge would do
window.dispatchEvent(new MessageEvent("message", {
  data: { type: "codesense:context-changed", orgs: [], allOrgs: 0, truncated: false }
}));

The last line is the trick for exercising a subscriber without the host actually moving: run it and watch your handler fire. Have the handler write what it saw to the page to check its filter logic.

Previewing the file standalone (file://)

Sometimes the fastest round-trip is opening the file directly in a browser from file:// — no viewer, no bridge. The viewer-injected window.codesense isn't there, so you need to feature-detect and provide a stub for the shapes you render. The pattern: 

const bridge = window.codesense || {
  // Minimal stub for standalone preview. Return a fake result for every verb
  // your doc exercises; log the call so you can see the flow.
  invoke(verb, args) {
    console.log("[stub] invoke", verb, args);
    const fakes = {
      context: { org: "you/context", team: "default", layer: "team", contentRoot: "/tmp/ctx" },
      worktrees: [
        { kind: "story", storyId: "DEMO-1", branch: "feat/DEMO-1" },
      ],
    };
    return Promise.resolve(fakes[verb] || null);
  },
  subscribeContext(_query, fn) {
    fn({ rows: [] }, null);
    return () => {};
  },
  onTheme() { return () => {}; },
};

// Use the stub when the real bridge is absent
bridge.invoke("worktrees", {}).then(render);

The stub stays in the file; the viewer's real codesense takes precedence when the dashboard runs inside CodeSense. The upshot: you can iterate on layout and render logic by double-clicking the HTML, then plug it into the viewer to verify the live bridge.

Snapshot — freezing a view for later

Centre-tab dashboards have a Snapshot band at the top of the chrome. Click it to serialize the current DOM — the host archives it under snapshots/ in the context repo. The next time you open the same dashboard, a baseline toggle appears; clicking it loads the frozen HTML in the baseline shape (opaque origin, no bridge) so you can diff the current state against the recorded one.

Snapshots are the right tool when:

  • You want to review what a dashboard showed a human during a decision.
  • You want to compare "before and after" an agent run without screenshotting.
  • You want to attach a reference view to a story or inbox message.

Trigger a snapshot programmatically from your doc: 

document.getElementById("save-view").addEventListener("click", () => {
  codesense.snapshot({ selected: state.selectedId });
});

Common pitfalls

  • Calling invoke before the bridge is ready. The viewer injects the bridge before your scripts run; relying on a late network fetch is fine. If you're sure the race exists, wait for codesense:ready from the parent before firing the first call.
  • Expecting ⌘W to close a right pane. Right panes ignore the close chord; the person closes a pane from the right pane's own controls.
  • Writing a long dashboard as an inbox message. Inbox messages auto-size; anything over ~500 px of content wants to be its own tab. Link to a centre-tab dashboard from the message instead.
  • Hard-coding colours. If the dashboard reads fine on one theme and disappears on the other, you've authored a hex instead of consuming a token. Grep your file for # + rgb + hsl.
  • Forgetting to clean up subscribers across view swaps. If your dashboard is a mini-SPA with routes, call unsubscribe() on your way out of a view. The viewer only drops listeners when the whole frame unloads.

Agent-side equivalent

An agent iterating on a dashboard follows the same loop with different levers: 

# Edit: with the agent's own file tools, in the team's content folder

# Read what the open page rendered (select it in CodeSense first)
read_rendered_document { format: "text" }

Agents don't get a browser inspector; they read the rendered page with read_rendered_document to catch failures.
