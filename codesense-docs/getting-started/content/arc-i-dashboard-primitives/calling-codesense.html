One call. A promise. A clear error.

Every action a dashboard performs — read the inbox, open a workspace, send a message, start a routine — goes through one function: window.codesense.invoke(verb, args). It returns a Promise. It resolves with the result shape documented in the explorer, or rejects with an error whose message you can match on. Most named methods you'll meet (codesense.openFile, codesense.inbox, codesense.worktrees) are thin wrappers over invoke.

The core call

invoke(verb, args) takes a verb name (a string) and an args object. The promise resolves with whatever the verb returns. A failure rejects with a plain Error whose message starts with a stable prefix you can branch on: 

try {
  const here = await codesense.invoke("context", {});
  render(here); // { org, team, layer, contentRoot }, or null outside every content root
} catch (err) {
  // err.message starts with one of:
  //   '… is not allowlisted'  — the verb isn't a bridge verb
  //   'denied: write budget'  — too many writes in a short window (also send, spawn, prefs)
  //   'busy'                  — too many agent launches already running
  //   'unavailable: …'        — the backend for this verb is down
  // or it is the app's own refusal, word for word.
  if (err.message.endsWith("is not allowlisted")) showFallback();
  else throw err;
}

The invoke tab of the explorer lists every verb with its arguments.

The allowlist contract

invoke accepts only the page-bridge verbs. Anything else is refused before it reaches the app — there is no route to a raw command. MCP tool names such as list_orgs_teams are for agents, not pages; a page that calls one gets … is not allowlisted.

Each verb needs a capability grant (for example inbox:write); a call without it is refused with denied: grant. By default an allowlisted verb with its grant runs without a confirm sheet. The team-safe preset and per-dashboard settings add confirm sheets for destructive or send-as-you verbs, and loadMedia always asks. The classes below decide which calls are logged and which runaway limit applies. Writes are confined by the app itself — a page can only edit content CodeSense manages, so a write into the read-only docs org is refused.

files.delete and files.move are allowed by default: a page that holds the grant can delete or move team content files without a confirm sheet. Dashboards are your own files and run with the app's page APIs, so open only dashboards you trust (see How CodeSense trusts agents). Both verbs are confirmable, so a per-dashboard setting can make each call wait for the person. If they decline, nothing is deleted or moved, and the page's promise resolves with {status: "cancelled"} rather than rejecting. After an approval it resolves with {status: "confirmed", result: ...}.

To set it, edit app-state.json in the app's data directory (~/Library/Application Support/ai.codesense/app-state.json for the macOS app) and add the verbs under your profile's dashboardPolicy.perDashboard, keyed by the dashboard's exact identity. The profile section is localProfileWorkspacesV1 keyed by your local principal, the same numeric user id the app shows for your account. Change only these fields and keep everything else in the file, including other profiles. The app watches the file, and the policy is read on every dispatch, so the next files.delete or files.move call uses the new setting; see Configuration is live too.

The key is not the dashboard's title. For an ordinary dashboard document it is the file's absolute path, with no doc: prefix. For a pane it is the pane's key, such as dashboard:team:<org>:<team>/<id> or dashboard:built-in:<org>/files-tree. A setting only affects the dashboard it is keyed to. 

{
  "localProfileWorkspacesV1": {
    "<account-id>": {
      "dashboardPolicy": {
        "perDashboard": {
          "/Users/me/work/acme-context/eng/content/dashboards/board.html": {
            "files.delete": "prompt",
            "files.move": "prompt"
          },
          "dashboard:team:acme:eng/triage": {
            "files.delete": "prompt"
          }
        }
      }
    }
  }
}

Verb classes

codesense.loadMedia({messageId}) fetches one inbox image only after the user asks to see it. It works in an Inbox pane: the built-in one, or a custom Inbox fork that keeps the human-inbox surface. Ordinary pages and message frames are refused with denied: loadMedia requires the Inbox pane, even with inbox:write. In an Inbox pane it needs the inbox:write grant and asks the user to confirm.

act('archive', {messageIds}) archives the human's messages and marks them read. To offer an Undo, keep the ids that were unread before archiving and pass them back: act('unarchive', {messageIds, restoreUnread}) unarchives the messages, makes the restoreUnread ones unread again and leaves the others read. It needs the same inbox:write grant as archive and resolves {unarchived: n}.

Three canonical patterns

  1. Read something and render it

    The simplest shape. Read once, render, done. Keep page-load calls to read verbs; anything that writes or launches belongs behind a button. 

    codesense.worktrees().then((wts) => {
  for (const wt of wts) renderRow(wt);
});

  2. Act on a click

    A write or a launch runs as soon as you call it, so put it behind a button the person clicks: 

    <button id="go">Open DEMO-12</button>
<script>
  document.getElementById("go").addEventListener("click", () =>
    codesense.invoke("openWorkspace", { storyId: "DEMO-12" }),
  );
</script>

  3. Subscribe and re-read

    Live dashboards wrap the read in a function and let a nudge event trigger it. See reacting to state for the full pattern — the short version: 

    function reload() {
  codesense.inbox().then(render);
}
reload();
codesense.onInboxChanged(reload);

Write for older apps too

A team's panes and dashboards reach every teammate, including people whose app has not updated yet. A page that uses a member their app lacks stops with a TypeError before it finishes loading.

Before you use a member the oldest supported app lacks, check that it exists. Calling it, reading through it, reading it into a variable and destructuring it are all uses. Any of these checks works: 

codesense.onTeardown?.(stop);

if (typeof codesense.onFlush === "function") codesense.onFlush(save);

async function load() {
  if (!codesense.subscribe) return showNotice("Update CodeSense to see this list.");
  render(await codesense.subscribe("sessions", { onChange: render }));
}

const kit = codesense.kit;
const list = typeof kit.virtualList === "function" ? kit.virtualList({ container, rows, render }) : null;
list?.setRows(rows);

The check must sit at the use: in the same condition, an earlier return in the same block, or a const that holds the test. A check made elsewhere does not count. The release check follows codesense through variables and function parameters; a parameter named cs, codesense or kit is treated as the API or its kit even when the caller is not visible. When a feature is missing, say so on the page (for example "This view needs a newer CodeSense") rather than leaving it empty. With a check, an older app shows the page without that feature, and a current app works as before.

The oldest supported app is CodeSense 0.0.25. Every supported app has these members, so they need no check: act, agent, agents, context, firstPaint, getNavSelection, humanStatus, inbox, invoke, kit, machines, modelRates, onAgentsChanged, onInboxChanged, onMachinesChanged, onNavSelectionChange, onRoutineResult, onRoutinesChanged, onSessions, onTheme, onVisibility, onWorktreesChanged, openFile, prefs, queryContext, readWorkspace, roles, routine, routineCancel, routineRefresh, routineResult, routineRun, routineRuns, routineStatus, routines, run, runEvidence, runWorkProduct, runs, sessionUsage, sessions, setBadge, setField, setPrefs, snapshot, sprints, subscribeContext, taxonomy, theme, updates, version, worktrees.

Nested members (the kit) every supported app has: kit.agentState, kit.agentStates, kit.avatar, kit.call, kit.dagSvg, kit.dagView, kit.edgePath, kit.empty, kit.h, kit.has, kit.icon, kit.iconMarkup, kit.iconNames, kit.keyed, kit.layoutDag, kit.live, kit.notice, kit.on, kit.phase, kit.phaseBadge, kit.phases, kit.s, kit.skeleton, kit.statusBadge, kit.statusDot, kit.storyBadge, kit.storyStatus, kit.storyStatuses, kit.timeAgo, kit.version.

Kit helpers for file-nav panes

Panes that replace the file list reuse the app's own rules instead of copying them: kit.fileKindOf(path) names a file's kind for kit.fileKindIcon; kit.stripViewerExtension(name) and kit.stripPipelineExtension(name) drop the extensions the nav hides; kit.inLens(lens, story) and kit.countLenses(stories) decide and count lens membership; kit.stageGroupOf(story) gives the by-stage group; and kit.compareNavNames(a, b) is the nav's name order, for Array.sort. How to do this via MCP

Agent-side equivalent

Pages and agents reach the same app through different doors. A page calls bridge verbs; an agent calls MCP tools. Many read verbs have an MCP twin: 

# Page
await codesense.invoke("worktrees", {});

# Agent (MCP tool)
list_worktrees {}

Spend caps require a person to loosen

Agent and routine reads include budgetUsd, budgetPending and spend. An edit through MCP or an embedded page can tighten a cap immediately; raising or removing it only saves a pending request. The native app's Spend cap controls are the acceptance surface. Pages cannot invoke the native set or accept commands.

This enforcement covers CodeSense surfaces. Agents run as you; give an agent you don't fully trust sandboxed permissions. See the Architecture boundary and How CodeSense trusts agents.

setModelRate changes that lower counted spend, including pricing an unpriced model, also stay pending until native acceptance. Raising rates applies immediately. See Spend caps.

Tool reference

Reference for MCP tools that act on the app's panes: commands, rendered documents, canvases and workspace card order. The page verb codesense.commands.list() returns the same rows as command_list, and codesense.commands.run(id, args) does what command_run does.

Commands

command_list

Lists the commands the slot dashboards (right-pane, dock and file-nav) declare that you may run: [{id, label, scope, binding, dashboard, active, humanOnly}]. id is what command_run takes. scope is where the person's chord fires and does not limit command_run. active is false while the dashboard has narrowed its commands with codesense.commands.register; an inactive command cannot run. A dashboard whose policy grant lacks commands:run is left out.

{
  "tool": "command_list",
  "arguments": {}
}

command_run

Runs a slot dashboard's command by id from command_list, with optional args for the page. The app reveals the dashboard's slot if it is closed and delivers the command once, after the page is ready, as the person's chord does. Returns {requested:true} once dispatched; the page acts on its own. Refused with denied: grant when the dashboard's policy grant lacks commands:run, denied: ... is for humans only for a humanOnly command, unavailable: for an inactive one, and unknown command for an id command_list does not list.

{
  "tool": "command_run",
  "arguments": {
    "id": "<id from command_list>",
    "args": {}
  }
}

Rendered documents and canvases

read_rendered_document

Reads an already-open HTML document or team/private pane's rendered DOM, without writing an archive or refreshing data. Select the document tab or show the pane in the main window first, and use the absolute path from pane_list; closed, hidden and fallback panes return actionable errors. format is text (default, readable text) or html (frozen serialized HTML with injected scripts removed). Returns sourcePath, format, content, capturedAt and truncated (512 KiB cap). It is point-in-time DOM content, not a screenshot, and it never opens documents, runs collection or changes schedules.

{
  "tool": "read_rendered_document",
  "arguments": {
    "path": "/abs/context/_team/engineering/content/dashboards/status.html",
    "format": "text"
  }
}

apply_canvas

Validates and atomically writes a shared Excalidraw canvas. path is a target .excalidraw file on the content rails, or under a registered source-repo attachment or worktree. elements are lightweight shapes {type, x, y, width?, height?, text?, label?, points?, strokeColor?, backgroundColor?} with type of rectangle, ellipse, diamond, text, line or arrow. It is a whole-scene apply: the elements you pass become the entire scene. Malformed input is rejected before any write. Returns {writtenPath, elementCount}.

{
  "tool": "apply_canvas",
  "arguments": {
    "path": "/abs/context/_team/engineering/content/diagrams/flow.excalidraw",
    "elements": [
      {
        "type": "rectangle",
        "x": 0,
        "y": 0,
        "width": 200,
        "height": 80,
        "text": "Start"
      }
    ]
  }
}

render_canvas

Renders an .excalidraw file's current on-disk scene to a PNG through the live app's exporter and returns the bytes inline as an MCP image block, plus a text block with sourcePath, byteLen and mimeType. No file is written. It needs the CodeSense app open, and returns an actionable error in headless runs. path is absolute, on the context-repo rails or a registered source-repo attachment or worktree. Use it to verify a canvas you just wrote with apply_canvas.

{
  "tool": "render_canvas",
  "arguments": {
    "path": "/abs/context/_team/engineering/content/diagrams/flow.excalidraw"
  }
}

Workspace card order

reorder_workspace

Reorders a workspace card in its team's shared display order, as card drag and the page moveWorkspace verb do. Pass teamKey (org:team), workspaceId and exactly one anchor workspace id: before or after. It changes display order only; move_workspace moves a workspace to another machine. Returns {requested:true} after dispatch to the desktop viewer; unknown ids and unchanged placements are no-ops.

{
  "tool": "reorder_workspace",
  "arguments": {
    "teamKey": "acme:engineering",
    "workspaceId": "story:DEMO-13",
    "before": "story:DEMO-12"
  }
}
