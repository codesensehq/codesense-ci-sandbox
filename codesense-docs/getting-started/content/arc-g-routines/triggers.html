Arc G · Routines

Pick your trigger.

A routine's triggers: list says when it fires; with none it is manual only. Each entry is a schedule (cron and time zone) or an event of kind inbox_idle, role_pending, agent_done or metadata_change. You can list several in one routine — "fire on inbox_idle, and also every hour as a safety net." Whatever fires it, the routine's mode decides what happens: wake types the task into its agent's running session, start a new (fresh) starts a new one. runs_on: each_mac is not a trigger but a scope for per-Mac recipes. Metadata triggers run personally or once for the team. Each example below is a drop-into-your-repo copy, under the agent it runs.

1 · inbox_idle

event · inbox_idle Wake the agent when mail waits

When: a session sits idle at its prompt with unread mail (at most once every 30 seconds per routine). With mode: wake only the routine's own agent's sessions count, and the one with the mail is woken: a worker's mail never wakes the Manager. With mode: fresh any session launched in the team counts. Why: a Claude agent with an inbox waiter is woken by new mail at once, but one that leaves its mail unread, or an agent with no waiter, sits idle with it; this is the nudge for those. After 3 wakes that leave the same mail unread, the runner stops repeating that mail and records the reason in routine run history. Inspect it with routine_runs then routine_run. Trigger context (fresh runs only): {{trigger.sessions}}, {{trigger.count}}. 

# config/agents/manager/routines/manager-wake/routine.yml
id: manager-wake
name: Wake the manager
owner: codesense
mode: wake
task: |
  You have unread mail. Call read_messages with your session id, then
  claim_role_messages for the manager role, and carry on with /manage-team.
  If there is nothing for you, say so in one line and wait.
where:
  kind: team_workspace
  machine: local
triggers:
  - event:
      kind: inbox_idle
policy:
  max_runtime: 5m
runs_on: each_mac
revision: 1

Copyable trigger recipes

The trigger cookbook gives a full MCP dry run, complete routine.yml, validation and result-reading instructions for schedule, metadata trigger, inbox_idle, agent_done, role_pending and after chaining. See command routines for the metadata → command → agent chain.

Alongside metadataTriggers and schedules, events accepts inbox_idle, agent_done and role_pending through routine_create and routine_update. Preview creation with dryRun:true. For role_pending, omit role to watch every queue in reach, or set role:"reviewer" to watch just reviewer mail.

When a field changes

In the routine editor, add a metadata trigger, choose a document kind and optional folder, then a field and the value it changes to. For example: when a story's status becomes in-progress. Set From to planning to require that exact transition. Custom frontmatter and HTML cs:* fields use the same selection and equality as query_context. List fields say “gains”: gaining blocked in tags fires once.

With routine_create, set when: "" for triggers without a schedule:

{"metadataTriggers":[{
  "selection":{"where":{"kinds":["story"],"pathPrefix":"stories/"}},
  "target":{"key":"status","op":"eq","value":"in-progress"}
}]}

For planning → in-progress, add "previous":{"key":"status","op":"eq","value":"planning"} beside target. A custom boolean target can be {"key":"review_requested","op":"eq","value":true}. Text compares exactly; a JSON number compares numerically. The editor sends text. routine_get returns the conditions. On update, omit metadataTriggers to preserve them, send the whole replacement list to edit, or send [] to remove them. Schedules and other events remain.

First discovery, restart, enabling and editing establish a baseline: documents already matching do not replay. Only a later observed entry fires. Unrelated edits do not fire; leaving and re-entering can. New or moved files without an observed previous value do not fire. Debounced saves may settle into one change; changes while observation was stopped are not replayed. The routine watches its synced team or personal files even with another team displayed.

Normal overlap and placement policies apply, without the agent-done five-minute throttle. Wake prompts stay static. Read routine_context with your sessionId and the wake header's runId: trigger_payload identifies org, team, path, story ID, field, previous_present, previous_value and new_value; coalesced_payloads retains every merged change. Fresh tasks may also use supported {{trigger.*}} fields.

2 · cron

schedule · cron Keep a manager on the queue

When: on a wall-clock cadence: a 5-field cron in an IANA zone (tz); nothing more often than every 5 minutes. Why: for liveness backstops, synthesis passes, nightly sweeps. As a wake on machine: any, this one checks in with the Manager wherever it runs, and starts one when none is running. A Manager on a machine that is offline still counts as running: that fire is undelivered (machine_offline) and no second Manager starts while that machine stays offline. Choose limits for the work: a light check like this one can wake every 15 minutes for weeks; there is no lifetime cap. A wake that starts heavy work should set min_gap (and maybe max_wakes_per_day or max_wakes) under policy, so it never rewakes or piles up. 

# config/agents/manager/routines/manager-ensure/routine.yml
id: manager-ensure
name: Keep a manager on the queue
owner: codesense
mode: wake
task: |
  Check the manager queue. Call role_state with role "manager".
  If anything is pending, claim it with claim_role_messages and carry on
  with /manage-team. If nothing is pending, say "manager queue empty" in
  one line and wait.
where:
  kind: team_workspace
  machine: any
triggers:
  - schedule:
      cron: "0 * * * *"
      tz: UTC
policy:
  max_runtime: 5m
  overlap: skip
revision: 1

3 · manual

manual Human-gated release cut

When: only when someone presses Run now on the routine, a dashboard's Refresh calls routineRefresh, or an agent calls routine_run_now. Why: for operations you keep in human hands — a release cut, a destructive sweep, an expensive one-shot. No triggers: at all. 

# config/agents/amelia-builder/routines/ship-release/routine.yml
id: ship-release
name: Cut a release
owner: you
mode: fresh
task: |
  Confirm main is green, cut the release, and tag the merge commit.
  Call signal_done with the tag name.
where:
  kind: team_workspace
policy:
  max_runtime: 30m
  visible: true
revision: 1

4 · agent_done

event · agent_done Review after the Builder finishes

When: an agent finishes (signal_done); from_agent narrows it to one. Why: to chain agents without a dispatcher. The routine shows under the agent it runs (the Reviewer), with an "after amelia-builder" note. Trigger context (fresh runs only): {{trigger.session_id}}, {{trigger.status}}, {{trigger.summary}}, {{trigger.agent}}. 

# config/agents/winston-reviewer/routines/review-after-build/routine.yml
id: review-after-build
name: Review what the Builder shipped
owner: you
mode: fresh
task: |
  The Builder finished: {{trigger.status}} — {{trigger.summary}}.
  If it opened a PR, review it with bmad-code-review and post the review.
  Call signal_done with the verdict.
where:
  kind: team_workspace
triggers:
  - event:
      kind: agent_done
      from_agent: amelia-builder
policy:
  max_runtime: 30m
revision: 1

5 · role_pending

event · role_pending Start a builder for each queued task

When: a message is queued for a role inbox the routine can reach (its own team's for a team routine; every team in the org for an Only me one). It watches the builder queue in this example. Omit role for every queue in reach. It fires once per message, and never on a message its own run queued. Why: nothing claims a role message on its own; this lets a routine start an agent that claims it. Trigger context: {{trigger.role}}, {{trigger.message_id}}, {{trigger.org}}, {{trigger.team}}. 

# config/agents/amelia-builder/routines/build-on-request/routine.yml
id: build-on-request
name: Build what lands in the builder queue
owner: you
mode: fresh
task: |
  A message is waiting for the {{trigger.role}} role. Claim it with
  claim_role_messages, do the work it asks for, then call signal_done.
where:
  kind: team_workspace
triggers:
  - event:
      kind: role_pending
      role: builder
policy:
  max_runtime: 60m
revision: 1

6 · each_mac

runs_on · each_mac One per teammate's Mac

When: paired with any trigger above as a scope. Why: sessions and inboxes are per Mac, so a recipe each teammate turns on for their own Mac ("Run on my Mac", or routine_set_enabled) wakes or starts that Mac's own agent. So an each_mac routine must use machine: local (or leave it out), except that a fresh one may use any (each Mac starts its own); a machine id is refused in either mode, since every teammate's Mac would wake or start the same agent there. 

# config/agents/winston-reviewer/routines/reviewer-wake/routine.yml
id: reviewer-wake
name: Wake the reviewer
owner: you
mode: wake
task: |
  You have unread mail. Claim one message for the reviewer role with
  claim_role_messages, review it with bmad-code-review, then ack it.
where:
  kind: team_workspace
  machine: local
triggers:
  - event:
      kind: inbox_idle
policy:
  max_runtime: 30m
runs_on: each_mac
revision: 1
