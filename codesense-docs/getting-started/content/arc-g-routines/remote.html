Routines on remote machines.

A routine's YAML sits in the context repo and syncs with every teammate. The firing, though, is per Mac — because a Mac is where the wall clock ticks, where the inbox lives, and where the agent spawns. Remote routines (ones that run on a build box or a teammate's always-on machine) use the same YAML as local routines; the only knobs that change are runs_on (the mode) and armed_here (this Mac's local switch). The Arc-D parity matrix treats routine schedules as the main caveat row — remote scheduling is strictly better than local for anything "always on".

Two modes: each_mac vs one_mac

runs_on: each_mac

A recipe each teammate turns on for their own Mac. Fires per Mac that armed it, each with its own schedule, its own history, and its own {{last_run_summary}}. Starts off on every Mac — including the author's — unless the routine ships with enabled: true.

  • Use for per-person work: "my morning digest", "PRs waiting on me".
  • Use for inbox_idle wakes (sessions are per Mac).
  • Use for sweeping remote fleets — one definition, N independent fires.

runs_on: one_mac (the default)

A shared job that runs once for the team, from exactly one Mac — the one it was armed on. Perfect for anything that must happen once (a Slack digest, a release-cut check), and the thing that should move to the always-on remote box when you want "never skipped".

  • Use for team-wide must-fire schedules.
  • Arm it on the remote account for always-on behavior.
  • Switching the arming Mac is a routine_update from the target Mac.

Wake an agent that runs on another machine

runs_on says which Mac's clock fires a routine. where.machine says where its agent is: local (this Mac, the default), a machine id from list_machines, or any connected machine.

  • Wake on a machine. The desktop hands the task to that machine, and the machine types it into the agent's session when it is idle. The wait happens there, so the wake still lands if your desktop drops meanwhile.
  • Nobody running there. A wake starts the agent on that machine, in its prepared workspace, with the task as its first prompt. any with no agent running anywhere starts it on this Mac.
  • Machine offline. A session last seen there still counts as live, so nothing starts a duplicate: the run is undelivered (machine_offline) and the next fire tries again. A machine this desktop doesn't know is undelivered (machine_unknown), with a fix.
  • An old terminal server. Wakes and timers need a current one; the run says "Update the terminal server on ‹machine›".

With runs_on, an each_mac routine must use machine: local (or leave it out), except that a fresh one may use any (each Mac starts its own); a machine id is refused in either mode, since every teammate's Mac would wake or start the same agent there. To have the machine's own clock fire a routine, arm it there with routine_arm_on and a machine id: its terminal server fires it on schedule whether or not any Mac is open, once for the team, and this Mac prepares its agent there and records its runs. A routine armed on a machine runs on its schedule only (no agent_done, inbox_idle or role_pending triggers). routine_arm_on with machine: "this_mac" moves it back.

The per-Mac switch

enabled on a routine is a per-Mac field: it names whether this Mac fires the routine. Flipping it is routine_set_enabled, which is a local edit to the Mac's state (never a git change, never shared). 

// Turn the routine on for THIS Mac
codesense.invoke('routine_set_enabled', { id: 'builder-wake', enabled: true })

// Turn it off for THIS Mac — other Macs that armed it are unaffected
codesense.invoke('routine_set_enabled', { id: 'builder-wake', enabled: false })

// Which Macs is it armed on? routine_get on each; each Mac answers for itself.
codesense.invoke('routine_get', { id: 'builder-wake' })
//   → { ..., armed_here: true, next_run_at: "2026-10-06T19:05:00Z" }

For a one_mac routine, exactly one Mac has armed_here: true at a time. Switching the arming Mac is a routine_update from the target — "pull the arming to this Mac", not a flip on the current one.

Parity caveats

Three rows from the Arc-D parity matrix describe how remote routines differ from local ones:

  • Run a routine — ✓ local, ⚠ remote. Caveat: a routine fires in the account that owns the triggering workspace. If you want "always on", own the routine on the always-on machine.
  • Routine schedule (cron) — ✓ local, ⚠ remote. Local Macs skip fires while asleep (standard Mac behavior); remote always-on boxes never skip. Workaround: own must-fire schedules on the remote.
  • Wake and timers — ✓ both. A remote session is woken, and its timers fire, by the machine it runs on, with the same idle and no-collision rules as a local one. See agent wake and session timers.

Try this now

List every routine on the active team along with its mode and arming state. The response includes runs_on and armed_here for each, so you can see at a glance which fires where.

How to do this via MCP 
// Every routine, each Mac's arming state
codesense.invoke('routine_list', {})

// A specific routine, with armed_here + next_run_at from THIS Mac's view
codesense.invoke('routine_get', { id: 'builder-wake' })

// Flip this Mac's per-Mac switch (local, never a git change)
codesense.invoke('routine_set_enabled', { id: 'builder-wake', enabled: true })

// Move the arming of a one_mac routine to THIS Mac
codesense.invoke('routine_update', {
  id: 'nightly-digest',
  baseRevision: 3,
  armHere: true,
})

// Fire it once (through its own overlap rule)
codesense.invoke('routine_run_now', { id: 'builder-wake' })
