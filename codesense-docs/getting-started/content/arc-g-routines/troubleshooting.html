When a routine misbehaves.

The routines console is the one surface that answers every question on the ladder above — the next scheduled fire, the last run with its status chip, the recent-N timeline, and the per-run detail with task template, stdout, and the publish side-channel. Open it first; the symptom names the step that failed.

Symptom catalogue

A run is stuck in running step 5

The agent launched but never called signal_done and never exited. maxRuntime will cut it eventually; you can cancel sooner.

  1. Open the run on the routines console; the stdout tail usually names the last thing it did.
  2. Use the MCP tool routine_cancel {runId}, with a run_id from routine_runs. It cancels one queued or running run. A fresh run's agent or command stops; a wake run keeps its existing session alive. See the cancel example for returned state, authorization and wake withdrawal errors. To stop future starts too, call routine_set_enabled {id, enabled:false}.
  3. Fix the task: either add an explicit signal_done step, or lower policy.max_runtime so stuck sessions fail fast and surface loudly.
  4. OpenCode agents. When the model provider answers with a server error (5xx), OpenCode retries without printing anything and without exiting, so only policy.max_runtime ends the run. For OpenCode, set a short one (30m suggested). A headless OpenCode run denies any tool outside read-only tools and CodeSense's own unless the agent's permissions.opencode allows it; a denied tool continues with an error turn instead of stopping the run. A headless OpenCode run that exits without calling signal_done ends with the model's final text as its summary; that text is a summary, never the run's result. A provider rejection (a 4xx, an unknown model) fails the run with its message.
  5. Unattended OpenCode. The OpenCode unattended starter keeps --auto. Escalating agents (--auto or an all-allow map) get an allow base headless, and their own denies still apply, so a bash: deny stays denied. Pair such an agent with a sandbox, and still give each of its routines a short policy.max_runtime (30m suggested).

Scheduled fires are missed step 1 · 3

A cron routine shows no run at the expected time. Three usual causes.

  1. Mac was asleep. Fires missed while the Mac was asleep or the app was closed are recorded as one skipped run (reason missed:N); with policy.missed: run_once, one of them also runs as a catch-up. To fire while the desktop is closed, arm the routine on a machine (remote): routine_arm_on { id, machine: <machineId> }.
  2. armed_here is false. routine_get says who's armed; move it here with routine_arm_on { id, machine: "this_mac" } (Run on this Mac) if that's where you want it to fire. An each_mac routine is turned on per Mac instead: routine_set_enabled { id, enabled: true } (Run on my Mac). If routine_get shows it armed on a machine, it fires there on purpose; moving it here ends that always-on firing.
  3. Overlap. A previous run is still going and the new fire coalesced. Check the console for a coalesced badge; shorten the task or raise the cadence.

Every run fails agent_unavailable step 4

The agent named by the routine isn't resolvable. Common after an agent rename or an uninstall.

  1. agent_list {} — confirm the id the routine targets still exists.
  2. If the agent was renamed, routine_update with the new agent id (and the baseRevision you last read).
  3. If it was uninstalled, either reinstall or point the routine at a built-in (builtin/claude, builtin/codex) that every Mac has.

inbox_idle never fires step 2

The queue has mail; the routine doesn't trigger. The idle threshold hasn't been crossed, or the sessions aren't CodeSense-launched.

  1. Check the queue in agent-inbox-console. If messages show unread · 10s ago, the idle threshold (default 2m) hasn't elapsed.
  2. A session a user opened by hand (not through CodeSense) is invisible to inbox_idle. Launch it through the Routines or Agents tab.
  3. Confirm the trigger shape: triggers: [{ event: { kind: inbox_idle, role: builder } }] with the exact role name. A typo in the role becomes a silent miss.

The dashboard shows "collecting" forever step 6

The dashboard binds routineResult but the snapshot never promotes — usually a schema mismatch or a missing publish step.

  1. On the console's run detail, look at latest attempt. A schema_mismatch status means the payload didn't match resultSchema. Fix the task or bump the routine's revision.
  2. If the task never calls routine_publish_result, the run can finish "ok" and yet publish nothing — add the publish step before signal_done.
  3. A dashboard calling routineRefresh at page load (not from a user action) is a lint warning and may be denied for budget reasons; move it behind an explicit Refresh button.

A hand-written routine never shows up step 0

A file that doesn't parse, or whose id doesn't match its folder, is skipped on load (logged only), so it never appears and never fires.

  1. The app's log names the file and the error. The common one is a routine that isn't under an agent: it must sit at config/agents/<agent>/routines/<id>/routine.yml, with the folder name equal to its id and no agent: key.
  2. The next common one is a duplicate id: ids are unique across the team, whichever agent holds them. Rename one.
  3. Still stuck? Compare against the routine.yml schema browser — every field is annotated with its validator rule.

Remote routines fire on the wrong Mac step 3

A one_mac routine fires on your laptop instead of the always-on build box, or vice versa.

  1. routine_get on each Mac answers who's armed. For one_mac, exactly one Mac has armed_here: true.
  2. To move the arming, call routine_arm_on { id, machine: "this_mac" } from the Mac you want to arm. The other Mac's armed_here flips to false next sync.
  3. See remote for the full switching flow.

A wake says queued, undelivered or unknown step 4

A mode: wake run never typed into the agent, or can't say whether it did. The run's Details popover names the reason.

  1. queued — the agent is busy or waiting on a permission prompt; it is typed at the next idle point, up to the max wait, else busy_timeout. Someone typing in that tab holds it back too.
  2. undelivered — machine_offline (tried again next fire), machine_unknown (fix the machine), session_ended, unobservable (CodeSense can't tell when this runtime is idle; Codex today), archived, limit_reached (over the routine's max_wakes_per_day; it resumes on its own), max_wakes (the routine made its max_wakes and paused itself, with one inbox note: resume it to start a new count), rate_limited (the session's safety backstop of 120 wakes an hour tripped, usually a loop; the inbox note names the top source, and it resumes on its own). A fire inside the routine's min_gap is coalesced, or skipped with overlap: skip. A wake with limits to a machine whose terminal server is too old to enforce them is unavailable, with the reason as its detail and one inbox note to update it. Limits count wakes only: a fresh routine ignores them (its save warns), a launch-if-absent start is not counted, and each Mac and machine keeps its own count. A machine-armed routine with limits is not armed on such a machine (it fires nowhere until the terminal server is updated, or the limits removed; the inbox says so once a day).
  3. unknown — "May have been delivered. Check the terminal before re-sending." It is never re-sent automatically; look at the tab's wake history first.
  4. Wake never offered at all? It needs a saved, foreground agent (starters are fresh only), and allowWake: true on an agent that auto-approves tools.

A session timer didn't fire step 4

Timers set with schedule_wakeup belong to one session and wait for it to be idle.

  1. list_wakeups with that session's id: no timer means it ended with its session, was cancelled, or ran out its count / until.
  2. The session is busy: a due fire waits for idle (folding later fires into it), and is dropped as busy_timeout after 24 hours.
  3. Setting, listing and cancelling need the desktop connected; a remote machine keeps firing the timers it already has while the desktop is away.
  4. A remote session reaches the CodeSense MCP tools through the desktop. If the desktop disconnects (sleep, quit, network), that session loses them — including list_wakeups, cancel_wakeup and routine_done — for the rest of its run, even after the desktop comes back; restart the agent to get them back. Its timers and queued wakes keep running on the machine.

Debug toolkit (in order of use)

Tool What it tells you When to reach for it
routines console Next fire, last fire, recent-N strip, run detail (task + stdout + publish). Always first. Nine times out of ten the answer is on the strip.
routine_runs({ id, limit: 20 }) History with skipped and coalesced fires + reasons. When a schedule looks "quiet" and you want proof of why.
routine_run_now({ id }) Fires once through the overlap rule; returns outcome. To bisect: does it work when I fire it by hand?
routine_run({ runId }) One run in full: status, delivery reason, result. When a wake says undelivered or unknown and you want the detail.
routine_create { …, dryRun: true } Validator error with field + rule. When the console says "load failed" with no detail.
routine_cancel({ runId }) Cancels one queued or running run; returns its resulting state. A finished run is unchanged with a validation message. When a run is in running past expected duration.
onRoutinesChanged(() => routineRuns({ key })) Re-reads a routine's runs each time it or one of its runs changes. When you want to watch an inbox-idle wake live.

Try this now

Open the routines console. The symptom catalogue above maps directly to the surfaces on the page: the strip answers the "did it fire" questions, the run detail answers the "what happened" questions.

How to do this via MCP 
// A specific routine's recent history, skipped fires included
routine_runs {"id":"acme/api/backend/builder-wake","limit":20}

// One run in full (a wake's delivery status and reason included)
routine_run {"runId":"<run_id from routine_runs>"}

// Fire once by hand; returns outcome: queued / coalesced / skipped:<reason>
routine_run_now {"id":"acme/api/backend/builder-wake"}

// Cancel one run; future fires stay enabled
routine_cancel {"runId":"<run_id from routine_runs>"}

These are MCP calls, available from a verified CodeSense connection. In a pane, codesense.routineCancel({key}) cancels this principal's live structured results for a routine, rather than one run by id. To validate a routine, call routine_create with dryRun: true.

Why was a fire skipped with budget_reached?

The routine or its agent has reached a daily or weekly spend cap, or has usage that cannot be priced. The skipped run names the scope, window, spend and cap; an unpriced refusal names the model. Open the agent's Overview → Spend cap, or the fresh routine's cap block. Wait for the local window to roll over, or have a person save or accept a cap. Changing a file or MCP value upward leaves the raise pending.

While a local agent is held, mail remains in its inbox and a person can still type. The current turn finishes; queued automatic turns wait. See Spend caps.
