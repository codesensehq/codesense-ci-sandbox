Arc G · Routines

Routines that write dashboards.

You've got a dashboard that needs data the app doesn't know about — a sprint digest, a PR queue, a per-repo failure rate. You don't want the pane to shell out every time it renders, and you don't want the user clicking Refresh for a stale pane. You want a routine to collect once, publish a structured result, and let every open dashboard pane read the same snapshot. That's the structured-data pattern: a routine with a resultSchema, a dashboard that binds routineResult and onRoutineResult, and a context-repo snapshot as the handoff.

Three shapes a dashboard-writing routine can take

Cron sweep

The routine fires on a schedule (every 15m, hourly, daily 09:00). The dashboard reads the last-good snapshot on open and re-reads on onRoutineResult. Great for digests, backlog counts, and any page where "fresh enough" is minutes.

Manual-only

Omit when; the routine fires only on routine_run_now or a Refresh button on the pane. Use for expensive collections, or for pages a user opens on demand.

Event-driven

An agent_done or inbox_idle trigger refreshes the snapshot exactly when upstream data changes. Example: a reviewer's agent_done retriggers the PR-queue digest.

Worked example — DEMO sprint digest

A cron routine sweeps DEMO's stories every 15 minutes, counts stories by phase, and publishes a tiny structured snapshot. The sprint-digest dashboard reads it and shows the four phase chips with the counts live. No polling in the pane, no HTTP from the pane, and no agent launch on every page open — the snapshot is already there.

Three contracts you must honor

  1. Schema pinning. The resultSchema on the routine must match the payload the task publishes. When you update the schema, bump the routine's revision; stale clients get schema_compatible: false back from routineResult and must say so, not render stale data as current.
  2. Page load never launches. routineResult and routineStatus read the cache. Only an explicit user action (a Refresh button, an on-demand workflow) may call routineRefresh. The validator warns on dashboards that call routineRefresh at the top level.
  3. Keep output small. The schema limit is 32 KiB; the payload limit is 1 MiB. Collect once, pre-aggregate, and let the dashboard do presentation. If you need large data, write it under content/ and point the snapshot at a file path.

Local vs remote

Local. The routine fires on the Mac that owns the team workspace; the snapshot is cached in that Mac's CodeSense state. The dashboard pane renders in your window and reads directly.

Remote. If the routine owns a remote context, it fires in the remote account's terminal server. The dashboard reads through the same window.codesense contract — the snapshot is streamed over the bridge exactly as a local snapshot would be. Try this now

Open the shipped reference dashboard for a routine-fed pane and inspect its live-data wiring. The example demonstrates the routineResult + onRoutineResult pattern without any writes.

How to do this via MCP 
// key: the routine's routines() row id, <org>/<team>/<id>
// The dashboard reads (never launches the agent)
codesense.routineResult({ key: 'acme/web/sprint-digest' })
codesense.routineStatus({ key: 'acme/web/sprint-digest' })

// Only an explicit user action may trigger this
codesense.routineRefresh({ key: 'acme/web/sprint-digest' })

// Live notifications when the routine publishes a new snapshot
codesense.onRoutineResult(() => { … })

// Inside the routine's agent (the publisher side)
routine_publish_result { sessionId, payload }
